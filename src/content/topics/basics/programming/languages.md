CPU が直接実行できるのは **機械語** だけです。人間が書いたプログラム（**原始プログラム**、ソースプログラム）を機械語に変換したり、そのまま解釈して実行したりするソフトウェアを **言語処理系**（言語処理ツール）といいます。
ここでは言語処理系の種類と、目的に応じて使い分けられる代表的なプログラム言語・データ記述言語を整理します。

### 前提となる用語

- **機械語・命令**: CPU が直接実行できる 0 と 1 の命令コード。CPU の種類（命令セット）ごとに異なるため、ある CPU 用の機械語は別の種類の CPU では動きません。
- **型（データ型）**: 整数・小数・文字列など、値の種類のこと。型によって、できる演算（足し算、文字列の連結など）が決まります。
- **実行可能ファイル**: OS が読み込んでそのまま実行できる形式のファイル。この記事の **ロードモジュール** に当たります。

## プログラム言語の変遷と分類

| 種類 | 特徴 |
| --- | --- |
| 機械語 | 0 と 1 の命令コード。CPU が直接実行できるが、人間には読みにくい |
| アセンブラ言語 | 機械語の命令を記号（ニーモニック）で表した言語。機械語とほぼ 1 対 1 に対応する |
| 高水準言語 | 人間の言葉や数式に近い形で書ける言語。CPU の種類に依存しにくい |

高水準言語は、考え方（パラダイム）によって **手続型言語**（処理の手順を順に記述）、**オブジェクト指向言語**（データと操作をクラス・オブジェクトとしてまとめる）、**関数型言語**、**論理型言語**、手軽に書いて実行できる **スクリプト言語** などに分類されます。

## 言語処理系

| 名称 | 役割 |
| --- | --- |
| アセンブラ | アセンブラ言語のプログラムを機械語に変換する |
| コンパイラ | 高水準言語のプログラムを **まとめて** 機械語などの目的プログラムに翻訳する。実行は速い |
| インタプリタ | プログラムを 1 命令ずつ解釈しながら実行する。目的プログラムを作らず、修正してすぐ試せる |
| リンカ（連係編集プログラム） | 複数の目的プログラムやライブラリを結合し、実行可能な **ロードモジュール** を作る |
| ローダ | ロードモジュールを主記憶に読み込み、実行できる状態にする |
| 実行時コンパイラ（JIT） | 実行時に中間コードなどを機械語に翻訳しながら実行する |
| クロスコンパイラ | 開発に使うコンピュータとは異なる種類のコンピュータ用の目的プログラムを作る（組込み開発など） |
| プリプロセッサ | コンパイルの前に、ソースプログラムに対してマクロ展開などの前処理を行う |

コンパイラ方式で作ったプログラムは、次の流れで実行されます。

```
原始プログラム → [コンパイラ] → 目的プログラム → [リンカ] → ロードモジュール → [ローダ] → 主記憶で実行
```

コンパイラの内部は、おおむね **字句解析 → 構文解析 → 意味解析 → 最適化 → コード生成** の順に処理を進めます。
字句解析はプログラムを字句（トークン）に分け、構文解析は文法に合っているかを調べて構文木を作ります。

| Python | スクリプト言語。読みやすい文法でライブラリが豊富。AI・データ分析で広く使われる |

## マークアップ言語とデータ記述言語

| 言語 | 特徴 |
| --- | --- |
| HTML | Web ページの構造を **あらかじめ決められたタグ** で記述する。見た目は CSS（スタイルシート）で指定する |
| XML | **利用者が独自にタグを定義できる** マークアップ言語。データ交換に使われる |
| JSON | JavaScript のオブジェクトの表記法を基にした、名前と値の組でデータを表す形式。異なる言語で書かれたプログラム間のデータ交換に使われる |

同じデータを XML と JSON で表すと次のようになります。

```
<book>                          {
  <title>基礎理論</title>          "title": "基礎理論",
  <price>2000</price>              "price": 2000
</book>                         }
```

## 実際の開発での使われ方

### 主な言語の実行方式

試験では「コンパイラ」と「インタプリタ」を対比しますが、現在の多くの言語は、両方を組み合わせた方式で動いています。

| 実行方式 | 主な言語 | 流れ | 特徴 |
| --- | --- | --- | --- |
| 機械語にコンパイル | C、C++、Go、Rust | ソース → コンパイラ・リンカ → CPU と OS ごとの実行可能ファイル | 実行が速い。動かす CPU・OS ごとにコンパイルし直す必要がある |
| 中間コード ＋ 仮想マシン | Java、Kotlin、C# | ソース → 中間コード（Java ならバイトコード）→ 仮想マシンが JIT で機械語にしながら実行 | 同じ中間コードを、仮想マシンのある環境ならどこでも動かせる |
| インタプリタ（内部で中間コードに変換） | Python、Ruby | 実行するときにソースを中間コード（バイトコード）に変換し、それを処理系が 1 命令ずつ解釈して実行 | 書いてすぐ試せる。一般に機械語にコンパイルする方式より遅い |
| JIT を備えたエンジン | JavaScript | ブラウザや Node.js のエンジンが、よく実行される部分を実行中に機械語へ翻訳する | 開発時はスクリプトとして手軽に書け、実行時の性能も高い |

それぞれの処理系の使い方の例です（コマンドは一例）。

```
gcc hello.c -o hello      … C: コンパイルとリンクで実行可能ファイル hello を作る
./hello                   …    作ったファイルを実行する

javac Hello.java          … Java: バイトコード Hello.class を作る
java Hello                …       JVM が Hello.class を実行する

python3 hello.py          … Python: ソースを渡すとそのまま実行される
```

### 静的型付けと動的型付け

言語は、**型をいつ決めて確かめるか** でも分けられます。

| 方式 | 主な言語 | 型の誤りが見つかるとき |
| --- | --- | --- |
| 静的型付け | C、Java、C#、Go、Rust、TypeScript | 実行する前（コンパイル時）。変数や引数の型が決まっており、合わない使い方はコンパイルエラーになる |
| 動的型付け | Python、JavaScript、Ruby | 実行して、その行を通ったとき。変数にはどの型の値でも入れられる |

動的型付けの言語では、次のような誤りが **その行を実行するまで** 見つかりません。

```python
price = 1100
print("税込 " + price + " 円")
# TypeError: can only concatenate str (not "int") to str
```

文字列と整数を `+` で連結しようとしたためで、`f"税込 {price} 円"` のように書けば正しく表示されます。めったに通らない分岐（エラー処理や月末だけの処理など）にこうした誤りがあると、テストで見つからないまま本番で止まることがあります。

このため、動的型付けの言語でも型の情報を書き足して実行前に検査する方法が広く使われています。Python では **型ヒント**（`def tax(price: int) -> int:` のような注釈）を書き、型チェッカーで検査します。JavaScript には、静的型付けを加えた **TypeScript** があり、型を検査してから JavaScript に変換して実行します。

### エラーの種類

| エラー | 見つかるとき | 例 |
| --- | --- | --- |
| コンパイルエラー（構文エラー） | コンパイル時（インタプリタなら実行開始時） | 括弧の閉じ忘れ、静的型付けの言語での型の不一致 |
| 実行時エラー | 実行中にその処理を行ったとき | 0 での割り算、存在しないファイルを開く、動的型付けの言語での型の不一致 |
| 論理エラー | 結果を確かめたとき（エラーとしては出ない） | 税率の掛け間違い、条件の不等号の向きの誤り |

論理エラーは処理系が教えてくれないので、テストで期待する結果と比べて見つけます。

### データ交換には JSON

異なる言語で書いたプログラムどうしは、JSON などの言語に依存しない形式でデータをやり取りします。多くの言語に JSON を読み書きする標準の機能があります。Python の例です。

```python
import json

text = json.dumps({"title": "基礎理論", "price": 2000}, ensure_ascii=False)
# '{"title": "基礎理論", "price": 2000}'  … Python の辞書 → JSON の文字列
book = json.loads(text)
book["price"] + 100   # 2100              … JSON の文字列 → Python の辞書（数値は数値のまま）
```

## 実際の進め方: 言語と処理系を選ぶ

1. **動かす環境を確かめる**: 環境で言語がほぼ決まることがあります。Web ブラウザの画面なら JavaScript（または TypeScript）、iPhone のアプリなら Swift、Android のアプリなら Kotlin（または Java）が標準です。
2. **性能とハードウェアへの近さ**: 組込み機器や OS のように、メモリや速度の制約が厳しくハードウェアを直接扱うなら C・C++・Rust など、機械語にコンパイルする言語が向きます。
3. **既存のシステム・チームの経験**: 既存のシステムと同じ言語にすると、部品やノウハウを使い回せます。基幹系の事務処理では COBOL で書かれたシステムが今も動いていることがあります。
4. **ライブラリの充実度**: データ分析・機械学習なら Python や R、Web のサーバ側なら Java・C#・Python・Go・JavaScript（Node.js）など、目的のライブラリがそろっている言語を選びます。
5. **規模と保守の期間**: 多人数で長く保守するシステムでは、静的型付け（または型ヒント・TypeScript）で誤りを早く見つけられる利点が大きくなります。

## 事例: あおば書店のシステムで使う言語

架空のオンライン書店「あおば書店」のシステムは、役割ごとに異なる言語で作られています。

| 部分 | 言語 | 選んだ理由 |
| --- | --- | --- |
| 利用者が操作する画面（ブラウザ） | TypeScript（JavaScript に変換して実行） | ブラウザで動くのは JavaScript。画面の部品が多く、型の検査で誤りを減らしたい |
| 注文・在庫を扱うサーバ | Java | 開発チームの経験が豊富。静的型付けで、長く保守しても誤りを見つけやすい |
| 売上の集計・分析 | Python | 表データの集計やグラフ作成のライブラリが充実している |
| 倉庫のバーコード読取り端末 | C | メモリの小さい専用端末で動かすため、機械語にコンパイルして使う。開発用のパソコン上でクロスコンパイラを使って作る |

画面とサーバ、サーバと倉庫の端末の間は、JSON 形式でデータをやり取りしています。言語が違っても、JSON の形を決めておけば互いの内部の作りを気にせずに済みます。

あるとき、Python の売上集計スクリプトが月末の締め処理の途中で止まりました。返品があった月だけ実行される分岐で、返金額（整数）を文字列と `+` で連結していたため、`TypeError` が発生していました。返品のない月のテストでは、その行が一度も実行されていなかったのです。対策として次を行いました。

- 誤りの行を `f"返金額: {amount} 円"` の形に直す
- 関数の引数と戻り値に型ヒントを書き、型チェッカーをテストと一緒に毎回自動で実行する（実行しなくても型の不一致が分かる）
- 返品がある月・ない月の両方のデータでテストする

## 例題

**例題** コンパイラとインタプリタの説明として適切なものはどれか。
(ア) コンパイラは 1 命令ずつ解釈して実行する (イ) インタプリタは目的プログラムを作成してから実行する
(ウ) コンパイラは原始プログラムをまとめて目的プログラムに翻訳する (エ) インタプリタは複数の目的プログラムを結合する

**解き方**: (ア)(イ) はコンパイラとインタプリタの説明が逆、(エ) はリンカの説明です。答えは **(ウ)**。

## 試験対策のポイント

- **ITパスポート**: C・Java・Python・JavaScript・R などの言語の特徴と用途、HTML・XML・JSON の違い（HTML は決められたタグ、XML は独自タグ、JSON はデータ交換用の表記）が問われます。
- **基本情報技術者**: コンパイラ・インタプリタ・リンカ・ローダ・クロスコンパイラなどの役割を区別する問題が頻出です。「どの段階で何が作られるか」を流れで覚えます。
- **応用情報技術者**: コンパイラの処理段階（字句解析・構文解析・意味解析・最適化）の内容や、言語の分類・実行方式の比較まで踏み込んで問われます。
