記憶装置には「速いものほど高価で容量が小さい」という性質があります。そこで、速度・容量・価格の異なる記憶装置を階層的に組み合わせ、
全体として「速くて大容量」に近づける構成を **記憶階層** といいます。CPU と主記憶の速度差を埋める **キャッシュメモリ** はその代表例です。

## 前提となる用語

- **主記憶（メモリ）と補助記憶（ストレージ）**: PC のカタログの「メモリ 16GB」は主記憶（DRAM）の容量、「SSD 512GB」は補助記憶の容量です。主記憶の内容は電源を切ると消えます。
- **ページキャッシュ（ディスクキャッシュ）**: OS が、補助記憶から読んだデータを主記憶の空いている領域に置いておき、次に同じデータを読むときに速く返す仕組みです。主記憶が補助記憶のキャッシュとして働く、記憶階層の考え方そのものです。
- **スワップ**: 主記憶が足りないときに、しばらく使われていないページを補助記憶上の領域（スワップ領域。Windows ではページングファイル）に書き出して空きを作ることです。仮想記憶のページアウトにあたります（[OS とプロセス管理](../os/)）。

## 仕組み

### 記憶階層

| 階層 | 主な素子・装置 | 速度 | 容量 |
| --- | --- | --- | --- |
| レジスタ | CPU 内部の回路 | 最も速い | 最も小さい |
| キャッシュメモリ（1次・2次…） | SRAM | ↑ | ↓ |
| 主記憶 | DRAM | | |
| 補助記憶装置 | SSD、HDD など | 遅い | 大きい |

CPU に近いキャッシュから順に 1次キャッシュ（L1）、2次キャッシュ（L2）… と呼びます。

ピラミッドの形で表すと、上ほど高速・小容量・高価で、下ほど低速・大容量・安価になります。

### 半導体メモリの種類

| 種類 | 特徴 | 主な用途 |
| --- | --- | --- |
| DRAM | コンデンサに電荷を蓄えて記憶。**リフレッシュ（再書込み）が必要**。集積度が高く安価 | 主記憶 |
| SRAM | フリップフロップ回路で記憶。リフレッシュ不要で高速だが高価 | キャッシュメモリ |
| ROM / フラッシュメモリ | 電源を切っても内容が消えない（不揮発性） | ファームウェア、SSD、USB メモリ |

DRAM・SRAM は電源を切ると内容が消える **揮発性** メモリです。

### 参照の局所性

キャッシュが有効に働くのは、プログラムのアクセスに次の偏り（**局所性**）があるためです。

- **時間的局所性** … 一度アクセスしたデータは、近いうちに再びアクセスされやすい（ループ内の変数など）
- **空間的局所性** … アクセスしたデータの近くのアドレスも、続けてアクセスされやすい（配列の順次処理など）

### 実効アクセス時間

アクセスしたいデータがキャッシュにある割合を **ヒット率** といいます。

$$
\def\arraystretch{1.6}
\begin{array}{ll}
\text{実効アクセス時間} &{}= \text{キャッシュのアクセス時間} \times \text{ヒット率} \\
&\quad {}+ \text{主記憶のアクセス時間} \times (1 - \text{ヒット率})
\end{array}
$$

（$1 - \text{ヒット率}$）は **NFP（Not Found Probability）** やミス率と呼ばれます。

ヒット率やアクセス時間を変えて、実効アクセス時間がどう変わるかを確かめてみましょう（「例題1」「例題2」のボタンで下の例題の値になります）。

### 書込み方式

| 方式 | 動作 | 長所 | 短所 |
| --- | --- | --- | --- |
| ライトスルー方式 | キャッシュと **同時に主記憶にも** 書き込む | キャッシュと主記憶の内容が常に一致し、制御が単純 | 書込みのたびに主記憶へアクセスするため遅い |
| ライトバック方式 | **キャッシュだけに** 書き込み、そのデータがキャッシュから追い出されるときに主記憶へ書き戻す | 主記憶へのアクセス回数が減り高速 | 一時的に内容が一致しないため、制御が複雑 |

### 割付け方式（マッピング）

主記憶のブロックをキャッシュのどこに置くかの方式です。

| 方式 | 内容 |
| --- | --- |
| ダイレクトマッピング | 主記憶のブロックごとに、格納できるキャッシュの位置が 1 か所に決まっている |
| フルアソシエイティブ | キャッシュの任意の位置に格納できる |
| セットアソシエイティブ | キャッシュをいくつかのセットに分け、決まったセットの中の任意の位置に格納できる（上記 2 つの中間） |

### メモリインタリーブ

主記憶を複数の **バンク** に分け、連続するアドレスを異なるバンクに割り当てて並行してアクセスすることで、主記憶へのアクセスを高速化する方式です。

## 例題

**例題1** キャッシュのアクセス時間が 10 ナノ秒、主記憶のアクセス時間が 60 ナノ秒、ヒット率が 90% のとき、実効アクセス時間を求めなさい。

**解き方**

$$
10 \times 0.9 + 60 \times (1 - 0.9) = 9 + 6 = 15 \text{ ナノ秒}
$$

答え: **15 ナノ秒**

**例題2** キャッシュのアクセス時間 5 ナノ秒、主記憶のアクセス時間 50 ナノ秒の構成で、実効アクセス時間を 9.5 ナノ秒にしたい。必要なヒット率を求めなさい。

**解き方**: ヒット率を $h$ とすると

$$
\begin{aligned}
5h + 50(1 - h) &= 9.5 \\
50 - 45h &= 9.5 \\
45h &= 40.5 \\
h &= 0.9
\end{aligned}
$$

答え: **90%**

**例題3** ライトバック方式の説明として適切なものはどれか。
(ア) 書込み時にキャッシュと主記憶の両方を更新する (イ) 書込み時はキャッシュだけを更新し、ブロックの置換え時に主記憶に書き戻す

**解き方**: **(イ)**。(ア) はライトスルー方式です。

## 実際の進め方

### 自分の PC のメモリを確かめる

| OS | 見る場所 | 分かること |
| --- | --- | --- |
| Windows | タスクマネージャーの「パフォーマンス」タブ →「メモリ」 | 搭載量、使用中・利用可能な量、キャッシュ済みの量、速度、使用中のスロット数（増設の余地） |
| macOS | アクティビティモニタの「メモリ」タブ | メモリプレッシャー（主記憶の逼迫の度合いを色で表示）、使用済みスワップ |
| Linux | `free -h`、`vmstat 1` | 使用量・利用可能な量・キャッシュの量、スワップの発生状況 |

Linux での例です。出力は形式を示す例で、OS の版によって列や表示が異なります。

```
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       5.2Gi       1.1Gi       312Mi       8.7Gi       9.6Gi
Swap:          2.0Gi          0B       2.0Gi
```

`free`（まったく使われていない量）が 1.1G バイトしかなくても、慌てる必要はありません。OS は空いている主記憶をページキャッシュ（`buff/cache`）に使っており、必要になればすぐに手放します。
新しいプログラムが使える量の目安は `available`（9.6G バイト）のほうです。

```
$ vmstat 1 5     # 1 秒ごとに 5 回表示（形式を示す例。一部の列を抜粋）
procs -----------memory---------- ---swap--
 r  b   swpd    free    buff   cache   si   so
 1  0      0 1153280  204800 8912896    0    0
```

`si`・`so` は、1 秒あたりにスワップ領域から読み込んだ量・書き出した量です。ここが 0 でない状態が続くなら、主記憶が足りずにスワップが起きています。
`swpd`（スワップ領域の使用量）が 0 でなくても、`si`・`so` が 0 なら、以前に書き出したページがそのまま残っているだけで、今は困っていません。

### メモリが足りなくなると何が起きるか

1. OS はまず、ページキャッシュを減らして空きを作ります。ファイルの読込みが少し遅くなります。
2. それでも足りないと、しばらく使われていないページをスワップ領域に書き出します。そのページが再び使われるとページフォールトが起き、補助記憶から読み戻します。
3. 書出しと読戻しが頻発すると **スラッシング** になり、ディスクへのアクセスばかりで処理が進まなくなります。CPU 使用率のうち入出力待ち（`wa`）の割合が上がり、画面の操作にも反応しなくなります。
4. さらに足りないと、プログラムがメモリを確保できずにエラーで終了したり、OS がプロセスを強制的に終了させたりします（Linux の OOM Killer など）。

わずかなスワップでも大きく遅くなる理由は、実効アクセス時間の式で確かめられます。主記憶のアクセスを 100 ナノ秒、SSD 上のスワップ領域からの読込みを 100 マイクロ秒（＝ 100,000 ナノ秒）とします（どちらも桁の目安です）。
アクセスの 0.1% がスワップ領域へ行くだけで、

$$
\def\arraystretch{1.8}
\begin{array}{ll}
&100 \times 0.999 + 100{,}000 \times 0.001 \\
&{}= 99.9 + 100 = 199.9 \text{ ナノ秒}
\end{array}
$$

と約 2 倍になり、1% なら $100 \times 0.99 + 100{,}000 \times 0.01 = 99 + 1{,}000 = 1{,}099$ ナノ秒で約 11 倍です。キャッシュのミスと同じく、遅い階層へ行く割合が少し増えるだけで全体が大きく遅くなります。

### 選ぶとき・増設するときに確かめること

| 項目 | 確かめること |
| --- | --- |
| 容量 | OS と、同時に使うアプリケーションの使用量の合計に余裕を足した量。今の PC で、忙しい時間帯の使用量を測ってから決める |
| 規格 | DDR4・DDR5 などの世代が違うモジュールは挿せない。マザーボードが対応する規格と最大容量を確かめる |
| 増設できるか | ノート PC には、主記憶が基板に直付けで後から増設できない機種がある。その場合は購入時に容量を決める |
| 挿し方 | 同じ容量・規格のモジュールを対にして挿すと、2 つの経路で並行して転送する（デュアルチャネル）ことが多い。メモリインタリーブと同じく、並行してアクセスして速くする考え方 |
| ECC | サーバでは、ビットの誤りを検出・訂正できる ECC メモリを使うことが多い |

### 足りないときの対処の順序

1. **何が使っているかを確かめる**: タスクマネージャーの「プロセス」タブのメモリ列、Linux の `top` の `RES` 列などで、使用量の大きいプロセスを探します。
2. **不要なものを止める**: 使っていないアプリケーションやブラウザのタブを閉じます。時間とともに使用量が増え続けるプロセスは、使い終わったメモリを解放しない不具合（**メモリリーク**）の可能性があり、再起動は一時しのぎで、修正が必要です。
3. **設定で使用量を抑える**: DBMS のバッファの大きさや、同時に動かす処理の数を調整します。
4. **増設する（スケールアップ）**: 上の手順で足りなければ増設します。スワップ領域を増やすと強制終了は起きにくくなりますが、速くはなりません。

### よくある失敗と対策

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| `free`（空き）が少ないのを見てメモリ不足と判断する | キャッシュとして有効に使われているだけなのに、不要な増設をする | `available` とスワップの発生（`si`・`so`）を見て判断する |
| スワップ領域を増やして解決したつもりになる | 強制終了は減るが、遅いままになる | 使用量を減らすか、主記憶を増設する |
| 1 つのプログラムに主記憶のほとんどを割り当てる | OS や他のプロセスの分が足りず、スワップが起きて全体が遅くなる | OS と他のプロセスの分を残して割り当てる |
| 規格を確かめずにメモリを買う | 挿さらない、認識しない、最大容量を超えて使えない | マザーボード（PC）の仕様で規格・スロット数・最大容量を確かめる |
| メモリリークを再起動だけで済ませ続ける | 同じ症状が繰り返し、業務中に止まる | 使用量の推移を記録して原因のプログラムを特定し、修正する |

## 事例: あおば書店の DB サーバのメモリ

架空のオンライン書店「あおば書店」の DB サーバ（8 コア・メモリ 16G バイト。構成は [CPU の構成と性能](../cpu/) の事例を参照）で、データは 20G バイトに増えていました。
DBMS は、表やインデックスのページを主記憶に置いておく **バッファ**（バッファキャッシュ）を 8G バイト使う設定で、ページの読取りのうちバッファで済んだ割合（ヒット率）は 95% でした。数値は説明のための仮の値です。

**1. 設定変更で全体が遅くなった**: 夜間の集計が遅いため、担当者がバッファを 15G バイトに増やしました。ところが翌日は、集計だけでなく画面の表示まで遅くなりました。

**2. 切り分け**: `free -h` では `available` が 0.3G バイトしかなく、`vmstat 1` の `si`・`so` はずっと 0 になりませんでした。
主記憶 16G バイトのうち 15G バイトをバッファが取ったため、OS と、利用者の接続ごとに DBMS が使うメモリが足りなくなり、スワップが起きていたのです。
バッファの一部までスワップ領域に追い出され、「バッファにあるはずのページ」を読むのにもディスクへのアクセスが発生していました。

**3. 対処**: バッファを 11G バイトに戻し、OS などのために 5G バイトを残しました。スワップは止まりましたが、データ 20G バイトに対してバッファ 11G バイトでは、ヒット率は大きく改善しません。
そこで夜間に仮想マシンのメモリを 32G バイトに増やし（スケールアップ）、バッファを 24G バイトにしました。データ全体がバッファに収まり、ヒット率は 99% になりました。

**4. 効果の見積もり**: バッファからのページの読取りを 0.01 ミリ秒、ストレージからの読取りを 0.5 ミリ秒、ヒット率を $h$ とすると、1 ページあたりの平均の読取り時間は

$$
\def\arraystretch{1.8}
\begin{array}{ll}
h = 0.95 &{}= 0.01 \times 0.95 + 0.5 \times 0.05 \\
&{}= 0.0095 + 0.025 = 0.0345 \text{ ミリ秒} \\
h = 0.99 &{}= 0.01 \times 0.99 + 0.5 \times 0.01 \\
&{}= 0.0099 + 0.005 = 0.0149 \text{ ミリ秒}
\end{array}
$$

で、$0.0345 \div 0.0149 \fallingdotseq 2.3$ 倍速くなる見込みです。キャッシュメモリの実効アクセス時間とまったく同じ式で、主記憶と補助記憶の組合せも評価できます。

データは今後も増えるので、ヒット率と `available` を毎月記録し、バッファに収まらなくなる時期を見積もっています（[システム構成と性能評価](../system-configuration/) の事例）。

## 試験対策のポイント

- **ITパスポート**: 記憶階層の順序（速い順・容量の大きい順）、キャッシュメモリの目的、DRAM と SRAM、揮発性・不揮発性の違いが中心です。
- **基本情報技術者**: 実効アクセス時間の計算（逆にヒット率を求める問題も）が頻出です。ライトスルー / ライトバックの違い、DRAM のリフレッシュも定番です。
- **応用情報技術者**: 割付け方式、キャッシュを 2 段にした場合の実効アクセス時間、キャッシュミスを考慮した CPU 性能計算など、組み合わせた問題が出ます。
