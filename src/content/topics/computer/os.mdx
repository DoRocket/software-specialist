**OS（オペレーティングシステム）** は、ハードウェアを管理し、アプリケーションに使いやすい実行環境を提供する基本ソフトウェアです。
特に、限られた CPU を複数のプログラムで分け合う **タスク管理（プロセス管理）** と、限られた主記憶を有効に使う **記憶管理（仮想記憶）** が重要です。

## 前提となる用語

- **プログラムとプロセス**: プログラムはファイルとして保存された命令の並び、**プロセス** は実行中のプログラムです。OS は起動されたプログラムごとに主記憶や CPU 時間を割り当てて管理します。同じプログラムを 2 回起動すると、2 つのプロセスになります。試験の「タスク」は、ほぼ同じ意味で使われます。
- **スレッド**: 1 つのプロセスの中で並行して進む処理の流れです。同じプロセスのスレッドは主記憶を共有するので、プロセスを分けるより軽く切り替えられます。
- **PID（プロセス ID）**: OS がプロセスに付ける番号です。プロセスを指定して止めるときなどに使います。
- **カーネル**: OS の中核で、タスク管理・記憶管理などを行う部分です。

## 仕組み

### OS の主な機能

| 機能 | 内容 |
| --- | --- |
| タスク管理（プロセス管理） | プログラムの実行単位（タスク）を生成し、CPU の割当てを制御する |
| 記憶管理 | 主記憶の割当て・解放、仮想記憶の管理 |
| 入出力管理 | 周辺装置の制御（デバイスドライバを介して行う） |
| ファイル管理 | 補助記憶装置上のファイルやディレクトリの管理 |
| ユーザ管理・セキュリティ | 利用者の認証やアクセス権の管理 |

複数のタスクを切り替えながら並行して実行することを **マルチタスク** といいます。

### タスクの状態遷移

タスクは次の 3 つの状態を遷移します。

| 状態 | 意味 |
| --- | --- |
| 実行状態 | CPU が割り当てられて処理を行っている |
| 実行可能状態（レディ状態） | CPU が割り当てられるのを待っている（いつでも実行できる） |
| 待ち状態 | 入出力の完了など、何らかの事象の発生を待っている |

| 遷移 | きっかけ |
| --- | --- |
| 実行可能 → 実行 | **ディスパッチ**（CPU の割当て） |
| 実行 → 実行可能 | タイムクウォンタム（割当て時間）の終了、より優先度の高いタスクの出現（**プリエンプション**） |
| 実行 → 待ち | 入出力要求など、事象の発生を待つ必要が生じた |
| 待ち → 実行可能 | 入出力の完了など、待っていた事象が発生した |

**待ち状態から直接実行状態にはならない**（いったん実行可能状態に戻る）点に注意します。

### スケジューリング方式

| 方式 | 内容 |
| --- | --- |
| 到着順（FCFS） | 実行可能になった順に CPU を割り当てる |
| 処理時間順（SPT） | 処理時間の短いタスクから順に割り当てる。平均の待ち時間が短くなる |
| 優先度順 | 優先度の高いタスクから割り当てる。低いタスクがいつまでも実行されない場合がある |
| ラウンドロビン | 一定時間（タイムクウォンタム）ずつ順番に割り当て、時間が来たら実行可能状態の列の末尾に戻す |

実行中のタスクから OS が強制的に CPU を取り上げられる方式を **プリエンプティブ**、タスクが自ら CPU を手放すまで切り替えない方式を **ノンプリエンプティブ** といいます。

### 仮想記憶

補助記憶装置の一部を利用して、**実際の主記憶（実記憶）より大きなアドレス空間** をプログラムに提供する仕組みです。
**ページング方式** では、プログラムと主記憶を **ページ** という固定長の単位に分割して管理します。

- 必要なページが主記憶にないことを **ページフォールト** といい、補助記憶から主記憶へ読み込む（**ページイン**）
- 主記憶に空きがない場合は、追い出すページを選んで補助記憶へ書き出す（**ページアウト**）
- ページの入替えが頻発して処理効率が極端に落ちる状態を **スラッシング** という

ページ置換えアルゴリズム:

| 方式 | 追い出すページ |
| --- | --- |
| FIFO | 最も **早く主記憶に読み込まれた** ページ |
| LRU | 最も **長い間参照されていない** ページ |
| LFU | **参照回数が最も少ない** ページ |

## 例題

**例題1** 3 つのタスク A（処理時間 6）、B（2）、C（4）が時刻 0 に同時に到着した。到着順（A → B → C）と処理時間順で実行したとき、それぞれの平均ターンアラウンドタイム（到着から終了までの時間）を求めなさい。

**解き方**

- 到着順: A 終了 6、B 終了 8、C 終了 12 → $\dfrac{6 + 8 + 12}{3} = \dfrac{26}{3} \approx$ **8.7**
- 処理時間順（B → C → A）: B 終了 2、C 終了 6、A 終了 12 → $\dfrac{2 + 6 + 12}{3} = \dfrac{20}{3} \approx$ **6.7**

**例題2** ページ枠が 3 つの主記憶で、ページを 1, 2, 3, 1, 4, 2, 5 の順に参照する。最初はすべての枠が空とする。LRU 方式と FIFO 方式で、ページフォールトの回数をそれぞれ求めなさい。

**解き方（LRU）**

| 参照 | 枠の内容 | 結果 |
| --- | --- | --- |
| 1 | 1 | フォールト |
| 2 | 1, 2 | フォールト |
| 3 | 1, 2, 3 | フォールト |
| 1 | 1, 2, 3 | ヒット |
| 4 | 1, 3, 4（最も長く参照されていない 2 を追い出す） | フォールト |
| 2 | 1, 4, 2（3 を追い出す） | フォールト |
| 5 | 4, 2, 5（1 を追い出す） | フォールト |

LRU: **6 回**

**解き方（FIFO）**

| 参照 | 枠の内容 | 結果 |
| --- | --- | --- |
| 1, 2, 3 | 1, 2, 3 | フォールト 3 回 |
| 1 | 1, 2, 3 | ヒット |
| 4 | 2, 3, 4（最初に読み込んだ 1 を追い出す） | フォールト |
| 2 | 2, 3, 4 | ヒット |
| 5 | 3, 4, 5（2 を追い出す） | フォールト |

FIFO: **5 回**。参照の並び方によっては、LRU が FIFO より常に有利とは限りません。

## 実際の進め方

### プロセスを確かめる

| OS | 見る場所・コマンド | 分かること・できること |
| --- | --- | --- |
| Windows | タスクマネージャーの「プロセス」タブ・「詳細」タブ | アプリごとの CPU・メモリ・ディスクの使用量。「詳細」では PID、状態、優先度も見られ、右クリックで終了・優先度の変更ができる |
| Windows | `tasklist`、`taskkill`（コマンドプロンプト） | プロセスの一覧と、PID を指定した終了 |
| macOS | アクティビティモニタ | プロセスごとの使用量と PID。選んで「×」のボタンから終了・強制終了 |
| Linux・macOS | `ps`、`top`、`kill` | プロセスの一覧と状態、シグナル（OS からプロセスへの通知）による終了 |

Linux の `ps` の例です。出力は形式を示す例で、列の並びは OS や指定するオプションによって変わります。

```
$ ps aux --sort=-%cpu | head -4      # CPU 使用率の高い順に先頭の数行
USER       PID %CPU %MEM     VSZ     RSS TTY  STAT START   TIME COMMAND
app       3157 97.3 12.1 1612344 1013320 ?    R    13:02   3:40 python3 export.py
app       1022 35.8 41.1 4123456 3450880 ?    S    Jun01 812:10 app-server
root         1  0.0  0.2  168000   12800 ?    Ss   Jun01   0:21 /sbin/init
```

| 列 | 意味 | 本文とのつながり |
| --- | --- | --- |
| `PID` | プロセス ID | 止めるときに指定する |
| `%CPU`・`%MEM` | CPU の使用率、主記憶に占める割合 | 資源を多く使っているプロセスを探す |
| `VSZ` | 仮想記憶上の大きさ（K バイト） | プログラムに見せているアドレス空間の大きさ |
| `RSS` | 実際に主記憶上にある大きさ（K バイト） | 仮想記憶では、使っているページだけが主記憶に載るので、`RSS` は `VSZ` より小さい |
| `STAT` | 状態。`R` は実行中または実行可能、`S` は事象の発生を待っている、`D` は主に入出力の完了を待っていて中断できない、`Z` は終了したが親プロセスの後始末を待っている（ゾンビ） | 3 つの状態との対応は、`R` が実行状態と実行可能状態（Linux はこの 2 つを区別しない）、`S`・`D` が待ち状態 |

### プロセスを止める手順

1. **何のプロセスかを確かめる**: コマンド名・利用者・起動時刻を見て、止めてよいものか判断します。サーバで動くサービスなら、止めると業務が止まります。
2. **まず通常の終了を求める**: アプリケーションの終了の操作をするか、`kill PID` を実行します。`kill` は何も指定しないと SIGTERM というシグナルを送り、プロセスに「後始末をして終わる」ことを求めます。
3. **しばらく待って、終わったかを確かめる**: `ps -p PID` で残っていないかを見ます。
4. **応答がなければ強制終了する**: `kill -9 PID`（SIGKILL）や、タスクマネージャーの「タスクの終了」で強制的に終わらせます。保存していないデータは失われ、一時ファイルが残ることがあります。
5. **資源が解放されたかを確かめ、原因を記録する**: CPU 使用率や主記憶の空きが戻ったか、なぜ暴走したかを残し、再発防止につなげます。

```
$ kill 3157              # 終了を求める（SIGTERM）
$ ps -p 3157             # まだ残っているかを確かめる
$ kill -9 3157           # 応答しないときだけ強制終了する（SIGKILL）
$ renice -n 10 -p 3157   # 止めずに優先度を下げる（値が大きいほど優先度が低い）
```

```
> tasklist /FI "IMAGENAME eq notepad.exe"     # Windows: 名前でプロセスを探す
> taskkill /PID 1234                          # 終了を求める
> taskkill /PID 1234 /F                       # 強制終了する
```

止めずに **優先度を下げる** 方法もあります（Linux の `nice`・`renice`、タスクマネージャーの「優先度の設定」）。優先度順のスケジューリングで、ほかのプロセスに CPU が先に割り当てられるようになります。
サーバのサービスは、`systemctl stop サービス名` のように、サービスを管理する仕組みを通して止めます。`kill` で直接止めると、設定によっては自動で再起動されることがあります。

### よくある失敗と対策

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| いきなり強制終了する | 保存前のデータが失われ、ファイルが壊れることがある | まず通常の終了を求め、応答がないときだけ強制終了する |
| PID を取り違える | 業務に必要な別のプロセスを止めてしまう | 実行する直前に `ps` でコマンド名と PID を確かめる |
| サービスを `kill` で止める | 自動で再起動される、関連するサービスが異常になる | サービス管理の仕組み（`systemctl` など）で止める |
| CPU 使用率が高いだけで止める | バックアップなど、必要な処理を中断してしまう | 何の処理か、いつ終わる予定かを確かめる。急がないなら優先度を下げる |
| 止めて終わりにする | 同じ原因で何度も起きる | 原因を調べ、実行する時間帯やプログラムを直す |

## 事例: あおば書店の Web サーバが昼に遅くなった

架空のオンライン書店「あおば書店」の Web サーバ（4 コア・メモリ 8G バイト。構成は [CPU の構成と性能](../cpu/) の事例を参照）で、ある平日の 13 時過ぎから表示が遅くなりました。数値は説明のための仮の値です。

**1. 状況を見る**: `top` では、CPU 使用率のうち `us` は 30% 程度でしたが、入出力待ちの `wa` が 45% と高く、`free -h` の `available` は 0.2G バイトしかありませんでした。
`vmstat 1` の `si`・`so` も 0 にならず、主記憶が足りずにスワップが起きていると分かりました（[記憶階層とキャッシュメモリ](../memory/)）。

**2. プロセスを特定する**: `ps aux --sort=-%mem` で主記憶の使用量が多い順に見ると、ふだんは無い `python3 report.py`（PID 2481）が 4.6G バイトを使っていました。
アプリケーションのプロセス（`app-server`）はスワップからの読戻しを待つ `D` の状態になることが多く、応答が遅れていました。主記憶の使用量を、OS など（0.8G バイト）、`app-server`（3.0G バイト）、`report.py`（4.6G バイト）と足し合わせると、

$$
0.8 + 3.0 + 4.6 = 8.4 \text{ G バイト} \gt 8 \text{ G バイト}
$$

で、搭載量を超えていました。

**3. 止めてよいかを確かめる**: `report.py` は、営業担当が月次の売上集計のために手作業で起動したもので、全注文を一度に主記憶へ読み込んで集計する作りでした。
データを読むだけで更新はしないこと、夜にやり直せることを担当者に確認しました。

**4. 止める**: `kill 2481` で終了を求めると数秒で終わり、`available` は 4G バイト台に戻り、`si`・`so` も 0 になって、表示の遅れは解消しました。強制終了（`kill -9`）は不要でした。

**5. 再発を防ぐ**: 集計は夜間に、Web サーバではなく集計用に用意したサーバで実行することにしました。あわせて、注文を少しずつ読み込んで集計するようにプログラムを直し、スワップが発生したら通知する監視を加えました。

## 試験対策のポイント

- **ITパスポート**: OS の役割（基本ソフトウェアとしての機能）、マルチタスク、仮想記憶の目的といった用語レベルの理解が中心です。
- **基本情報技術者**: タスクの状態遷移（特に「待ち → 実行」はない）、スケジューリング方式の特徴、ページ置換えのトレース（FIFO・LRU）が頻出です。
- **応用情報技術者**: ラウンドロビンなどでのタスクの実行順序や終了時刻の計算、スラッシングの原因、ページサイズや置換え方式の比較などが問われます。
