ソフトウェアは、ハードウェアを直接管理する **OS**、多くのアプリケーションに共通する機能を提供する **ミドルウェア**、業務などの目的を実現する **アプリケーションソフトウェア** の階層で構成されます。
ここでは OS の上で働く仕組みとして、ミドルウェアと API、ファイルを整理するファイルシステム、データを守るバックアップ、そして OSS（オープンソースソフトウェア）の扱い方を学びます。

## 前提となる用語

- **リストア**: バックアップから、データを元の場所（または別の場所）に戻すことです。
- **媒体**: データを保存する物です。HDD・SSD・磁気テープ・光ディスクのほか、クラウドのストレージサービスも保存先の 1 つとして扱います。
- **RPO・RTO**: 障害が起きたとき「どの時点のデータまで戻せればよいか」（RPO：目標復旧時点）と「どれだけの時間で戻すか」（RTO：目標復旧時間）です。バックアップの頻度や方式を決める基準になります（[事業継続](../../management/service-management/continuity/)）。
- **同期**: 2 か所のデータを常に同じ内容に保つことです。削除や上書きもすぐに相手に伝わるので、それだけではバックアップの代わりになりません。

## 仕組み

### ミドルウェア

**ミドルウェア** は、OS とアプリケーションの中間に位置し、さまざまなアプリケーションで共通に使われる機能を提供するソフトウェアです。
アプリケーションごとに同じ機能を作る必要がなくなり、開発の効率と品質が上がります。

| 種類 | 役割 |
| --- | --- |
| DBMS | データベースの定義・操作・同時実行制御・障害回復を行う |
| TP モニター | 大量のトランザクション処理を効率よく制御する |
| Web サーバ / アプリケーションサーバ | HTTP 要求を受け付け、業務処理を実行する環境を提供する |
| 通信管理システム | ネットワークを介したデータの送受信を管理する |
| 運用管理ツール | システムの稼働状況の監視やジョブの自動実行を行う |

**API**（Application Programming Interface）は、アプリケーションから OS やミドルウェア、他のソフトウェアの機能を呼び出すための **取決め（呼出し方の仕様）** です。
ネットワーク経由で HTTP などを使って呼び出せるようにしたものを **Web API** といい、外部サービスの機能を自社のシステムに組み込むときに使われます。
また、利用者が入力したコマンドを解釈して OS（カーネル）の機能を呼び出すプログラムを **シェル**（コマンドインタプリタ）といいます。

### ディレクトリとパス

ファイルは、**ディレクトリ**（フォルダ）を使って木構造（階層構造）で管理されます。

| 用語 | 意味 |
| --- | --- |
| ルートディレクトリ | 階層の最上位のディレクトリ（UNIX 系では `/`） |
| カレントディレクトリ | 現在作業の基準になっているディレクトリ |
| `.` / `..` | カレントディレクトリ自身 / 1 つ上（親）のディレクトリ |
| 絶対パス | **ルートディレクトリから** 目的のファイルまでの道筋 |
| 相対パス | **カレントディレクトリから** 目的のファイルまでの道筋 |

```
/
├── home
│   ├── alice
│   │   ├── docs
│   │   │   └── report.txt
│   │   └── photo.jpg
│   └── bob
└── etc
```

ほかに、別の場所にあるファイルを参照するための **シンボリックリンク**（Windows のショートカットに相当）があります。
ディスク領域をファイルとして使えるように管理する方式をファイルシステムといい、Windows の **NTFS**、USB メモリなどで使われる **FAT** のように OS や用途ごとに種類があります。

### バックアップ方式

障害や誤操作に備えて、データの複製を別の媒体に保存しておくことを **バックアップ** といいます。

| 方式 | 取得する範囲 | バックアップの時間・量 | 復元に必要なもの |
| --- | --- | --- | --- |
| フルバックアップ | すべてのデータ | 最も多い | 最新のフルバックアップだけ |
| 差分バックアップ | **直前のフルバックアップ以降** に変更されたデータ | 日を追うごとに増える | フル + **最新の差分** |
| 増分バックアップ | **直前のバックアップ（フル・増分を問わない）以降** に変更されたデータ | 最も少ない | フル + **それ以降のすべての増分** |

差分は「取得に時間がかかるが復元が速い」、増分は「取得は速いが復元に手間がかかる」というトレードオフの関係です。
複数世代のバックアップを残しておく **世代管理** を行うと、ある時点で壊れたデータに気づかずバックアップしてしまっても、さらに前の世代から戻せます。
ランサムウェア対策として、ネットワークから切り離した場所にも保管しておくことが重要です。

### OSS（オープンソースソフトウェア）

**OSS** は、ソースコードが公開され、利用・改変・再配布が認められているソフトウェアです。主な特徴は次のとおりです。

- ソースコードが公開されている
- 再配布を制限しない（有償で販売することも禁止されていない）
- 改変した派生ソフトウェアの作成・配布を認める
- 原則として **無保証**（不具合による損害は作者が責任を負わない）

OSS は自由に使えますが「著作権を放棄したソフトウェア」ではなく、**ライセンス（利用許諾条件）を守る義務** があります。

| ライセンス | 特徴 |
| --- | --- |
| GPL | **コピーレフト** 型。GPL のソフトウェアを改変・組み込んで配布する場合は、派生物も GPL で公開しなければならない |
| BSD ライセンス / MIT ライセンス | 著作権表示などを残せば、派生物のソースコードを公開しなくてもよい（商用製品への組込みがしやすい） |
| Apache ライセンス | 著作権表示などを条件に改変・再配布を認める。特許の利用許諾についても定めている |
| MPL | 改変したファイル単位でソースコードの公開を求める（GPL より範囲が限定的） |

代表的な OSS には、OS の **Linux**、Web サーバの **Apache HTTP Server**、DBMS の **MySQL**・**PostgreSQL** などがあり、これらを組み合わせた Web システムの構成を **LAMP** / **LAPP** と呼びます。

## 例題

**例題1** 上の図で、カレントディレクトリが `/home/alice/docs` のとき、`photo.jpg` と `bob` ディレクトリを相対パスで表しなさい。また、`photo.jpg` の絶対パスを答えなさい。

**解き方**

- `photo.jpg` は 1 つ上の `alice` にあるので、相対パスは **`../photo.jpg`**
- `bob` は 2 つ上の `home` の下にあるので、相対パスは **`../../bob`**
- 絶対パスはルートからたどって **`/home/alice/photo.jpg`**

**例題2** 毎週日曜日にフルバックアップを取得し、月曜日から土曜日は毎日の業務終了後にバックアップを取得している。木曜日の業務中にディスクが故障した。水曜日の終了時点までのデータを復元するのに必要なバックアップを、平日のバックアップが (1) 差分の場合と (2) 増分の場合について答えなさい。

**解き方**

1. 差分: 水曜日の差分には日曜日以降の変更がすべて含まれるので、**日曜日のフル + 水曜日の差分**
2. 増分: 各日の増分にはその日の変更しか含まれないので、**日曜日のフル + 月・火・水曜日の増分**（この順に適用する）

## 実際の進め方

### パスを確かめる

コマンドで操作するときは、まずカレントディレクトリを確かめてから相対パスを使うと、意図しない場所のファイルを消すといった事故を防げます。出力は例です。

```
$ pwd                    # Linux・macOS: カレントディレクトリを表示
/home/alice/docs
$ ls ../                 # 相対パスで 1 つ上（/home/alice）の中身を表示
docs  photo.jpg
$ cd /etc                # 絶対パスで移動
```

```
> cd                     # Windows のコマンドプロンプト: カレントディレクトリを表示
C:\Users\alice\Documents
> dir ..\Pictures        # 相対パスで別のフォルダの中身を表示
```

Windows では区切りに `\` を使い、`C:` のようなドライブ名から始まるのが絶対パスです。
ネットワーク上の共有フォルダは `\\192.168.20.10\共有名` のように、コンピュータ名（またはアドレス）から始まる形（UNC パス）で表します。

### バックアップを設計する手順

1. **守る対象と量を決める**: どのデータ（共有フォルダ、データベース、設定）か、全体と 1 日あたりの変更がどれくらいか。
2. **RPO・RTO を決める**: 失ってもよいデータの範囲と、戻すまでに許される時間から、取得の頻度と方式を決めます。
3. **方式と頻度を決める**: 例えば週 1 回のフルバックアップと、毎日の差分（または増分）を組み合わせます。
4. **保存先を「3-2-1 ルール」で決める**: よく使われる目安で、
   - **3**: データを 3 つ持つ（元のデータ＋バックアップ 2 つ）
   - **2**: 2 種類以上の媒体に保存する
   - **1**: 1 つは離れた場所（別の建物やクラウド）に置く

   ランサムウェアに備えて、さらにそのうち 1 つをネットワークから切り離す（オフライン）か、書き換えられない設定にしておくことが勧められます。
5. **世代数と保存期間を決める**: 壊れたデータに気づかずにバックアップしてしまっても、前の世代から戻せるようにします。
6. **自動化し、失敗を通知させる**: 手作業は忘れます。失敗したことに気づけない仕組みでは、必要なときに古いバックアップしか残っていません。
7. **リストアの手順書を作り、訓練する**: 下の手順で、実際に戻せることと、かかる時間を確かめます。

| 項目 | 決めること（記入例） |
| --- | --- |
| 対象・量 | 共有フォルダ全体。全体 ○T バイト、1 日の変更 ○G バイト |
| RPO / RTO | 前日の業務終了時点まで / 1 営業日以内 |
| 方式・頻度 | 毎週フル + 毎日増分 |
| 保存先 | 外付け HDD（2 台を交互に使い、1 台は社外に保管）、クラウド |
| 世代・期間 | 日次 14 世代、週次 8 世代 |
| 監視 | 失敗したら担当者にメールで通知 |
| 訓練 | 四半期に 1 回、手順書に沿ってリストアし、時間を記録 |

### リストア訓練の進め方

1. **場面を決める**: 「ファイルを 1 つ誤って消した」「NAS 全体が壊れた」など、起こりうる場面ごとに行います。
2. **本番を上書きしない場所に戻す**: 訓練で本番のデータを壊さないよう、別のフォルダや予備の装置に戻します。
3. **中身を確かめる**: ファイルが開けるか、件数や容量が元と合うかを確かめます。
4. **かかった時間を測り、RTO と比べる**: 全体を戻すのに何時間かかるかは、実際にやってみないと分かりません。
5. **手順書を直す**: つまずいた点を反映します。構成を変えたときも、訓練をやり直します。

### OSS を使うときに確かめること

- 使っている OSS の名前・バージョン・ライセンスを一覧にしておきます（ソフトウェアの部品表、**SBOM** と呼ばれます）。
- 自社の製品に組み込んで配布するなら、GPL のようなコピーレフト型のライセンスかどうかで、ソースコードの公開義務が変わります。
- 脆弱性の情報を確認し、必要に応じて更新します。OSS は原則として無保証なので、利用者が自分で管理します。

### よくある失敗と対策

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| 同じ NAS の別のフォルダにバックアップする | NAS が壊れると、元データとバックアップを同時に失う | 別の装置・媒体に保存する |
| RAID だからバックアップは不要と考える | 誤削除・ランサムウェア・RAID 自体の故障では戻せない | RAID は「止まらない」ため、バックアップは「戻す」ためと区別する（[システムの信頼性](../reliability/)） |
| 同期サービスをバックアップの代わりにする | 削除や暗号化された状態も同期されてしまう | 世代を持つバックアップを別に取る |
| バックアップ用の外付けディスクをつなぎっぱなしにする | ランサムウェアに元データと一緒に暗号化される | 取得のときだけつなぐ、書き換えられない保存先を使う |
| バックアップの失敗に気づかない | いざというときに、何か月も前のものしか残っていない | 失敗の通知と、定期的な結果の確認 |
| 一度もリストアしたことがない | 手順が分からない、戻せない、時間が RTO を超える | 定期的にリストア訓練をする |
| 対象のフォルダを 1 つずつ指定する | 後から作ったフォルダが対象から漏れる | 上位のフォルダを指定し、必要なら除外を指定する |

## 事例: みなと事務所の NAS のバックアップ

[みなと事務所](../../network/)（社員 30 名）の NAS（192.168.20.10）には共有フォルダが約 3T バイトあり、1 日の変更は 20G バイト前後です。NAS はディスク 4 台の RAID で動いています。
これまでのバックアップは「つなぎっぱなしの外付け HDD 1 台に、週 1 回のフルバックアップ」だけで、3-2-1 ルールに照らすと、離れた場所の複製がなく、ランサムウェアにも弱い状態でした。速度は説明のための仮の値です。

**1. 目標を決める**: RPO は前日の業務終了時点まで（最大 1 日分のデータの損失を許す）、RTO は 1 営業日以内としました。

**2. 保存先と頻度を決める**

| コピー | 媒体・場所 | 取得の頻度 |
| --- | --- | --- |
| 1. 元データ | NAS（事務所内） | — |
| 2. 外付け HDD | HDD 2 台を交互に使う。取得後は取り外し、使っていない 1 台は社外に保管 | 毎週金曜日の夜にフル |
| 3. クラウド | クラウドのバックアップサービス（社外） | 毎晩、前日からの変更分（増分） |

コピーは 3 つ、媒体は事務所のディスク（NAS・外付け HDD）とクラウドの 2 種類以上、社外にはクラウドと保管中の HDD の 2 つがあり、HDD は取り外すのでオフラインの複製にもなります。

**3. 時間を見積もる**: 外付け HDD へのフルバックアップは、HDD の書込みの速さ（実効 150M バイト/秒）で決まるとすると、

$$
\dfrac{3 \times 10^{12} \text{ バイト}}{150 \times 10^6 \text{ バイト/秒}} = 20{,}000 \text{ 秒} \fallingdotseq 5.6 \text{ 時間}
$$

で、金曜日の夜のうちに終わります。クラウドへの毎晩の増分は、[ネットワークの性能](../../network/performance/) の事例で見積もったとおり約 13 分です。
ただし、クラウドへの最初のフルバックアップは、上り 200M ビット/秒では

$$
\dfrac{3 \times 10^{12} \times 8 \text{ ビット}}{200 \times 10^6 \text{ ビット/秒}} = 120{,}000 \text{ 秒} \fallingdotseq 33 \text{ 時間}
$$

かかるので、金曜日の夜から週末にかけて実行しました。同じ理由で、NAS 全体をクラウドから戻すのにも長い時間がかかるため、「全体は HDD から戻し、金曜日以降に変更されたファイルだけをクラウドから戻す」という手順にしました。

**4. リストア訓練で見つかったこと**: 最初の訓練で、共有フォルダの 1 つ（2GB）をクラウドから予備のフォルダに戻すと、10 分ほどで戻りファイルも開けました。
一方、外付け HDD のバックアップを確かめると、4 月に作った共有フォルダ「制作2026」が入っていませんでした。バックアップの対象を共有フォルダごとに 1 つずつ指定していたためで、上位のフォルダを対象にするよう設定を直しました。
戻してみて初めて分かる漏れを見つけるのが、訓練の目的です。この NAS で実際に起きた障害と、このバックアップからの復旧は [システムの信頼性](../reliability/) の事例で扱います。

## 試験対策のポイント

- **ITパスポート**: 絶対パス・相対パスの指定、バックアップの必要性と世代管理、OSS の特徴（ソース公開、再配布の自由、無保証）と GPL・コピーレフトの意味が中心です。API・Web API の役割もプログラミングの範囲で問われます。
- **基本情報技術者**: ミドルウェアの役割、相対パスのトレース、差分・増分バックアップの取得量と復元手順の比較が頻出です。OSS ライセンスの違い（GPL とそれ以外）も押さえます。
- **応用情報技術者**: バックアップ方式の選択（取得時間・復元時間・媒体の本数）、OSS を製品に組み込む際のライセンス上の留意点、仮想化・クラウド関連の OSS（Docker・Kubernetes など）の特徴が問われます。
