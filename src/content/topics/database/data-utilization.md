業務システムに蓄積されたデータは、日々の処理に使うだけでなく、分析して意思決定に役立てることができます。
ここでは、分析用にデータを集める **データウェアハウス**、データから知識を掘り出す **データマイニング**、多様で大量なデータを扱う **ビッグデータ** と、それを支える **NoSQL** を整理します。

## 業務処理と分析処理

| 項目 | OLTP（オンライントランザクション処理） | OLAP（オンライン分析処理） |
| --- | --- | --- |
| 目的 | 受注・入金など日々の業務処理 | 売上傾向の分析など意思決定の支援 |
| 処理の特徴 | 少量のデータを高頻度に更新 | 大量のデータを集計・検索（更新はまれ） |
| 主な DB | 業務系の RDB | データウェアハウス |

## データウェアハウス

**データウェアハウス（DWH）** は、複数の業務システムからデータを集めて統合し、時系列で蓄積した分析専用のデータベースです。
「テーマ（顧客、商品など）ごとに整理される」「統合されている」「時系列で保持される」「原則として更新・削除しない」という性質があります。

- **データマート**: DWH から部門や目的ごとに必要なデータだけを切り出した小規模なデータベース。
- **ETL**: 業務システムからデータを **抽出（Extract）**、形式をそろえて **変換（Transform）**、DWH へ **書き出し（Load）** する処理。先に書き出してから DWH 側で変換する方式を **ELT** と呼びます。
- **データクレンジング**: 表記ゆれ（「(株)」と「株式会社」）、重複、欠損などを修正してデータの品質を高める作業。同一人物の重複データを1件にまとめる **名寄せ** もその一つです。

### OLAP の操作

DWH のデータは「期間 × 地域 × 商品」のような **多次元** の立方体（キューブ）として分析されます。

| 操作 | 内容 |
| --- | --- |
| ドリルダウン | 集計の粒度を細かくする（年 → 月 → 日） |
| ドリルアップ（ロールアップ） | 集計の粒度を粗くする（店舗 → 地域） |
| スライス | ある次元を1つの値に固定して断面を見る（2024年だけ） |
| ダイス | 分析する次元の組合せや軸を入れ替える |

## データマイニング

大量のデータから、統計や機械学習の手法を使って **人が気づいていない規則性や関係** を発見することです。

| 手法 | 内容 | 例 |
| --- | --- | --- |
| アソシエーション分析 | 同時に起こりやすい事象の組合せを見つける（バスケット分析） | 「おむつを買う人はビールも買う」 |
| クラスタ分析 | 似た性質のデータをグループに分ける | 顧客の購買傾向による分類 |
| 決定木 | 条件分岐を木構造にして分類・予測する | 解約しそうな顧客の判定 |
| テキストマイニング | 文章データから頻出語や傾向を抽出する | 問合せ内容や SNS 投稿の分析 |

### 例題: アソシエーション分析の指標

**問** 全取引 1,000 件のうち、パンを含む取引が 200 件、牛乳を含む取引が 250 件、両方を含む取引が 100 件あった。「パン → 牛乳」の支持度・確信度・リフト値を求めよ。

**解き方**

- **支持度**（両方を含む取引の割合）$= 100 \div 1{,}000 =$ **10%**
- **確信度**（パンを買った取引のうち牛乳も買った割合）$= 100 \div 200 =$ **50%**
- **リフト値** $= \text{確信度} \div \text{牛乳を含む取引の割合} = 50\% \div (250 \div 1{,}000) = 50\% \div 25\% =$ **2.0**

リフト値が 1 より大きければ、パンを買うことが牛乳の購入を後押ししている（関連がある）と判断します。1 なら無関係です。

## ビッグデータとデータレイク

**ビッグデータ** は、従来のデータベースでは扱いきれない大量・多様なデータです。特徴は **3V**（Volume: 量、Variety: 多様性、Velocity: 発生・更新の速度）で表され、Veracity（正確性）と Value（価値）を加えて 5V とすることもあります。

| 分類 | 内容 | 例 |
| --- | --- | --- |
| 構造化データ | 列の定義が決まっている | RDB の表、CSV |
| 半構造化データ | タグなどで構造を表すが、形式が固定されない | JSON、XML |
| 非構造化データ | 決まった構造をもたない | 文書、画像、音声、動画 |

**データレイク** は、構造化・非構造化を問わずデータを **加工せず元の形式のまま** 大量に蓄える保管場所です。
DWH が「格納時に形式をそろえる」のに対し、データレイクは「使うときに目的に応じて解釈・加工する」点が異なります。
部門ごとにデータがばらばらに管理され連携できない状態（**データのサイロ化**）を解消する手段にもなります。

## NoSQL

**NoSQL**（Not only SQL）は、関係モデル以外の方式でデータを管理するデータベースの総称です。

| 種類 | データの持ち方 | 向いている用途 | 製品例 |
| --- | --- | --- | --- |
| キーバリュー型（KVS） | キーと値の組 | セッション情報、キャッシュ | Redis |
| ドキュメント指向型 | JSON などの文書単位。項目は文書ごとに異なってよい | 項目が変わりやすいデータ、Web サービス | MongoDB、CouchDB |
| ワイドカラム型（列指向型） | 行ごとに異なる列を持てる | 大量の書込み、時系列データ | Apache Cassandra |
| グラフ指向型 | ノード（点）とエッジ（関係） | SNS の人間関係、経路探索、推薦 | Neo4j |

| 観点 | RDB | NoSQL（一般的な傾向） |
| --- | --- | --- |
| スキーマ | 事前に厳密に定義 | 柔軟（スキーマレスなものも多い） |
| 整合性 | ACID 特性による強い整合性 | BASE 特性（結果整合性）を採るものが多い |
| 拡張方法 | スケールアップ（サーバの高性能化）が中心 | **スケールアウト**（サーバの台数を増やす）が容易 |
| 複雑な検索・結合 | 得意（SQL） | 不得意なものが多い |

### CAP 定理と BASE 特性

分散データベースでは、**一貫性**（Consistency）・**可用性**（Availability）・**分断耐性**（Partition tolerance）の3つを同時に完全には満たせないとする **CAP 定理** が知られています。
ネットワーク分断が避けられない大規模分散環境では、一貫性を一時的に緩めて可用性を優先する設計がよく採られ、その考え方を **BASE 特性** と呼びます。

| 要素 | 意味 |
| --- | --- |
| Basically Available | 一部に障害があっても、基本的にはサービスを提供し続ける |
| Soft state | データの状態は、外部からの入力がなくても同期の進行によって変化しうる |
| Eventually consistent | 更新直後は複製間で値が食い違っても、**最終的には一致する**（結果整合性） |

データを複数のサーバにキーなどで分割して配置する **シャーディング** は、負荷と容量を水平に分散する代表的な手法です。
大量データの分散処理には Apache Hadoop（分散ファイルシステム HDFS など）や Apache Spark といったフレームワークが使われます。

## 試験対策のポイント

- **ITパスポート**: データウェアハウス・データマイニング・ビッグデータ・テキストマイニングの意味を区別できることが中心です。NoSQL ではキーバリュー型・ドキュメント指向型・グラフ指向型の特徴を答えられるようにします。
- **基本情報**: OLTP と OLAP、DWH とデータマート、ETL とデータクレンジングの役割が問われます。アソシエーション分析の支持度・確信度・リフト値の計算や、データレイクの特徴も押さえます。
- **応用情報**: RDB と NoSQL の比較、CAP 定理・BASE 特性・結果整合性、シャーディングによるスケールアウトなど、要件に応じたデータベース方式の選択が問われます。BASE は ACID との対比で説明できるようにしておきます。
