業務システムに蓄積されたデータは、日々の処理に使うだけでなく、分析して意思決定に役立てることができます。
ここでは、分析用にデータを集める **データウェアハウス**、データから知識を掘り出す **データマイニング**、多様で大量なデータを扱う **ビッグデータ** と、それを支える **NoSQL** を整理します。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| 業務システム（基幹系） | 受注・在庫・会計など、日々の業務の取引を記録し処理するシステム |
| 集計 | 合計・件数・平均などを、分類ごとにまとめて求めること（SQL の `GROUP BY` と集約関数で行う） |
| 指標（KPI） | 目標の達成度を測る数値。分析では、何を指標にし、どう計算するか（定義）を最初に決める |
| 相関と因果 | 相関は「一方が大きいと他方も大きい」などの関係があること。因果は一方が原因で他方が起きること。相関があっても因果があるとは限らない |
| 個人情報 | 生存する個人を識別できる情報。取得時に示した利用目的の範囲で扱う必要がある |

## 業務処理と分析処理

| 項目 | OLTP（オンライントランザクション処理） | OLAP（オンライン分析処理） |
| --- | --- | --- |
| 目的 | 受注・入金など日々の業務処理 | 売上傾向の分析など意思決定の支援 |
| 処理の特徴 | 少量のデータを高頻度に更新 | 大量のデータを集計・検索（更新はまれ） |
| 主な DB | 業務系の RDB | データウェアハウス |

## データウェアハウス

**データウェアハウス（DWH）** は、複数の業務システムからデータを集めて統合し、時系列で蓄積した分析専用のデータベースです。
「テーマ（顧客、商品など）ごとに整理される」「統合されている」「時系列で保持される」「原則として更新・削除しない」という性質があります。

- **データマート**: DWH から部門や目的ごとに必要なデータだけを切り出した小規模なデータベース。
- **ETL**: 業務システムからデータを **抽出（Extract）**、形式をそろえて **変換（Transform）**、DWH へ **書き出し（Load）** する処理。先に書き出してから DWH 側で変換する方式を **ELT** と呼びます。
- **データクレンジング**: 表記ゆれ（「(株)」と「株式会社」）、重複、欠損などを修正してデータの品質を高める作業。同一人物の重複データを1件にまとめる **名寄せ** もその一つです。

### OLAP の操作

DWH のデータは「期間 × 地域 × 商品」のような **多次元** の立方体（キューブ）として分析されます。

| 操作 | 内容 |
| --- | --- |
| ドリルダウン | 集計の粒度を細かくする（年 → 月 → 日） |
| ドリルアップ（ロールアップ） | 集計の粒度を粗くする（店舗 → 地域） |
| スライス | ある次元を1つの値に固定して断面を見る（2024年だけ） |
| ダイス | 分析する次元の組合せや軸を入れ替える |

## データマイニング

大量のデータから、統計や機械学習の手法を使って **人が気づいていない規則性や関係** を発見することです。

| 手法 | 内容 | 例 |
| --- | --- | --- |
| アソシエーション分析 | 同時に起こりやすい事象の組合せを見つける（バスケット分析） | 「おむつを買う人はビールも買う」 |
| クラスタ分析 | 似た性質のデータをグループに分ける | 顧客の購買傾向による分類 |
| 決定木 | 条件分岐を木構造にして分類・予測する | 解約しそうな顧客の判定 |
| テキストマイニング | 文章データから頻出語や傾向を抽出する | 問合せ内容や SNS 投稿の分析 |

### 例題: アソシエーション分析の指標

**問** 全取引 1,000 件のうち、パンを含む取引が 200 件、牛乳を含む取引が 250 件、両方を含む取引が 100 件あった。「パン → 牛乳」の支持度・確信度・リフト値を求めよ。

**解き方**

- **支持度**（両方を含む取引の割合）$= 100 \div 1{,}000 =$ **10%**
- **確信度**（パンを買った取引のうち牛乳も買った割合）$= 100 \div 200 =$ **50%**
- **リフト値** $= \text{確信度} \div \text{牛乳を含む取引の割合} = 50\% \div (250 \div 1{,}000) = 50\% \div 25\% =$ **2.0**

リフト値が 1 より大きければ、パンを買うことが牛乳の購入を後押ししている（関連がある）と判断します。1 なら無関係です。

## ビッグデータとデータレイク

**ビッグデータ** は、従来のデータベースでは扱いきれない大量・多様なデータです。特徴は **3V**（Volume: 量、Variety: 多様性、Velocity: 発生・更新の速度）で表され、Veracity（正確性）と Value（価値）を加えて 5V とすることもあります。

| 分類 | 内容 | 例 |
| --- | --- | --- |
| 構造化データ | 列の定義が決まっている | RDB の表、CSV |
| 半構造化データ | タグなどで構造を表すが、形式が固定されない | JSON、XML |
| 非構造化データ | 決まった構造をもたない | 文書、画像、音声、動画 |

**データレイク** は、構造化・非構造化を問わずデータを **加工せず元の形式のまま** 大量に蓄える保管場所です。
DWH が「格納時に形式をそろえる」のに対し、データレイクは「使うときに目的に応じて解釈・加工する」点が異なります。
部門ごとにデータがばらばらに管理され連携できない状態（**データのサイロ化**）を解消する手段にもなります。

## NoSQL

**NoSQL**（Not only SQL）は、関係モデル以外の方式でデータを管理するデータベースの総称です。

| 種類 | データの持ち方 | 向いている用途 | 製品例 |
| --- | --- | --- | --- |
| キーバリュー型（KVS） | キーと値の組 | セッション情報、キャッシュ | Redis |
| ドキュメント指向型 | JSON などの文書単位。項目は文書ごとに異なってよい | 項目が変わりやすいデータ、Web サービス | MongoDB、CouchDB |
| ワイドカラム型（列指向型） | 行ごとに異なる列を持てる | 大量の書込み、時系列データ | Apache Cassandra |
| グラフ指向型 | ノード（点）とエッジ（関係） | SNS の人間関係、経路探索、推薦 | Neo4j |

| 観点 | RDB | NoSQL（一般的な傾向） |
| --- | --- | --- |
| スキーマ | 事前に厳密に定義 | 柔軟（スキーマレスなものも多い） |
| 整合性 | ACID 特性による強い整合性 | BASE 特性（結果整合性）を採るものが多い |
| 拡張方法 | スケールアップ（サーバの高性能化）が中心 | **スケールアウト**（サーバの台数を増やす）が容易 |
| 複雑な検索・結合 | 得意（SQL） | 不得意なものが多い |

### CAP 定理と BASE 特性

分散データベースでは、**一貫性**（Consistency）・**可用性**（Availability）・**分断耐性**（Partition tolerance）の3つを同時に完全には満たせないとする **CAP 定理** が知られています。
ネットワーク分断が避けられない大規模分散環境では、一貫性を一時的に緩めて可用性を優先する設計がよく採られ、その考え方を **BASE 特性** と呼びます。

| 要素 | 意味 |
| --- | --- |
| Basically Available | 一部に障害があっても、基本的にはサービスを提供し続ける |
| Soft state | データの状態は、外部からの入力がなくても同期の進行によって変化しうる |
| Eventually consistent | 更新直後は複製間で値が食い違っても、**最終的には一致する**（結果整合性） |

データを複数のサーバにキーなどで分割して配置する **シャーディング** は、負荷と容量を水平に分散する代表的な手法です。
大量データの分散処理には Apache Hadoop（分散ファイルシステム HDFS など）や Apache Spark といったフレームワークが使われます。

## 実際の進め方: データ分析を施策につなげる

DWH やマイニングの手法は道具で、それだけでは成果になりません。分析は「目的 → データ準備 → 集計・可視化 → 深掘り → 施策と効果検証」の順で進めます。

1. **目的（問い）と指標を決める** … 「何を決めるための分析か」を一文にし、判断に使う指標とその **定義** を決めます（例: 「リピート率 = 初回購入から 90 日以内に 2 回目の注文をした顧客の割合」）。定義を決めずに集計すると、人によって数字が変わります。結果の見込み（仮説）も書いておくと、集計の切り口が決まります。
2. **データを準備する** … 必要なデータがどのシステムのどの表にあるかを確かめ、ETL で分析用の DB（DWH やデータマート）に集めます。そのうえで **データクレンジング**（表記ゆれ・重複・欠損・明らかな誤りの修正）を行い、テスト用の注文や取消しの扱いなど、対象に含める範囲をそろえます。個人に関するデータは、利用目的の範囲内で使い、氏名やメールアドレスなど分析に不要な項目は外して扱います。
3. **集計・可視化する** … まず全体の数字を出し、次に OLAP の操作（ドリルダウン、スライスなど）で切り口を変えて、差の大きいところを探します。伝えたい内容に合ったグラフを選びます。

| 見せたいもの | 向いているグラフ |
| --- | --- |
| 時間による推移 | 折れ線グラフ |
| 項目どうしの大小の比較 | 棒グラフ |
| 全体に占める割合（構成比） | 帯グラフ、円グラフ |
| 2つの量の関係 | 散布図 |
| 値のばらつき（分布） | ヒストグラム、箱ひげ図 |

4. **深掘りする** … 必要に応じて、アソシエーション分析、クラスタ分析、決定木などで規則性を探します。
5. **施策を決め、効果を検証する** … 分析結果から施策を決め、本当に効果があったかを確かめます。施策を行う群と行わない群を **無作為に** 分けて比べる A/B テストが基本です。施策のあとも、決めた指標を定期的に見続けます（ダッシュボードなど）。

### ワークシート: 分析計画

| 項目 | 記入する内容 |
| --- | --- |
| 問い | 〈何を決めるための分析か〉 |
| 指標と定義 | 〈指標名 = 分子 ÷ 分母、期間、対象〉 |
| 仮説 | 〈こうなっているのではないか〉 |
| 使うデータ | 〈システム・表・期間〉、除外するデータ |
| 集計の切り口 | 〈期間、商品分類、地域、顧客の属性 など〉 |
| 判断の基準 | 〈どんな結果なら、何をするか〉 |

### よくある失敗と対策

| 失敗 | 何が起きるか | 対策 |
| --- | --- | --- |
| 目的を決めずに、データを集めてから考える | 集計表やグラフが増えるだけで、何も決まらない | 先に問いと判断の基準を決める |
| 指標の定義が人によって違う | 会議で数字が合わず、議論が進まない | 定義（分子・分母・期間・除外するデータ）を文書にして共有する |
| データクレンジングをしない | 表記ゆれで同じ地域が別々に集計される、重複で件数が水増しされる | 集計前に表記ゆれ・重複・欠損を確かめる。少量のデータで手計算と照らし合わせる |
| 平均値だけを見る | 一部の極端な値に引っ張られ、実態を見誤る | 分布（ヒストグラム）や中央値も見る。切り口を変えて比べる |
| 相関を因果と取り違える | 効果のない施策に費用をかける | 「施策を受けた人」と「受けなかった人」をそのまま比べず、無作為に分けた A/B テストで確かめる |
| 分析結果を施策につなげない | 報告書で終わる | 判断の基準に照らして、次の行動と担当を決める |

## 事例: あおば書店のリピート率を上げる

[SQL](../sql/) の記事で使った架空のオンライン書店「あおば書店」が、蓄積した注文データを分析します（数値は架空の設定です）。

**① 問いと指標**: 「初めて買った顧客が2回目も買ってくれるようにするには、何をすべきか」。指標は **リピート率**（初回購入から 90 日以内に 2 回目の注文をした顧客 ÷ その期間の新規顧客）です。仮説は「初回に買った本の種類によってリピート率が違うのではないか」としました。

**② データの準備**: 業務 DB の顧客・注文・注文明細・書籍の表を、毎晩 ETL で DWH に取り込んでいます。分析の前に次のクレンジングを行いました。

- 都道府県の表記ゆれ（「東京」「東京都」）を「東京都」にそろえる
- 同じ人がメールアドレスを変えて二重に登録している顧客を、氏名と電話番号で名寄せする（名寄せしないと、2回目の注文が「別の新規顧客」として数えられ、リピート率が実際より低く出る）
- 社内のテスト注文と、取り消された注文を除く

顧客ごとの注文回数と初回の注文日は、例えば次の SQL で求められます。

```sql
SELECT 顧客番号, COUNT(*) AS 注文回数, MIN(注文日) AS 初回注文日
FROM 注文
GROUP BY 顧客番号;
```

**③ 集計とドリルダウン**: 2026 年 1〜6 月の新規顧客 3,000 人のうち、90 日以内に 2 回目の注文をしたのは 660 人で、リピート率は $\dfrac{660}{3{,}000} = 22\%$ でした。初回に買った本の分類でドリルダウンすると、大きな差がありました。

| 初回に買った本の分類 | 新規顧客 | 90 日以内に 2 回目 | リピート率 |
| --- | --- | --- | --- |
| IT 資格書 | 1,000 人 | 350 人 | 35% |
| 一般書 | 1,500 人 | 225 人 | 15% |
| 雑誌・コミック | 500 人 | 85 人 | 17% |
| 合計 | 3,000 人 | 660 人 | 22% |

IT 資格書の顧客は、参考書のあとに問題集を買うなど続けて買う傾向がありました。一方、人数の最も多い一般書の顧客のリピート率が低く、ここを伸ばす余地が大きいと判断しました。

**④ アソシエーション分析**: 同じ期間の全注文 10,000 件で、「データベース入門」を含む注文が 800 件、「SQLドリル」を含む注文が 600 件、両方を含む注文が 240 件でした。

- 支持度 $= \dfrac{240}{10{,}000} = 2.4\%$
- 確信度（データベース入門 → SQLドリル）$= \dfrac{240}{800} = 30\%$
- リフト値 $= 30\% \div \dfrac{600}{10{,}000} = 30\% \div 6\% = 5.0$

リフト値が 1 を大きく上回るので、商品ページに「一緒に買われている本」として表示することにしました（これは 1 回の注文の金額を増やす施策です）。

**⑤ 施策と効果検証**: リピート率を上げる施策として、一般書を初めて買った顧客に、購入から 30 日後に同じ著者・同じ分類の本を案内するメールを送ることにしました。
効果を確かめるため、7 月の一般書の新規顧客 1,200 人を **無作為に** 2 つの群に分けました。

| 群 | 人数 | 90 日以内に 2 回目 | リピート率 |
| --- | --- | --- | --- |
| A（メールを送らない） | 600 人 | 90 人 | 15% |
| B（メールを送る） | 600 人 | 126 人 | 21% |

B 群のほうが 6 ポイント高く、この差が偶然の範囲を超えるかを統計的な検定で確かめたうえで、すべての新規顧客に展開しました。
なお、「メールを開いた人」と「開かなかった人」のリピート率を比べる方法は使いませんでした。メールを開く人はもともと書店への関心が高く、メールがなくても買った可能性があるため、メールの効果を正しく測れないからです。
展開後も、リピート率を初回の分類別に毎月ダッシュボードで確認しています。

## 試験対策のポイント

- **ITパスポート**: データウェアハウス・データマイニング・ビッグデータ・テキストマイニングの意味を区別できることが中心です。NoSQL ではキーバリュー型・ドキュメント指向型・グラフ指向型の特徴を答えられるようにします。
- **基本情報**: OLTP と OLAP、DWH とデータマート、ETL とデータクレンジングの役割が問われます。アソシエーション分析の支持度・確信度・リフト値の計算や、データレイクの特徴も押さえます。
- **応用情報**: RDB と NoSQL の比較、CAP 定理・BASE 特性・結果整合性、シャーディングによるスケールアウトなど、要件に応じたデータベース方式の選択が問われます。BASE は ACID との対比で説明できるようにしておきます。
