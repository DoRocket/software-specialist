データベース設計は、業務で扱うデータとその関係を整理し、DBMS 上の表や格納方式にまで落とし込む作業です。
**概念設計 → 論理設計 → 物理設計** の順に、DBMS に依存しない抽象的な表現から、特定の DBMS での具体的な実装へと詳細化していきます。

## 設計の3段階

| 段階 | 内容 | 主な成果物 | DBMS への依存 |
| --- | --- | --- | --- |
| 概念設計 | 業務に必要なデータ（実体）と、その関連を洗い出して図にする | **E-R図**（概念データモデル） | しない |
| 論理設計 | 採用するデータモデル（関係モデルなど）に合わせて表・主キー・外部キー・制約を決め、正規化する | 表の定義（論理データモデル） | データモデルには依存する |
| 物理設計 | 格納領域・ファイル編成・インデックスなどを、性能と記憶効率の観点から決める | 物理データモデル、容量見積り | する |

概念設計の前には、業務で使うデータ項目を集めて意味を整理する **データ分析** を行います。
同じものを違う名前で呼ぶ **異音同義語**（「得意先」と「顧客」）や、違うものを同じ名前で呼ぶ **同音異義語** をなくし、項目名と意味を **データディクショナリ** で一元管理します。

### 3層スキーマ

DBMS の内部構造は、データの見え方を3つの層（スキーマ）に分けて定義します。層を分けることで、格納方式を変えてもアプリケーションに影響しない **データ独立性** が高まります。

| スキーマ | 内容 | 対応するもの |
| --- | --- | --- |
| 外部スキーマ（副スキーマ） | 利用者やアプリケーションから見たデータ | ビュー |
| 概念スキーマ | データベース全体の論理的な構造 | 表の定義 |
| 内部スキーマ（記憶スキーマ） | 記憶装置上の物理的な格納方法 | インデックス、格納領域 |

「概念スキーマ」は DBMS 上で定義する表構造のことで、DBMS に依存しない「概念設計（E-R図）」とは別物です。名前が似ているので混同しないようにします。

## E-R図

E-R図（Entity-Relationship Diagram）は、データを **エンティティ（実体）** と **リレーションシップ（関連）** で表す図です。

| 構成要素 | 意味 | 例 |
| --- | --- | --- |
| エンティティ | 管理対象となる「もの」や「こと」 | 顧客、商品、受注 |
| 属性 | エンティティがもつ性質 | 顧客番号、顧客名 |
| リレーションシップ | エンティティ間の関連 | 顧客が受注を「行う」 |

### カーディナリティ（多重度）

リレーションシップの両端で、相手側のエンティティが **いくつ対応するか** を表したものです。

| 種類 | 意味 | 例 |
| --- | --- | --- |
| 1対1 | 一方の1件に、他方の1件が対応 | 社員 と 社員証 |
| 1対多 | 一方の1件に、他方の複数件が対応 | 部署 と 社員（1つの部署に複数の社員） |
| 多対多 | 双方とも複数件が対応 | 学生 と 科目（1人が複数科目を履修し、1科目を複数人が履修） |

IPA の試験問題では、1対多の関連を **矢印（矢印の先が「多」側）** で表す記法がよく使われます。
このほか、多側を鳥の足のような記号で描く IE 記法や、UML のクラス図で「1」「0..1」「1..*」「*」のように多重度を書く方法もあり、「0..1」のように **0件を許すか（任意か必須か）** まで表現できます。

```text
[部署] ──────→ [社員]        部署1件に社員が複数（1対多）
[学生] ←─────→ [科目]        多対多（このままでは表にできない）
```

## E-R図から表への変換

| E-R図の要素 | 表への変換ルール |
| --- | --- |
| エンティティ | 1つの表にする。エンティティを識別する属性を **主キー** にする |
| 1対多 | **「多」側の表** に、「1」側の主キーを **外部キー** として追加する |
| 1対1 | どちらか一方の表に、他方の主キーを外部キーとして追加する |
| 多対多 | 両者をつなぐ **連関エンティティ（関連表）** を新たに作り、双方の主キーを外部キーとして持たせる（通常は2つを組み合わせた複合主キー） |

多対多を直接表にできないのは、1つのセルに複数の値を入れることになり、第1正規形に反するためです。
学生と科目の例では、次のように「履修」表を設けて1対多の関連2つに分解します。

| 表 | 属性（太字は主キー） |
| --- | --- |
| 学生 | **学生番号**, 氏名 |
| 科目 | **科目コード**, 科目名 |
| 履修 | **学生番号, 科目コード**, 成績 |

「成績」のように、学生と科目の **組合せ** によって決まる属性は、連関エンティティ側に置かれます。

## インデックス

インデックス（索引）は、表の特定の列について値と格納位置の対応をまとめたもので、**検索を高速化** する物理設計の手段です。

| 種類 | 特徴 |
| --- | --- |
| B-tree インデックス | 木構造で値を順序付けて管理する。一致検索と **範囲検索** の両方に強く、最も一般的 |
| ハッシュインデックス | ハッシュ関数で格納位置を求める。一致検索は高速だが、範囲検索や並べ替えには使えない |
| ビットマップインデックス | 値ごとに「該当する行は1」というビット列を持つ。性別のような **値の種類が少ない列** の検索に向くが、更新が多い表には不向き |
| ユニークインデックス | 値の重複を許さない。主キーや一意性制約の実現に使われる |
| クラスタ化インデックス | インデックスのキー順に **データ自体を並べて格納** する。1つの表に1つだけ作れる |
| カバリングインデックス | 問合せに必要な列をすべてインデックスに含め、表本体を読まずに結果を返せるようにする |
| 転置インデックス | 単語からそれを含む文書を引けるようにしたもの。全文検索で使われる |

インデックスは万能ではありません。行の追加・更新・削除のたびにインデックスも更新されるため **更新処理が遅くなり、記憶容量も増えます**。
検索条件や結合条件によく使われ、値の絞り込み効果が高い列に作り、更新が頻繁な表ではインデックスの数を絞るのが基本です。

## 例題: ディスク容量の見積り

**問** 1件 200 バイトのレコードを 100,000 件格納する。ブロック長は 4,000 バイトで、1件のレコードは複数のブロックにまたがらない。必要なブロック数と容量はいくらか。

**解き方** 1ブロックに入るレコード数は $4{,}000 \div 200 = 20$ 件です。必要なブロック数は $100{,}000 \div 20 =$ **5,000 ブロック** で、容量は $5{,}000 \times 4{,}000 = 20{,}000{,}000$ バイト $=$ **20M バイト** です。
割り切れない場合は、1ブロックあたりの件数は **切り捨て**、ブロック数は **切り上げ** で求めます。

## 試験対策のポイント

- **ITパスポート**: E-R図がデータとその関連を表す図であること、主キー・外部キー・インデックスの役割を答えられれば十分です。「インデックスは検索を速くする」と押さえます。
- **基本情報**: E-R図のカーディナリティを業務の説明文から読み取る問題、E-R図から表を作るときに外部キーをどちらの表に置くかを問う問題が定番です。多対多は連関エンティティで分解する、と覚えます。
- **応用情報**: 午後のデータベース問題では、E-R図の欠けている関連線や多重度を補う問題、関係スキーマに外部キーを補完する問題がほぼ毎回出ます。インデックスの種類と、更新負荷を含めた適否の判断も問われます。
