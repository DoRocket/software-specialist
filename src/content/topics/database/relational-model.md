関係モデルは、データを **表（関係: relation）** の集まりとして表現するデータモデルです。
E.F.コッドが提唱したもので、関係データベース（RDB）の理論的な土台になっています。
業務システムでは「顧客」「商品」「注文」のような情報をそれぞれ表にし、**キー** で表どうしをつないで管理します。

## 前提となる用語

- **DBMS**（データベース管理システム）: データベースを管理するソフトウェア。表の定義、データの検索・更新、同時実行の制御、障害回復などを受け持ちます。
- **NULL**: 値が「無い」または「分からない」ことを表す特別な印です。数値の 0 や空の文字列とは別物で、`=` で比べても真になりません（SQL では `IS NULL` で判定します）。

## 用語の対応

関係モデルの理論用語と、実際のデータベースで使う用語は次のように対応します。

| 関係モデルの用語 | 一般的な呼び方 | 意味 |
| --- | --- | --- |
| 関係（リレーション） | 表（テーブル） | 同じ形式のデータの集まり |
| タプル（組） | 行（レコード） | 1件分のデータ |
| 属性（アトリビュート） | 列（カラム、項目） | データの項目 |
| 定義域（ドメイン） | 列が取りうる値の集合 | 例: 年齢は 0 以上の整数 |

関係は集合として定義されるため、理論上は **同じタプルが重複せず、行や列の並び順に意味がない** という性質があります。

## キー

| キー | 説明 |
| --- | --- |
| 候補キー | 行を一意に特定でき、かつ余分な属性を含まない（極小な）属性の組 |
| 主キー | 候補キーの中から1つ選んだもの。**一意** で **NULL を許さない** |
| 代替キー | 主キーに選ばれなかった候補キー |
| 複合キー（連結キー） | 複数の属性を組み合わせたキー |
| 外部キー | 他の表の主キー（または候補キー）を参照する属性 |
| スーパキー | 行を一意に特定できる属性の組（余分な属性を含んでもよい） |

### 外部キーと参照制約

外部キーには **参照制約（参照整合性制約）** を設定できます。
外部キーの値は、参照先の表に存在する値か NULL でなければなりません。

**社員表**

| 社員番号（主キー） | 氏名 | 部署コード（外部キー） |
| --- | --- | --- |
| 101 | 佐藤 | D1 |
| 102 | 鈴木 | D2 |
| 103 | 高橋 | D1 |

**部署表**

| 部署コード（主キー） | 部署名 |
| --- | --- |
| D1 | 営業部 |
| D2 | 開発部 |

この例で、社員表に部署コード `D9`（部署表に無い値）の行を追加しようとすると参照制約違反になります。
また、社員から参照されている部署 `D1` を部署表から削除する操作も、制約の設定（拒否・連鎖削除・NULL 設定など）に従って制限されます。

## 関係演算

関係（表）に対する演算で、結果もまた関係（表）になります。

| 演算 | 内容 | SQL での対応 |
| --- | --- | --- |
| 選択（selection） | 条件に合う **行** を取り出す | `WHERE` 句 |
| 射影（projection） | 指定した **列** を取り出す | `SELECT` 句の列指定 |
| 結合（join） | 共通の属性の値をもとに2つの表をつなぐ | `JOIN` / `WHERE` での結合条件 |
| 商（division） | ある表のすべての値と組になっている行を求める | 直接の構文は無い（副問合せなどで表現） |

このほか、集合演算として **和・差・積（共通部分）・直積** があります。和・差・積は、両方の表の列構成（属性の数と定義域）が同じ **和両立** の場合に適用できます。

### 例

上の社員表と部署表について:

- **選択**: 部署コードが D1 の行 → 佐藤、高橋の2行
- **射影**: 氏名の列だけ → 佐藤、鈴木、高橋
- **結合**: 部署コードで結合 → 「101 佐藤 D1 営業部」のように部署名が付いた表
- **直積**: $\text{社員表3行} \times \text{部署表2行} = \text{6行}$（すべての組合せ）

## 実際の進め方: 表とキーを決める

新しく表を作るときは、次の順でキーを決めていきます。

1. **何を1行にするかを決める**: 「顧客1人で1行」「注文1件で1行」「注文の中の書籍1冊の種類で1行」のように、1行が表す単位を言葉で書きます。ここがあいまいだと、後でキーが決まりません。
2. **行を一意に特定できる属性（の組）を探す**: 実データを見ながら「この値が同じ行は2つと無いか」を確かめます。サンプルにたまたま重複が無いだけ、ということもあるので、業務のルール（同じメールアドレスで2人登録できるか、など）で判断します。
3. **候補キーの中から主キーを選ぶ**: 値が **変わらない・必ずある・短い** ものを選びます。氏名やメールアドレスは変わりうるので、業務で使う意味を持たない番号（**代理キー**、サロゲートキー）を振って主キーにすることがよくあります。
4. **他の表とのつながりを外部キーにする**: 「注文はどの顧客のものか」のように、ほかの表の行を指す列を外部キーにし、参照制約を付けます。
5. **参照先の行が削除・更新されたときの動作を決める**: SQL では `ON DELETE` に次のような動作を指定できます。

| 指定 | 参照先の行を削除しようとしたとき | 向いている場面 |
| --- | --- | --- |
| `NO ACTION` / `RESTRICT` | 参照している行があれば削除を **拒否** する（何も書かないときの既定は `NO ACTION`） | 注文履歴がある顧客を消させたくない |
| `CASCADE` | 参照している行も **連鎖して削除** する | 注文を消すなら、その明細もまとめて消す |
| `SET NULL` | 参照している行の外部キーを **NULL にする** | 担当者が退職したら「担当者なし」に戻す |

## 事例: 架空のオンライン書店「あおば書店」

小さなオンライン書店の注文管理を、4つの表で表します（この事例は正規化・SQL・トランザクションの記事でも使います）。

**顧客**

| 顧客番号（主キー） | 氏名 | 都道府県 | メールアドレス |
| --- | --- | --- | --- |
| C001 | 青木 | 東京都 | `aoki@example.com` |
| C002 | 石井 | 大阪府 | `ishii@example.com` |
| C003 | 上田 | 東京都 | `ueda@example.com` |
| C004 | 江口 | 福岡県 | `eguchi@example.com` |

**書籍**

| 書籍番号（主キー） | 書名 | 価格 | 在庫数 |
| --- | --- | --- | --- |
| B01 | データベース入門 | 2800 | 12 |
| B02 | SQLドリル | 1800 | 5 |
| B03 | ネットワーク基礎 | 3200 | 0 |
| B04 | アルゴリズム図鑑 | 2400 | 8 |

**注文**

| 注文番号（主キー） | 顧客番号（外部キー → 顧客） | 注文日 |
| --- | --- | --- |
| 1001 | C001 | 2026-04-01 |
| 1002 | C002 | 2026-04-01 |
| 1003 | C001 | 2026-04-03 |
| 1004 | C003 | 2026-04-05 |

**注文明細**

| 注文番号（主キー・外部キー → 注文） | 書籍番号（主キー・外部キー → 書籍） | 数量 | 単価 |
| --- | --- | --- | --- |
| 1001 | B01 | 1 | 2800 |
| 1001 | B02 | 2 | 1800 |
| 1002 | B04 | 1 | 2400 |
| 1003 | B02 | 1 | 1800 |
| 1003 | B03 | 1 | 3200 |
| 1004 | B01 | 2 | 2800 |

### キーの判断

- **顧客**: 顧客番号もメールアドレスも、業務のルール上 1 人に 1 つで重複しないので、どちらも **候補キー** です。メールアドレスは利用者が変更できるため、変わらない顧客番号を主キーにし、メールアドレスは **代替キー**（SQL では `UNIQUE` 制約）にします。
- **注文明細**: 1 件の注文に複数の書籍があり、同じ書籍は複数の注文に現れます。注文番号と書籍番号の **複合キー** で初めて行が決まります。2 つの列はそれぞれ外部キーでもあります。
- **外部キーの動作**: 注文履歴のある顧客を誤って削除すると売上の記録が壊れるので、注文 → 顧客の参照は削除を拒否（`NO ACTION`）にします。注文明細 → 注文は、注文を取り消して削除するなら明細も不要なので `CASCADE` が候補になります。

### 関係演算で業務の質問に答える

| 業務の質問 | 関係演算 | 結果 |
| --- | --- | --- |
| 東京都の顧客は誰か | 顧客から **選択**（都道府県 = 東京都） | 青木、上田 |
| 書名の一覧がほしい | 書籍から **射影**（書名） | 4つの書名 |
| 注文ごとに顧客の氏名を付けたい | 注文と顧客を顧客番号で **結合** | 1001 青木、1002 石井、1003 青木、1004 上田 |
| 一度も注文していない顧客は誰か | 顧客の顧客番号の集合 **差** 注文の顧客番号の集合（どちらも顧客番号だけに射影して和両立にする） | C004（江口） |

最後の例のように、差をとる前に射影して列構成をそろえる（和両立にする）のがポイントです。SQL での書き方は [SQL](../sql/) の記事で同じデータを使って確かめます。

## 試験対策のポイント

- **ITパスポート**: 主キー（一意・NULL 不可）と外部キー（他の表との関連付け）の役割、選択・射影・結合の違いを区別できること。「行を取り出すのが選択、列を取り出すのが射影」は頻出です。
- **基本情報**: 表の例から主キーとして適切な列（の組）を選ぶ問題、参照制約に違反する操作を選ぶ問題がよく出ます。直積の行数（行数の積）も確認しておきましょう。
- **応用情報**: 候補キー・スーパキーの区別、関係演算の結果を SQL に置き換える問題、E-R 図から表を導いて外部キーを判断する問題に対応できるようにします。
