トランザクションは、データベースに対する **一連の処理をひとまとまりにした単位** です。
例えば「口座Aから1万円引き出し、口座Bに1万円入金する」は、片方だけ実行されると矛盾するため、全体を1つのトランザクションとして扱います。

## 前提となる用語

- **コミット**: トランザクションの更新をすべて確定させること。確定した更新は他のトランザクションから見えるようになり、取り消せなくなります。
- **ロールバック**: トランザクションの更新をすべて取り消し、開始前の状態に戻すこと。
- **同時実行**: 多数の利用者の処理を、DBMS が並行して進めること。1件ずつ順番に処理するより速い反面、互いの更新がぶつかる問題が起きます。
- **自動コミット**: 1つの SQL 文を実行するたびに自動でコミットする動作です。多くの DBMS や、プログラムから DBMS に接続するライブラリは、何も指定しなければこの動作になっています。

## ACID 特性

トランザクションが満たすべき性質の頭文字です。

| 特性 | 意味 | 実現する主な仕組み |
| --- | --- | --- |
| Atomicity（原子性） | すべて実行されるか、まったく実行されないかのどちらか | コミット / ロールバック |
| Consistency（一貫性） | 実行前後でデータの整合性（制約）が保たれる | 整合性制約 |
| Isolation（独立性・隔離性） | 同時に実行しても、互いに干渉せず順番に実行した場合と同じ結果になる | 排他制御（ロック） |
| Durability（耐久性・永続性） | コミットした結果は障害が起きても失われない | ログ、障害回復 |

## 排他制御

複数のトランザクションが同じデータを同時に更新すると、**ロストアップデート**（後の更新が先の更新を上書きして消す）などの不整合が起こります。
これを防ぐのが排他制御で、代表的な方法が **ロック** です。

| ロックの種類 | 別名 | 他のトランザクションの参照 | 他のトランザクションの更新 |
| --- | --- | --- | --- |
| 共有ロック | 読取りロック | 可（共有ロック同士は両立） | 不可 |
| 専有ロック | 排他ロック・書込みロック | 不可 | 不可 |

- ロックをかける範囲（表・ページ・行など）を **ロックの粒度** といいます。粒度が小さいほど同時実行性は高まりますが、ロックの管理負荷は増えます。
- ロックを獲得する段階と解放する段階を分ける **2相ロック方式** を守ると、同時実行の結果が直列に実行した場合と同じになる（直列化可能性が保証される）ことが知られています。

### デッドロック

2つ以上のトランザクションが、互いに相手が持つロックの解放を待ち続けて処理が進まなくなる状態です。

| 時刻 | トランザクション T1 | トランザクション T2 |
| --- | --- | --- |
| 1 | データ X をロック | データ Y をロック |
| 2 | データ Y のロックを要求 → 待ち | |
| 3 | | データ X のロックを要求 → 待ち（デッドロック） |

対策として、**ロックを獲得する順序をすべてのトランザクションで統一する** ことで発生を防げます。
発生した場合は、DBMS が待ちの関係を検出し、一方のトランザクションをロールバックして解消します。

### 隔離性水準

独立性を完全に守ると待ちが増えて遅くなるため、SQL では **どこまで干渉を許すか（隔離性水準）** を選べます。標準 SQL では次の4つが定められています（○は起こりうる、×は起こらない）。

| 隔離性水準 | ダーティリード | ノンリピータブルリード | ファントム |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | ○ | ○ | ○ |
| `READ COMMITTED` | × | ○ | ○ |
| `REPEATABLE READ` | × | × | ○ |
| `SERIALIZABLE` | × | × | × |

- **ダーティリード**: 他のトランザクションが **まだコミットしていない** 値を読んでしまう。相手がロールバックすると、存在しなかった値を使ったことになる
- **ノンリピータブルリード**: 同じ行を2回読む間に他のトランザクションが更新・コミットし、1回目と2回目で値が変わる
- **ファントム**: 同じ条件で2回検索する間に他のトランザクションが行を追加し、2回目に無かった行（幻の行）が現れる

`SERIALIZABLE` は直列に実行した場合と同じ結果を保証します。実際の DBMS の既定値は製品によって異なるため、使う DBMS の設定を確認します。

## 障害回復

DBMS は更新の前後の値（更新前ログ・更新後ログ）を **ログファイル（ジャーナル）** に記録し、障害時の回復に利用します。

| 回復方法 | 使うログ | 用途 |
| --- | --- | --- |
| ロールバック（後退復帰） | 更新前ログ | 未完了・異常終了したトランザクションを取り消し、開始前の状態に戻す |
| ロールフォワード（前進復帰） | 更新後ログ | バックアップから復元した後、コミット済みの更新を再現する |

### 障害の種類と対応

- **トランザクション障害**（プログラムの異常終了など）: そのトランザクションをロールバックします。
- **システム障害**（電源断など、ディスクは無事）: 最後の **チェックポイント** を起点に、障害発生時点でコミット済みだったトランザクションはロールフォワード、未コミットのものはロールバックします。
- **媒体障害**（ディスク故障）: バックアップファイルからデータベースを復元し、更新後ログを使ってロールフォワードします。

チェックポイントは、メモリ上の更新内容を定期的にディスクへ書き出す時点です。これより前にコミットされた更新はディスクに反映済みなので、回復処理の範囲を短くできます。

## 2相コミット

複数のデータベース（サイト）にまたがる **分散トランザクション** で原子性を保つための方式です。調整役（コーディネータ）と各参加者の間で、次の2段階でコミットします。

1. **第1相（準備）**: コーディネータが各参加者に「コミット可能か」を問い合わせ、各参加者はコミットもロールバックもできる **セキュア状態** になって可否を返答する。
2. **第2相（確定）**: 全員が可と答えればコミットを、1つでも否（または応答なし）があればロールバックを全参加者に指示する。

一部のサイトだけがコミットする事態を防げますが、第1相で可と答えた参加者は第2相の指示を受けるまで結果を確定できず、コーディネータに障害が起きると待たされ続ける（ブロッキング）という弱点があります。

## 事例: あおば書店の注文確定処理

架空のオンライン書店「あおば書店」（[SQL](../sql/) の記事と同じ表）では、利用者が「注文を確定」を押すと次の処理を行います。
支払いには、店のサイトに前もって入金しておく **プリペイド残高**（残高表: 顧客番号, 残高）を使うことにします。

1. 書籍表の在庫数を注文数だけ減らす
2. 残高表から代金を引き落とす
3. 注文表と注文明細表に行を追加する

### 不具合1: トランザクションにしないと二重引落しが起きる

自動コミットのまま、3つの処理を1文ずつ確定させていたとします。青木さん（残高 10,000 円）が SQLドリル（1,800 円）を注文しました。

| 時刻 | できごと | 青木さんの残高 | 注文の記録 |
| --- | --- | --- | --- |
| 1 | 「注文を確定」を押す。在庫数を減らす（確定） | 10,000 | なし |
| 2 | 残高から 1,800 円を引き落とす（確定） | 8,200 | なし |
| 3 | 注文の登録中に通信が切れ、処理が中断する | 8,200 | なし |
| 4 | 画面に「注文できませんでした」と出たので、もう一度押す | 8,200 | なし |
| 5 | 在庫を減らし、1,800 円を引き落とし、今度は注文の登録まで成功 | 6,400 | 1件 |

注文は1件なのに 3,600 円が引き落とされ（**二重引落し**）、在庫も2冊減っています（**在庫のずれ**）。
1〜3 を1つのトランザクションにしておけば、時刻 3 の失敗でロールバックされ、残高 10,000 円・在庫も元のままに戻るので、やり直しても正しい結果になります（原子性）。

```sql
START TRANSACTION;

UPDATE 書籍 SET 在庫数 = 在庫数 - 1
WHERE  書籍番号 = 'B02' AND 在庫数 >= 1;
-- 更新件数が 0 なら在庫切れ → ROLLBACK して終了

UPDATE 残高 SET 残高 = 残高 - 1800
WHERE  顧客番号 = 'C001' AND 残高 >= 1800;
-- 更新件数が 0 なら残高不足 → ROLLBACK して終了

INSERT INTO 注文 (注文番号, 顧客番号, 注文日) VALUES (1005, 'C001', DATE '2026-04-06');
INSERT INTO 注文明細 (注文番号, 書籍番号, 数量, 単価) VALUES (1005, 'B02', 1, 1800);

COMMIT;   -- ここで初めて4つの更新がまとめて確定する
```

途中でエラーが起きたら `ROLLBACK` を実行します。コミット前にプログラムや DBMS が止まった場合も、未コミットのトランザクションとして障害回復でロールバックされます。

### 不具合2: 同時に注文すると在庫がずれる（ロストアップデート）

残り1冊の「アルゴリズム図鑑」を、上田さんと江口さんがほぼ同時に注文しました。プログラムが「在庫数を読む → 1 以上なら、読んだ値から 1 を引いた値を書き込む」という作りで、ロックをかけていなかったとします。

| 時刻 | 上田さんの処理（T1） | 江口さんの処理（T2） | 在庫数 |
| --- | --- | --- | --- |
| 1 | 在庫数を読む → 1（注文できる） | | 1 |
| 2 | | 在庫数を読む → 1（注文できる） | 1 |
| 3 | 1 − 1 = 0 を書き込み、コミット | | 0 |
| 4 | | 1 − 1 = 0 を書き込み、コミット | 0 |

2人とも注文に成功しましたが、在庫数は 0 で、実際の本は1冊しかありません。T2 の書き込みが T1 の更新を上書きして消したためです。
数量が2冊以上だと数字のずれとして表に出ます（在庫 10 冊に 3 冊と 2 冊の注文が重なると、本来 5 冊のはずが 7 冊や 8 冊と記録される）。

対策は次のどちらか（または両方）です。

- **読むときに専有ロックをかける**: T1 が在庫数の行をロックしている間、T2 は読むのを待たされ、T1 のコミット後の値（0）を読むので「在庫切れ」と判断できます。
- **現在の値をもとに条件付きで更新する**: 上の SQL のように `在庫数 = 在庫数 - 1 ... AND 在庫数 >= 1` と1文で書くと、DBMS が更新する行に専有ロックをかけるので、後から来た更新は待たされます。多くの DBMS では、待ちが解けたあと確定後の値（0）で条件が判定されて0行の更新となり、在庫切れとして扱えます（隔離性水準によっては、待たされた側がエラーになり、やり直しを求められます）。

### 不具合3: 2冊を同時に注文するとデッドロックが起きる

青木さんが「B01 と B02」を、石井さんが「B02 と B01」を、それぞれ画面の並び順で在庫を減らしていくと、互いに相手が先にロックした行を待ってデッドロックになることがあります。
**在庫を更新する順序を「書籍番号の昇順」などに統一** すれば、2人とも B01 → B02 の順にロックするので、循環した待ちは起きません。

## 実際の進め方: トランザクションを設計する

1. **一緒に成功・失敗すべき更新を洗い出す**: 「在庫・代金・注文の記録」のように、どれか1つだけ確定すると困る更新を1つのトランザクションにまとめます。
2. **範囲はできるだけ短くする**: ロックを持っている時間が長いほど他の処理が待たされます。利用者の入力待ちや、外部への問合せをトランザクションの途中に入れないようにします。
3. **「読んでから書く」処理は、ロックか条件付き更新にする**: ロストアップデートを防ぎます。更新件数を確かめ、想定どおりでなければロールバックします。
4. **ロックの順序を統一する**: デッドロックを減らします。それでもデッドロックで自分のトランザクションがロールバックされることはあるので、**やり直す処理** を用意しておきます。
5. **隔離性水準を決める**: 集計のように多少のずれを許せる読取りと、在庫・残高のように許せない更新とで、必要な水準を考えます。
6. **データベースの外の処理に気を付ける**: クレジットカード会社の決済のような外部のサービスは、自分のデータベースのロールバックでは取り消せません。2相コミットに対応していない相手には、同じ依頼を2回受けても1回分しか処理しない仕組み（依頼ごとに一意な番号を付けるなど）や、失敗時に取消しを依頼する処理を組み合わせます。

## 試験対策のポイント

- **ITパスポート**: ACID の4つの意味、ロック（排他制御）の目的、ロールバックとロールフォワードの違いが問われます。「更新前ログ→ロールバック」「バックアップ＋更新後ログ→ロールフォワード」と対応付けて覚えます。
- **基本情報**: 時系列の図からデッドロックの発生やロストアップデートを判断する問題、共有ロック・専有ロックの両立性、障害発生時にどのトランザクションをロールバック／ロールフォワードするかを選ぶ問題が頻出です。
- **応用情報**: チェックポイントと障害時刻の図から回復対象を判定する問題、2相コミットの手順と弱点、隔離性水準（ダーティリードなど）との関係まで理解しておきます。
