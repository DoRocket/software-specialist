設計は、要件定義で決めた「何を作るか」を、「どのような構造で作るか」に落とし込む工程です。
処理の流れに着目する **構造化設計** と、データと操作をひとまとめにする **オブジェクト指向設計** が代表的な考え方で、図の表記法として **UML** が広く使われます。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| 外部設計 | 利用者から見える部分（画面、帳票、外部システムとのやり取り、扱うデータ）を決める設計。基本設計とも呼ぶ |
| 内部設計 | 外部設計を実現するための内部の構造（プログラムの分割、モジュール間のやり取り、データベースの物理的な構造）を決める設計。詳細設計とも呼ぶ |
| モジュール | プログラムを分割した単位（関数、クラス、部品など） |
| クラスとインスタンス | クラスは「予約」のような種類の設計図。インスタンス（オブジェクト）は、そこから作られる「予約番号 1001 の予約」のような個々のもの |
| 属性と操作 | クラスが持つデータ（予約の人数、来店日時）と、クラスが行う処理（キャンセルする） |
| アクター | システムの外にいて、システムとやり取りする人や外部システム |

## 構造化設計

機能を段階的に分解し、プログラムを独立性の高いモジュールに分割します。データの流れは **DFD（データフロー図）** で表します。

| 分割技法 | 考え方 |
| --- | --- |
| STS分割 | データの流れを「源泉（Source）→変換（Transform）→吸収（Sink）」に分ける |
| TR分割 | 入力データの種類（トランザクション）ごとに処理を分ける |
| 共通機能分割 | 複数箇所で使う共通処理を独立したモジュールにする |

### 凝集度と結合度

良い設計は **モジュール内の凝集度が強く、モジュール間の結合度が弱い** 状態です。

| 凝集度（上ほど強く望ましい） | 内容 |
| --- | --- |
| 機能的凝集 | 単一の機能だけを実行する |
| 情報的凝集 | 同じデータを扱う複数の機能をまとめ、機能ごとに入口を持つ |
| 連絡的凝集 | 同じデータを使う処理を順番に実行する |
| 手順的凝集 | 決められた順序で実行する処理をまとめる |
| 時間的凝集 | 初期化処理など、同じ時期に実行する処理をまとめる |
| 論理的凝集 | 関連する複数機能を引数などで切り替えて実行する |
| 暗合的凝集 | 関係のない処理を寄せ集めた |

| 結合度（上ほど弱く望ましい） | 内容 |
| --- | --- |
| データ結合 | 必要な単一データ項目だけを引数で渡す |
| スタンプ結合 | 構造体などのデータ構造を丸ごと渡し、その一部を使う |
| 制御結合 | 処理を切り替えるためのフラグなど制御情報を渡す |
| 外部結合 | 単一のデータ項目を外部宣言（グローバル変数）で共有する |
| 共通結合 | データ構造全体を共通域（グローバル領域）で共有する |
| 内容結合 | 他のモジュールの内部を直接参照・変更する |

## オブジェクト指向

データ（属性）と操作（メソッド）を **オブジェクト** としてまとめ、その設計図を **クラス** と呼びます。

| 概念 | 説明 |
| --- | --- |
| カプセル化 | 内部のデータを隠蔽し、メソッド経由でのみ操作させる |
| 継承（インヘリタンス） | スーパクラスの属性・操作をサブクラスが引き継ぐ |
| 汎化・特化 | 共通部分をまとめて上位クラスにするのが汎化、その逆が特化（is-a 関係） |
| 集約 | 全体と部分の関係（part-of 関係） |
| ポリモーフィズム（多態性） | 同じメッセージに対し、オブジェクトごとに異なる振る舞いをする |

## 主なUML図

UML（Unified Modeling Language）は、OMG が標準化したモデリング言語です。図は大きく構造図と振る舞い図に分かれます。

| 種類 | 図 | 表すもの |
| --- | --- | --- |
| 構造図 | クラス図 | クラスの属性・操作と、クラス間の関連・多重度・汎化 |
| 構造図 | コンポーネント図 / 配置図 | ソフトウェア部品の構成 / ハードウェアへの配置 |
| 振る舞い図 | ユースケース図 | アクター（利用者や外部システム）とシステムの機能の関係 |
| 振る舞い図 | アクティビティ図 | 処理の流れ（分岐・並行処理を含む） |
| 振る舞い図 | シーケンス図 | オブジェクト間のメッセージのやり取りを時系列で表す |
| 振る舞い図 | ステートマシン図 | イベントによる状態の遷移 |
| 振る舞い図 | コミュニケーション図 | オブジェクト間の関係に着目したメッセージのやり取り |

クラス図の関連には **多重度** を書きます。例えば「顧客 1 ―― 0..* 注文」は、1人の顧客が0件以上の注文を持ち、1件の注文は1人の顧客に属することを表します。
集約は白抜きのひし形、より強い全体と部分の関係（部分が全体と生存期間を共にする）である **コンポジション** は黒塗りのひし形で表します。

## 実際の進め方

UML の図は「全部描く」ものではなく、関係者で認識をそろえたい部分・誤りが起きやすい部分を選んで描きます。オブジェクト指向で機能を設計するときの、一般的な流れの一例です。

1. **要件と範囲を確かめる** … 設計する機能が、どの要件（要件 ID）を実現するのかを一覧にします。後で「この設計はどの要件のためか」をたどれるようにします。
2. **外部設計: 利用者とのやり取りを決める** … ユースケース図で「誰が・どの機能を使うか」を整理し、ユースケースごとに正常な流れと例外の流れ（失敗・取消し・期限切れ）を文章で書きます（ユースケース記述）。画面の項目と画面遷移、外部システムとの接続方法もここで決めます。
3. **クラス図を描く** … ユースケース記述や要件の文章から **名詞を拾い出し**、クラスの候補にします（名詞抽出法）。それ自体が ID を持ち、複数の値をまとめて持つものはクラス、1つの値で表せるもの（人数、金額）は属性にします。次にクラスどうしの関連を引き、両方向に「1つの A に対して B はいくつか」と問うて **多重度** を書きます。
4. **シーケンス図で主な流れを確かめる** … 正常な流れを、どのオブジェクトがどのメッセージを送るかで描きます。メッセージを受ける側に、その処理（操作）をクラス図へ追加します。描いてみて「この処理を担当するクラスがない」「同じデータを2か所で持っている」と気付くことが多く、クラス図とシーケンス図は行き来しながら直します。
5. **状態を持つものはステートマシン図にする** … 注文や予約のように状態が移り変わるものは、状態と、移り変わるきっかけ（イベント）を整理します。「どの状態からはどの操作ができないか」がはっきりし、テストケースの元にもなります。
6. **設計レビューを行う** … 凝集度・結合度の観点で見直します。1つのクラスに関係の薄い処理が集まっていないか（凝集度が弱い）、外部サービスの都合が設計のあちこちに入り込んでいないか（結合度が強い）を確かめます。

### ワークシート: 名詞抽出

| 拾った名詞 | 判断 | 理由 |
| --- | --- | --- |
| 〈要件・ユースケース記述に出てくる名詞〉 | クラス／属性／対象外 | 〈ID を持つか、複数の値をまとめて持つか、システムで扱う必要があるか〉 |

### よくある失敗と対策

| 失敗 | 何が起きるか | 対策 |
| --- | --- | --- |
| 正常な流れだけを設計する | 失敗・取消しのときの動きが決まっておらず、実装者ごとにばらばらになる | ユースケース記述に例外の流れを書き、シーケンス図も主な例外について描く |
| 多重度を片方向からしか考えない | 「1人が複数の予約を持てる」などの条件が漏れ、データベースの設計で困る | 関連ごとに両方向から「いくつか」を問う。0 を許すかも決める |
| 1つのクラスに何でも入れる（「予約管理」クラスがすべてを行う） | 凝集度が弱くなり、変更の影響が読めない | 責任（何を知り、何をするか）ごとにクラスを分ける |
| 外部サービスの呼出しをあちこちに直接書く | 結合度が強くなり、外部サービスの変更や切替えで多くの箇所を直す。テストもしにくい | 外部との接続を1つのインタフェースの後ろに隠す |
| 図を描いて満足し、実装と食い違ったまま放置する | 図が信用されなくなり、誰も見なくなる | 描く図を絞り、変更のたびに更新する図だけを残す |

## 事例

[要件定義](../requirements/) の事例の続きです。架空の企業 **ツバメ情報システム** は、予約 SaaS「ヨヤクル」の **予約金の事前決済** 機能（要件 R-01〜R-07）を設計します。

**① ユースケース**: アクターは「来店客」「店舗スタッフ」と外部システムの「決済代行会社」です。来店客のユースケースは「予約金を支払って予約する」「予約をキャンセルする」、スタッフは「予約金を設定する」「当日の予約を確認する」です。
「予約金を支払って予約する」の例外の流れとして、「カード決済が失敗した」「決済画面で 15 分間操作がなかった」場合を書き、どちらも仮予約を取り消して席を戻すと決めました。

**② 名詞抽出**:

| 拾った名詞 | 判断 | 理由 |
| --- | --- | --- |
| 店舗 | クラス | 店舗 ID を持ち、店名や予約金の設定をまとめて持つ |
| 来店客 | クラス | 会員 ID を持ち、氏名・連絡先を持つ |
| 予約 | クラス | 予約番号を持ち、日時・人数・状態をまとめて持つ |
| 予約金 | クラス（予約金決済） | 金額だけでなく、決済の ID・状態・返金の記録を持つ必要がある |
| キャンセル規定 | クラス | 店ごとに返金の期限と内容を持つ |
| 人数、来店日時 | 予約の属性 | 1つの値で表せる |
| カード番号 | 対象外 | R-06 により自社では保持しない。決済代行会社が扱う |

「来店済」や「キャンセル」の予約に対してキャンセル操作はできない、ということもこの表から読み取れます。これらの行は、そのまま [テスト](../testing/) のテストケースの元になります。

**⑥ 設計レビュー**: 最初の案では、予約サービスの中に決済代行会社 A 社の API の呼出しが直接書かれていました。レビューで「将来、別の決済代行会社に切り替えると予約サービスを大きく直すことになる」「テストのたびに A 社のテスト環境が必要になる」と指摘されました。
そこで「決済ゲートウェイ」というインタフェース（決済する・返金する）を決め、予約サービスはそれだけを呼び出すようにし、A 社用の実装クラスを別に用意しました。同じ「決済する」というメッセージに対して、A 社用・テスト用の実装がそれぞれの振る舞いをする **ポリモーフィズム** の使い方で、予約サービスと決済代行会社の結合度を弱めています。

## 例題

**問** 呼出し元が「処理区分フラグ」を引数で渡し、呼出し先モジュールがその値で処理を切り替えている。このモジュール間の結合は何か。

**解き方** 制御情報（フラグ）を渡して相手の動作を制御しているので **制御結合** です。必要なデータ項目だけを渡すデータ結合に比べて結合度は強くなります。

## 試験対策のポイント

- **ip**: UMLという言葉と、ユースケース図・クラス図・アクティビティ図などが何を表すかを押さえます。
- **fe**: 凝集度・結合度の強弱の順序と具体例、クラス図の多重度の読み取り、汎化と集約の区別が頻出です。
- **ap**: シーケンス図・ステートマシン図の読み取り、オブジェクト指向の概念を設計の場面に当てはめる問題に備えます。
