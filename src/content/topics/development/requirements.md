要件定義は、利用者や経営層の「こうしたい」という要求を整理し、システムが満たすべき条件（要件）として明確にして、関係者で合意する工程です。
ここでの誤りや漏れは後工程ほど修正コストが大きくなるため、開発全体の品質を左右する最上流の作業と位置付けられます。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| 要求と要件 | 要求は利害関係者の「こうしたい」という希望。要件は、そのうち実現すると合意し、システムが満たすべき条件として明確にしたもの |
| 利害関係者（ステークホルダ） | システムの利用者、発注者、運用担当、連携先など、システムに関わり影響を受ける人や組織 |
| 発注者（取得者）と受注者（供給者） | システムを依頼して受け取る側と、開発して納める側。社内開発でも、依頼する部門と開発する部門の関係として考える |
| ベースライン | レビューで承認され、以後の変更を正式な手続で管理する基準となる版（[ソフトウェア開発管理技術](../software-management/) で扱う） |

## 要件の種類

| 種類 | 内容 | 例 |
| --- | --- | --- |
| 業務要件 | 業務上実現すべきこと。業務の流れ、対象範囲、ルール | 「受注から出荷までを翌営業日以内に完了する」 |
| 機能要件 | 業務要件を実現するためにシステムが備える機能 | 受注登録、在庫引当て、出荷指示書の出力 |
| 非機能要件 | 機能以外の品質や制約。性能、信頼性、セキュリティ、移行、運用・保守など | 「画面の応答時間は3秒以内」「稼働率99.9%以上」 |

非機能要件は利用者から明示的に語られにくく、漏れやすいのが特徴です。
IPA の **非機能要求グレード** は、非機能要求を「可用性」「性能・拡張性」「運用・保守性」「移行性」「セキュリティ」「システム環境・エコロジー」の6つの大項目に分けて、発注者と受注者が段階的に合意できるよう整理したものです。

## 要求の獲得と分析

要求は利用者の頭の中や現場の業務にあり、そのままでは曖昧です。次のような手法で引き出し（獲得し）、整理します。

| 手法 | 概要 |
| --- | --- |
| インタビュー（ヒアリング） | 利用者に直接質問する。質問を固定する構造化、大枠だけ決める半構造化、自由に話してもらう非構造化がある |
| アンケート | 多数の利用者から同じ形式で意見を集める |
| 観察（フィールドワーク） | 現場で実際の業務を観察し、利用者が言葉にしない手順や問題を把握する |
| ワークショップ | 関係者が集まり、進行役（ファシリテータ）のもとで要求を出し合う |
| プロトタイプ・モックアップ | 画面などの試作品を見せて要求を具体化し、仕様の漏れを早期に発見する |
| ユースケース / ユーザーストーリー | アクター（利用者）とシステムのやり取りや、「誰が・何のために・何をしたいか」を記述する |

集めた要求は、DFD、E-R 図、UML、決定表（デシジョンテーブル）などで表現して分析し、矛盾や重複、実現可能性を検討します。

### 要件の確認と合意

- 利害関係者（ステークホルダ）ごとに要求の内容や重みが異なるため、優先順位を付けて調整し、**合意・承認** を得ます。
- 要件定義書は取得者（発注者）と供給者（開発者）が **共同レビュー** を行って確定します。
- 要件と設計・テストの対応を **双方向に追跡できる**（トレーサビリティ）ようにしておくと、要件の漏れや変更の影響範囲を確認できます。

## 共通フレーム（SLCP）での位置付け

**共通フレーム**（SLCP-JCF）は、ソフトウェアの企画から開発、運用、保守、廃棄までのライフサイクルで行う作業項目や用語を定義し、発注者と受注者が「同じ言葉」で取引できるようにした枠組みです（国際規格 ISO/IEC 12207 に対応する JIS X 0160 がベース）。
特定の開発モデルや文書の様式を強制するものではなく、プロジェクトに合わせて取捨選択（テーラリング）して使います。

| プロセス | 主な内容 | 主体 |
| --- | --- | --- |
| 企画プロセス | システム化構想の立案、システム化計画の立案 | 取得者（発注者） |
| 要件定義プロセス | 業務要件を中心とした利害関係者の要件を定義し合意する | 取得者（供給者が支援） |
| システム開発プロセス | システム要件定義 → **システム方式設計** → … → システム結合・適格性確認テスト | 供給者 |
| ソフトウェア実装プロセス | ソフトウェア要件定義 → ソフトウェア方式設計 → 詳細設計 → 構築 → テスト | 供給者 |

### システム方式設計との関係

要件定義で決めた「何を実現するか」を受けて、システム要件定義で機能・性能などをシステムの要件として具体化し、
**システム方式設計** で、それらの要件を **ハードウェア・ソフトウェア・手作業（サービス）に振り分け**、システムの構成品目を決定します。
例えば「稼働率99.9%以上」という非機能要件は、方式設計で冗長構成などとして具体化されます。

## 実際の進め方

### 1. 利害関係者を洗い出す

最初に「誰の要求を聞くべきか」を一覧にします。使う人だけでなく、お金を出す人、運用する人、連携先も含めます。抜けた利害関係者の要求は、テストや稼働の直前に「聞いていない」という形で出てきます。

### 2. ヒアリングを準備して行う

- **目的と範囲を一文で伝える**（例: 「無断キャンセルによる損失を減らすための機能を決めたい」）。
- **現状の業務（As-Is）** を先に聞きます。「今はどうしているか」「どこで困っているか」「例外のときはどうしているか」。いきなり「どんな機能がほしいか」と聞くと、相手が思いつく範囲の解決策しか出てきません。
- 質問は大枠だけ決めておき（半構造化インタビュー）、話の流れで深掘りします。「なぜそうしたいのか」を繰り返し聞くと、表面の要望の奥にある本当の目的に近づけます。
- 話を聞くだけでなく、可能なら **現場を観察** します。忙しい時間帯の電話対応のように、言葉にされない手順や問題が見えます。
- 聞いた内容は当日中に議事録にまとめ、相手に確認してもらいます。

### 3. 要求を整理し、優先順位を付ける

集めた要求を1行1件の **要求一覧** にし、出所（誰の要求か）、種類（業務・機能・非機能）、優先度を付けます。
優先度の付け方には、例えば **MoSCoW**（Must: 必須 / Should: できれば / Could: 余裕があれば / Won't: 今回はやらない）があります。「今回はやらない」を明示しておくと、後で範囲がふくらむのを防げます。
重複・矛盾している要求（例: 「すぐ予約を確定したい」と「店が承認してから確定したい」）は、利害関係者に戻して調整します。

### 4. 要件定義書にまとめる

要件定義書の構成は組織によって違いますが、一般的には次のような内容を含みます。

| 章 | 内容 |
| --- | --- |
| 目的・背景 | なぜこのシステム（機能）が必要か、解決したい課題、期待する効果 |
| 範囲 | 対象とする業務・利用者・期間。対象外とするもの |
| 業務要件 | 業務の流れ（To-Be）、業務ルール |
| 機能要件 | 機能の一覧、画面・帳票・外部とのインタフェースの概要、扱うデータ |
| 非機能要件 | 性能、可用性、セキュリティ、運用・保守、移行などの目標値 |
| 制約条件・前提 | 予算、期限、使わなければならない外部サービス、法令 |
| 未決事項 | まだ決まっていないことと、いつ・誰が決めるか |

### 5. ユーザーストーリーと受入れ基準を書く

アジャイル開発では、機能要件を **ユーザーストーリー** で表すことが多くあります。ストーリーだけでは「どこまでできたら完成か」が曖昧なので、必ず **受入れ基準**（Acceptance Criteria）を添えます。
受入れ基準は、テストで合否を判定できる形で書きます。前提・操作・結果を分けて書く **Given（前提）/ When（操作）/ Then（結果）** の形式がよく使われます。

| 良くない受入れ基準 | 良い受入れ基準（確かめられる） |
| --- | --- |
| キャンセルが簡単にできること | Given 予約金を支払った予約がある / When 来店日の前日 23:59 までにキャンセルする / Then 予約金の全額が返金され、確認メールが届く |
| 決済画面がすばやく表示されること | 決済画面は、通常時に 3 秒以内に表示される（測定方法: …） |

「簡単に」「すばやく」「適切に」のような言葉は人によって解釈が違うので、数値や具体的な操作に置き換えます。

### 6. レビューして合意し、追跡できるようにする

要件定義書は発注者と開発者で **共同レビュー** を行い、承認を得ます。承認した版をベースラインとし、以後の変更は [変更管理](../software-management/) の手続で扱います。
要件ごとに ID を付けておけば、設計書やテストケースから「どの要件のためか」をたどれます（トレーサビリティ）。

### ワークシート: 要求一覧

| ID | 要求 | 出所 | 種類 | 優先度 | 受入れ基準・目標値 | 状態 |
| --- | --- | --- | --- | --- | --- | --- |
| R-01 | 〈何をしたいか〉 | 〈誰の要求か〉 | 業務／機能／非機能 | Must / Should / Could / Won't | 〈確かめられる条件〉 | 合意済み／調整中 |

### よくある失敗と対策

| 失敗 | 何が起きるか | 対策 |
| --- | --- | --- |
| 声の大きい人・発注担当者だけに聞く | 実際に使う人の要求が漏れ、稼働後に使われない | 利害関係者を一覧にし、現場の利用者・運用担当にも聞く。観察も行う |
| 「ほしい機能」だけを聞く | 本当の課題とずれた機能を作る | 現状業務と困りごとから聞き、「なぜ」を掘り下げる |
| 非機能要件を決めない | 稼働後に「遅い」「止まると困る」が発覚する | 非機能要求グレードなどのチェックリストで項目ごとに目標値を決める |
| 曖昧な言葉で書く | 受入れテストで合否が判断できず、もめる | 数値・具体的な操作に置き換え、Given/When/Then で書く |
| 例外の流れを聞かない | 正常な流れしか作られず、運用で回らない | 「取消し」「失敗」「期限切れ」のときどうするかを必ず聞く |
| 合意した後の変更を口頭で受ける | 範囲と費用がふくらみ、誰も全体を把握できない | ベースラインを決め、変更は変更管理の手続で影響を評価して承認する |

## 事例

[開発プロセスモデル](../process-models/) の事例の続きです。架空の企業 **ツバメ情報システム** は、予約 SaaS「ヨヤクル」に **予約金の事前決済** 機能を追加します（数値・状況は架空の設定です）。

**① 利害関係者**: 飲食店のオーナー（お金を受け取る・規定を決める）、店舗スタッフ（日々の予約を扱う）、来店客（予約して支払う）、決済代行会社（カード決済を処理する）、自社のサポート担当（問い合わせに答える）、経理（入金を照合する）。

**② ヒアリングと観察**: 協力店3店のオーナーとスタッフに半構造化インタビューを行い、金曜夜の電話予約の様子を観察しました。分かったことは次のとおりです。

- 無断キャンセルは「大人数のコース予約」で特に損失が大きい。少人数の席だけの予約には予約金を求めたくない（客足が遠のくため）。
- 前日までのキャンセルなら料理の仕込みに影響しないので返金してよい。当日のキャンセルは返金しない店が多い。
- 予約金の額は店ごとに違い、1人 1,000〜3,000 円程度を考えている。
- スタッフは忙しい時間に「この予約は支払い済みか」をすぐ確かめたい（観察で、電話を受けながら画面を探す様子が見られた）。

**③ 要求一覧（抜粋）**:

| ID | 要求 | 出所 | 種類 | 優先度 | 受入れ基準・目標値 |
| --- | --- | --- | --- | --- | --- |
| R-01 | 当日キャンセル・無断キャンセルの場合、予約金を店の収入とする | オーナー | 業務 | Must | 店ごとのキャンセル規定として画面に表示し、予約時に来店客の同意を得る |
| R-02 | 店ごとに、予約金を求めるコースと1人あたりの金額を設定する | オーナー | 機能 | Must | 金額は 0〜10,000 円（100 円単位）。0 円は予約金なし |
| R-03 | 来店客が予約と同時に予約金をカードで支払う | 来店客 | 機能 | Must | 予約人数は 1〜20 名。予約金 = 1人あたりの金額 × 人数 |
| R-04 | 来店客が自分で予約をキャンセルし、期限内なら返金を受ける | 来店客 | 機能 | Must | 来店日の前日 23:59 までのキャンセルは全額返金、来店日の 0:00 以降は返金しない |
| R-05 | 当日の予約一覧で支払い状況が一目でわかる | スタッフ | 機能 | Should | 一覧の各行に「支払済／未払い／返金済」を表示する |
| R-06 | カード番号を自社のサーバで保持しない | 自社・決済代行 | 非機能（セキュリティ） | Must | カード情報の入力と処理は決済代行会社の仕組みで行い、自社には決済の結果だけを受け取る |
| R-07 | 決済画面の表示が速い | 来店客 | 非機能（性能） | Must | 金曜 18〜21 時のピーク時でも、決済画面へ進む操作の応答は 3 秒以内 |
| R-08 | 外国語での予約 | 経営企画 | 機能 | Won't（今回） | 次の段階で検討する |

ヒアリングでは「当日の昼までなら返金してほしい店」と「前日までの店」に分かれました。PO とオーナーたちで話し合い、最初の版は「前日 23:59 まで」に統一し、店ごとの期限設定は次の段階で検討することにしました（未決事項に記録）。

**④ ユーザーストーリーと受入れ基準**: R-04 は次のように書きました。

> 来店客として、予約を自分でキャンセルし、期限内なら予約金の返金を受けたい。店に電話しなくても済むからだ。
>
> - Given 予約金を支払った予約がある / When 来店日の前日 23:59 までにキャンセルする / Then 予約金の全額が返金処理され、キャンセルと返金の確認メールが届く
> - Given 予約金を支払った予約がある / When 来店日の 0:00 以降にキャンセルする / Then 「キャンセル規定により返金されません」と表示し、確認したうえでキャンセルできる
> - Given 予約金なしの予約がある / When キャンセルする / Then 返金処理は行わずにキャンセルされる

**⑤ レビューと合意**: 要件定義書を協力店オーナー・サポート・経理と共同レビューし、承認した版をベースラインにしました。経理から「返金が月をまたぐときの扱い」が未記載と指摘され、未決事項に追加しました。
要件 ID（R-01〜R-07）は、このあとの [設計](../design/) と [テスト](../testing/) で、どの要件のための設計・テストかをたどるのに使います。

## 例題

**問** 次の記述を、業務要件・機能要件・非機能要件に分類せよ。

1. 締め日の翌営業日までに請求書を発送する
2. 請求データを CSV 形式で会計システムに連携する
3. 障害発生時は2時間以内に業務を再開できる

**解き方** 1 は業務として実現すべきことなので **業務要件**、2 はシステムが提供する機能なので **機能要件**、3 は可用性（復旧時間）に関する品質なので **非機能要件** です。
「システムが何をするか」が機能要件、「どの程度の品質で動くか」が非機能要件です。

## 試験対策のポイント

- **ip**: 業務要件・機能要件・非機能要件の区別と、要件定義が調達や開発の前に行われることを押さえます。インタビューの3種類（構造化・半構造化・非構造化）も用語として出題されます。
- **fe**: 事例の記述を要件の種類に分類する問題、共通フレームのプロセスと作業の対応、プロトタイプやユースケースなど要求分析手法の特徴が問われます。
- **ap**: 非機能要件の具体化（性能・可用性の目標値の設定）、利害関係者間の要件の調整、トレーサビリティの確保など、要件定義の進め方と品質を問う問題に備えます。
