テストは、作ったソフトウェアが仕様どおりに動くかを確認し、誤り（バグ）を見つけるための活動です。
「どの単位で行うか（テスト工程）」と「どうやってテストケースを作るか（テスト技法）」の2つの軸で整理します。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| テストケース | 1回のテストで行う「前提・入力（操作）・期待結果」の組 |
| 期待結果 | 仕様どおりなら得られるはずの結果。実際の結果と比べて合否を判定する |
| バグ（欠陥、不具合） | プログラムや設計の誤り。テストで期待結果と違う動きとして見つかる |
| モジュール | プログラムを分割した単位（[設計手法とUML](../design/) で扱う） |
| 自動テスト | テストの実行と合否判定をプログラムで行うもの。何度でも同じ手順で繰り返せる |
| CI（継続的インテグレーション） | 変更をまとめるたびに、自動でビルドとテストを行う仕組み（[開発プロセスモデル](../process-models/) で扱う） |

## テスト工程

| 工程 | 対象 | 主な確認内容 | 主に実施する人 |
| --- | --- | --- | --- |
| 単体テスト | モジュール単体 | 内部設計・プログラム設計どおりか | 開発者 |
| 結合テスト | 複数モジュールの組合せ | インタフェースが正しく連携するか | 開発者 |
| システムテスト（総合テスト） | システム全体 | 機能要件、性能・負荷などの非機能要件を満たすか | 開発者側 |
| 受入れテスト（運用テスト） | 納入されたシステム | 業務で使えるか、要件を満たすか | 利用者（発注者） |

### 結合テストの進め方とスタブ・ドライバ

| 方法 | 進め方 | 必要な仮モジュール |
| --- | --- | --- |
| トップダウンテスト | 上位モジュールから順に結合する | **スタブ**（未完成の下位モジュールの代わりに呼び出される） |
| ボトムアップテスト | 下位モジュールから順に結合する | **ドライバ**（未完成の上位モジュールの代わりに呼び出す） |

「スタブは呼ばれる側、ドライバは呼ぶ側」と覚えます。上下両方から進める方法をサンドイッチテストと呼びます。

### 回帰テスト（リグレッションテスト）

プログラムを修正・変更したときに、**変更していない部分に悪影響（デグレード）が出ていないか** を確認するテストです。保守工程や反復型開発で重要になり、自動化されることが多いテストです。

## ブラックボックステスト

内部構造を考えず、**入力と出力（仕様）** に着目してテストケースを作ります。

- **同値分割** … 入力値を、同じ扱いを受けるグループ（同値クラス）に分け、各グループから代表値を選ぶ。有効同値クラスと無効同値クラスの両方を考える。
- **境界値分析** … 同値クラスの境目の値は誤りが起こりやすいため、境界とその前後の値を選ぶ。
- このほか、条件の組合せを表で整理する **デシジョンテーブル（決定表）** も使われます。

## ホワイトボックステスト

プログラムの **内部構造（制御の流れ）** に着目してテストケースを作ります。どこまで網羅するかの基準（網羅率、カバレッジ）が問われます。

| 基準 | 内容 |
| --- | --- |
| 命令網羅 | すべての命令を少なくとも1回実行する |
| 判定条件網羅（分岐網羅） | 各判定の結果（真・偽）を少なくとも1回ずつ実行する |
| 条件網羅 | 判定内の各条件の真・偽を少なくとも1回ずつ実行する |
| 判定条件／条件網羅 | 判定条件網羅と条件網羅を同時に満たす |
| 複数条件網羅 | 判定内の条件の真偽の組合せをすべて実行する |

条件網羅を満たしても判定条件網羅を満たすとは限らない点に注意します（下の例題2）。

## 実際の進め方

### 1. テスト計画を立てる

テストは「思いついた操作を試す」のではなく、計画を立ててから行います。テスト計画には一般に次の内容を書きます。

| 項目 | 内容 |
| --- | --- |
| 対象と範囲 | どの機能・要件をテストするか。テストしないもの（対象外）とその理由 |
| 方針 | どの工程で何を確かめるか、使う技法（同値分割・境界値分析・デシジョンテーブルなど）、自動化する範囲 |
| 環境とデータ | テスト環境、外部サービスのテスト環境やスタブ、テストデータの用意の仕方 |
| 開始基準・終了基準 | テストを始めてよい条件（前工程のテストが終わっている など）と、終えてよい条件（全ケース実施、重大なバグが残っていない など） |
| 体制と日程 | 誰がいつ行うか。バグの報告先と判断する人 |
| リスク | テストが遅れる・不十分になる要因と対策 |

### 2. テストケースを設計する

1. **要件・設計から、入力と条件を書き出す** … 入力項目ごとの有効な範囲、業務ルールの期限、状態の移り変わりなどです。
2. **同値クラスと境界を表にする** … 項目ごとに有効・無効の同値クラスを分け、境界の値を拾います。同じ「有効」でも扱いが変わる値（例: 0 円は「予約金なし」）は別のクラスにします。
3. **条件の組合せはデシジョンテーブルで漏れなく整理する** … 条件が複数あり、組合せで結果が変わるときに使います。
4. **状態があるものは状態ごと・遷移ごとにケースを作る** … 「できるはずの遷移」に加え、「できてはいけない遷移」（来店済の予約をキャンセルするなど）も確かめます。
5. **テストケース表にまとめる** … 1行1ケースで、前提・入力（操作）・**期待結果** を、実施前に書いておきます。期待結果を実施後に書くと、出た結果をそのまま正しいと思い込んでしまいます。

### ワークシート: テストケース表

| ID | 要件 | 観点 | 前提 | 入力・操作 | 期待結果 | 結果 | 実施日・実施者 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| TC-01 | 〈要件 ID〉 | 〈境界値（下限）など〉 | 〈事前の状態〉 | 〈具体的な値・操作〉 | 〈具体的な結果〉 | 合格／不合格 | |

### 3. 実行し、バグ票を書く

テストを実行したら、合否と、実施した環境・プログラムの版を記録します。期待結果と違えば **バグ票**（障害票、不具合報告）を書きます。バグ票は、読んだ人が **同じ現象を再現できる** ように書くことが最も重要です。

| 項目 | 書く内容 |
| --- | --- |
| ID・件名 | 1件1枚。件名だけで現象が分かるように（「キャンセルできない」ではなく「来店日 0:00 ちょうどのキャンセルで全額返金される」） |
| 環境・版 | テスト環境の名前、プログラムの版（ビルド番号・コミット）、ブラウザ・端末 |
| 前提と再現手順 | 番号付きの手順。使ったテストデータ |
| 期待結果と実際の結果 | 両方を並べて書く。画面の写しやログを添付する |
| 再現性 | 毎回起きるか、ときどき起きるか |
| 重要度・優先度 | 重要度は影響の大きさ（お金・データの誤り、業務停止など）、優先度は直す順番。分けて付ける |
| 状態 | 起票 → 修正中 → 修正済み → 確認済み（完了）／却下（仕様どおり など） |

### 4. 修正を確かめ、回帰テストを行い、終了を判定する

修正されたら、まずそのバグが直ったことを確かめ（**確認テスト**、再テスト）、次に修正が他の部分を壊していないかを **回帰テスト** で確かめます。回帰テストは修正のたびに繰り返すので、自動化しておくと効果が大きくなります。
終了判定では、終了基準を満たしたかに加え、**バグの累積件数の推移**（バグ曲線、信頼度成長曲線）を見ます。テストを続けても新しいバグがほとんど見つからなくなり、曲線が横ばいに近づいていれば品質が安定してきたと判断する材料になります。まだ右上がりなら、終了するのは早いと考えます。

### よくある失敗と対策

| 失敗 | 何が起きるか | 対策 |
| --- | --- | --- |
| 正常な値・正常な操作だけを試す | 無効な入力や例外の流れでの不具合が本番で見つかる | 無効同値クラス、例外の流れ、「できてはいけない操作」をケースに入れる |
| 期待結果を「正しく動くこと」と書く | 合否を判定できず、実施者によって判断が分かれる | 具体的な値・表示・データの状態で書く |
| 再現手順のないバグ票 | 開発者が再現できず、「再現せず」で閉じられる | 環境・版・手順・データ・期待結果と実際の結果をそろえる |
| 修正したバグだけ確かめて終える | 修正によるデグレードを見逃す | 回帰テストを行う。自動テストを CI で毎回実行する |
| 日付・時刻が絡むテストを手作業で、その日の時刻で行う | 境界の時刻を試せない、結果が日によって変わる | 現在時刻を外から与えられる設計にし、テストで固定する |
| 見つかったバグの件数だけで品質を判断する | テストが不十分でバグが少ないのか、品質が良いのか区別できない | 消化したケース数・網羅した要件と合わせて、累積件数の推移を見る |

## 事例

[設計](../design/) の事例の続きです。架空の企業 **ツバメ情報システム** は、予約 SaaS「ヨヤクル」の **予約金の事前決済** 機能をテストします（数値・状況は架空の設定です）。

**① テスト計画（要点）**:

| 項目 | 内容 |
| --- | --- |
| 対象 | 要件 R-02（予約金の設定）、R-03（予約と同時の支払い）、R-04（キャンセルと返金）、R-05（支払い状況の表示）。R-07（性能）は別の負荷テストで扱う |
| 方針 | 単体テストと API のテストは自動化し、CI で毎回実行する。決済代行会社は、設計で用意した「決済ゲートウェイ」のテスト用実装（スタブ）で置き換え、最後に決済代行会社のテスト環境でつないで確かめる |
| 環境 | ステージング環境。現在時刻はテストから指定できるようにする |
| 終了基準 | 全テストケースを実施し、重要度「高」のバグが残っていないこと。累積バグ数が横ばいになっていること |

**② 同値クラスと境界**:

| 項目 | 仕様 | 同値クラス | 境界値分析で選ぶ値 |
| --- | --- | --- | --- |
| 予約人数（R-03） | 1〜20 名 | 0 以下（無効）、1〜20（有効）、21 以上（無効） | 0, 1, 20, 21 |
| 1人あたり予約金（R-02） | 0〜10,000 円、100 円単位。0 円は予約金なし | 負の値（無効）、0（有効・予約金なし）、100〜10,000（有効・予約金あり）、10,001 以上（無効）、100 円単位でない値（無効） | −100, 0, 100, 10,000, 10,100、それに 150 |
| キャンセル時刻（R-04） | 来店日の前日 23:59 までは全額返金、来店日の 0:00 以降は返金なし（分単位で扱う） | 前日 23:59 以前（全額返金）、来店日 0:00 以降（返金なし） | 前日 23:59、来店日 0:00 |

予約金の 0 円は「有効」ですが、決済画面に進まないという別の扱いを受けるので、100〜10,000 円とは別のクラスにしました。

**③ デシジョンテーブル（キャンセル）**: 条件の組合せで結果が変わるので表に整理しました（Y: 満たす、N: 満たさない、—: 関係しない、X: 実行する）。

| 条件・動作 | 規則1 | 規則2 | 規則3 | 規則4 |
| --- | --- | --- | --- | --- |
| 予約の状態が「確定」 | Y | Y | Y | N |
| 予約金を支払っている | Y | Y | N | — |
| 前日 23:59 まで | Y | N | — | — |
| 全額返金してキャンセル | X | | | |
| 返金せずにキャンセル（規定を表示して確認） | | X | | |
| 返金処理なしでキャンセル | | | X | |
| キャンセルを受け付けない | | | | X |

**④ テストケース表（抜粋）**: 来店日を 2026-12-18（金）19:00、予約金 1人 3,000 円の店とします。

| ID | 要件 | 観点 | 入力・操作 | 期待結果 |
| --- | --- | --- | --- | --- |
| TC-01 | R-03 | 人数の境界（無効） | 人数 0 で予約 | 「1〜20 名で入力してください」と表示し、予約できない |
| TC-02 | R-03 | 人数の境界（下限） | 人数 1 で予約 | 予約金 3,000 円で決済画面へ進む |
| TC-03 | R-03 | 人数の境界（上限） | 人数 20 で予約 | 予約金 60,000 円で決済画面へ進む |
| TC-04 | R-03 | 人数の境界（無効） | 人数 21 で予約 | 「1〜20 名で入力してください」と表示し、予約できない |
| TC-11 | R-02 | 予約金なし | 予約金 0 円の店で人数 4 で予約 | 決済画面に進まずに予約が確定する |
| TC-13 | R-04 | 期限の境界（内） | 支払い済みの予約を 12-17 23:59 にキャンセル | 12,000 円（4 名分）が全額返金処理され、確認メールが届く |
| TC-14 | R-04 | 期限の境界（外） | 支払い済みの予約を 12-18 0:00 にキャンセル | 「キャンセル規定により返金されません」と表示し、確認後に返金なしでキャンセルされる |
| TC-15 | R-04 | できてはいけない遷移 | 来店済の予約をキャンセル | キャンセルボタンが表示されない。API を直接呼んでもエラーになる |

**⑤ バグ票**: TC-14 で期待結果と違う動きが見つかりました。

| 項目 | 内容 |
| --- | --- |
| 件名 | 来店日 0:00 ちょうどのキャンセルで、予約金が全額返金される |
| 環境・版 | ステージング、ビルド 2026.12.03-2 |
| 再現手順 | 1. 来店日 2026-12-18 19:00、4 名、予約金支払い済みの予約を作る 2. 現在時刻を 2026-12-18 0:00 に設定する 3. 来店客の画面からキャンセルする |
| 期待結果 | 返金されない旨が表示され、返金なしでキャンセルされる（R-04） |
| 実際の結果 | 規定の表示がなく、12,000 円が全額返金処理された |
| 再現性 | 毎回（0:01 では正しく返金なしになる） |
| 重要度・優先度 | 高（店の収入が誤って減る）・高 |

原因は、返金の判定が「キャンセル時刻が来店日の 0:00 **以前**（`<=`）なら返金」となっていたことでした。正しくは「0:00 **より前**（`<`）なら返金」です。境界そのものの値で誤りが出る、境界値分析の典型的な例です。

**⑥ 修正の確認と回帰テスト**: 修正後に TC-13・TC-14 で確認テストを行い、合格しました。この2件を自動テストに加えたうえで、CI で既存の自動テスト全体（回帰テスト）を実行し、ほかの機能に影響がないことを確かめました。
テスト期間の後半には新しいバグがほとんど見つからなくなり、累積バグ数の推移が横ばいに近づいたことと、重要度「高」のバグが残っていないことから、終了基準を満たしたと判断しました。
見つかったバグの件数・修正にかかった時間は、次の [開発管理](../software-management/) で見積りやプロセスの改善に使います。

## 例題

**例題1（同値分割・境界値分析）** 年齢は 0〜120 の整数を有効とする。境界値分析で選ぶテストデータを答えよ。

**解き方** 同値クラスは「0未満（無効）」「0〜120（有効）」「121以上（無効）」の3つです。境界値分析では各境界とその隣の値を選ぶので、**−1, 0, 120, 121** となります。同値分割なら、各クラスから代表値（例: −5, 50, 200）を1つずつ選びます。

**例題2（網羅基準）** `if (A and B) then X` について、テストケース (A, B) = (真, 偽) と (偽, 真) の2件で満たす基準はどれか。

**解き方**

| ケース | A | B | A and B |
| --- | --- | --- | --- |
| 1 | 真 | 偽 | 偽 |
| 2 | 偽 | 真 | 偽 |

A・B それぞれが真と偽を取っているので **条件網羅は満たします**。しかし判定結果はどちらも偽で、真の場合を実行していないため **判定条件網羅は満たしません**。命令 X も実行されないので命令網羅も満たしません。

## 試験対策のポイント

- **ip**: テスト工程の順序と目的、ブラックボックス／ホワイトボックスの違い、回帰テストの意味を押さえます。
- **fe**: 境界値を選ぶ問題、網羅基準ごとに必要な最小テストケース数を考える問題、スタブとドライバの区別が頻出です。
- **ap**: テスト工程と設計工程の対応、テストの進捗管理（バグ曲線など）や、変更時に回帰テストの範囲をどう決めるかといった応用的な観点も問われます。
