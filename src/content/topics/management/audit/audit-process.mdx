システム監査は、**監査計画の策定 → 監査の実施（予備調査・本調査・評価・結論）→ 監査報告 → フォローアップ** という流れで進みます。
ここでは各段階で監査人が何をし、何を残すのか、そして証拠を集めるための **監査技法** を整理します。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| 監査の依頼者 | 監査を依頼し、報告を受ける人。内部監査では経営者（社長など）であることが多い |
| 監査対象部門 | 監査を受ける部門。指摘を受けて改善を実施する |
| 監査手続 | 監査証拠を集めるために監査人が行う具体的な作業（例: 権限の一覧と人事の一覧を突き合わせる） |
| 判断尺度 | 監査対象が適切かどうかを判断する物差し。社内規程やシステム管理基準などから選ぶ（[システム監査基準とシステム管理基準](../audit-standards/) 参照） |
| 母集団とサンプル | 確かめたい記録の全体が母集団、そこから抜き出して調べる一部がサンプル |

## 監査の流れ

<AuditProcessFlow />

### 監査計画

監査人は、有効かつ効率的に監査を行うため、監査の目的・テーマ、対象範囲、方法、実施時期、実施体制、スケジュールなどを決めた **監査計画** を立てます。
監査にかけられる時間や人員には限りがあるので、リスクの大きい領域に重点的に監査資源を配分する **リスクアプローチ** で計画します。

| 計画の種類 | 内容 |
| --- | --- |
| 中長期計画 | 複数年にわたる監査の方針・重点テーマを示す |
| 年度計画 | その年度に実施する監査の対象・時期・体制などを示す |
| 個別監査計画 | 個々の監査ごとに、具体的な監査手続・日程・担当者などを示す |

資料によっては、年度計画を「基本計画」、個別監査計画を「個別計画」と呼ぶこともあります。
計画は固定ではなく、監査の途中で状況が変われば見直します。

### 予備調査と本調査

- **予備調査** … 監査対象の実態を大まかにつかむ段階です。関連する文書の閲覧、アンケート、関係者へのヒアリングなどで業務やシステムの概要と問題になりそうな点を把握し、本調査で実施する **監査手続** を具体的に決めます。
- **本調査** … 予備調査で決めた監査手続を実施し、監査の結論を裏付ける **監査証拠** を入手する段階です。後述の監査技法を使います。

### 評価・結論

入手した監査証拠に基づいて、コントロールが適切に整備・運用されているかを評価し、**監査の結論** を形成します。
結論は、監査人の推測ではなく、**十分かつ適切な監査証拠** に裏付けられていなければなりません。

### 監査報告とフォローアップ

監査人は **監査報告書** を作成し、**監査の依頼者**（経営者など）に報告します。報告書には、監査の目的・範囲、監査の結論のほか、問題点を示す **指摘事項** と、その **改善提案** を記載します。
報告の後は、改善提案や、監査対象部門が作成した **改善計画** への措置が適切かつ適時に実施されているかを確認する **フォローアップ** を行い、結果をフォローアップ報告書にまとめます。

改善を **実施するのは監査対象部門** であり、監査人自身が改善を行うわけではない点が重要です。

## 監査証拠と監査調書

**監査証拠** は、監査人の結論を裏付けるために必要な情報です。例えば次のようなものがあります。

| 監査証拠の例 | 何を確かめるのに使うか |
| --- | --- |
| アクセスログ | 権限のない利用者がアクセスしていないか |
| トランザクションログ | 取引が漏れなく正しく処理されたか |
| 運用・保守の記録 | 手順どおりに運用・変更されているか |
| インシデント報告書 | インシデントが適切に報告・対応されたか |
| 進捗管理資料 | 開発プロジェクトが計画どおり管理されているか |

処理の流れを後から追跡できるようにした記録を **監査証跡** といいます。情報システムは、監査証拠を円滑に入手できるよう、監査証跡を残す仕組みを備えておくことが望まれます。
一方で、監査のためだけの文書作成を開発・運用の現場に求めて負担をかけないよう配慮することも望ましいとされています。

**監査調書** は、監査人が実施した手続、入手した証拠、評価の過程を、結論に至った筋道が分かるように整理して記録した文書です。
監査報告書を作成するときの基礎資料となり、監査結果の裏付けになります。監査人は監査調書を作成し、適切に **保管** します。

## 監査技法

本調査で監査手続を実施するための代表的な技法です。

| 監査技法 | 内容 |
| --- | --- |
| チェックリスト法 | 監査人があらかじめ作成したチェックリストに、監査対象部門などから回答を求める |
| ドキュメントレビュー法 | 文書や記録（規程、設計書、運用記録など）を収集・閲覧して確かめる |
| インタビュー法 | 関係者に直接質問して回答を得る。質問書・調査票を使うこともある |
| ウォークスルー法 | データの発生から入力・処理・出力・活用に至る一連の流れと、そこに組み込まれたコントロールを、書類上または実際に追跡して確かめる |
| 突合・照合法 | 関連する複数の記録を突き合わせる。また、記録された結果を原始資料（伝票など）までさかのぼって突き合わせる |
| 現地調査法 | 監査人が現場に出向き、作業やシステムの状況を自ら観察・調査する |
| 統計的サンプリング | 母集団から統計的な手法で標本を抽出して検証し、その結果から母集団の状態を推定する |

### コンピュータ支援監査技法（CAAT）

大量のデータや、目に見えない処理の中身を検証するには、コンピュータを使った監査技法 **CAAT**（Computer Assisted Audit Techniques）を使います。

| 技法 | 内容 |
| --- | --- |
| 監査ソフトウェア | 汎用の監査ソフトウェアで、データの抽出・集計・比較などを行う |
| データサンプリング・データ分析 | ログなどの大量のデータから標本を抽出したり、傾向や異常値を分析したりする |
| テストデータ法 | 監査人が用意したテストデータを監査対象のプログラムで処理させ、その結果を監査人が想定した結果と比較して、処理の正しさを確かめる |
| 監査モジュール法 | 監査対象のプログラムに監査用のモジュールを組み込み、本番の処理の中で条件に合う取引などを抽出・記録する |
| ペネトレーションテスト法 | 外部からの攻撃者の手口で実際にシステムへの侵入を試み、セキュリティ上の弱点がないかを確かめる |

このほか、過去の試験では次のような技法も出題されています。

| 技法 | 内容 |
| --- | --- |
| ITF法 | 本番のシステムに監査用の架空の口座などを設け、本番データと一緒にテストデータを処理させて結果を確かめる |
| スナップショット法 | プログラムの特定の箇所でその時点のデータを書き出し、処理の途中経過を確かめる |
| 並行シミュレーション法 | 監査人が用意した検証用のプログラムで本番と同じデータを処理し、本番の結果と比較する |

テストデータ法と並行シミュレーション法の違いは、「**データ** を監査人が用意する（プログラムは本番）」か、「**プログラム** を監査人が用意する（データは本番）」かです。

## 実際の進め方

内部監査部門が1年をかけて監査を回す流れを、作る文書とあわせて示します。

1. **年度計画を作る（リスクアプローチ）** … 監査の対象になりうるシステムや業務を一覧にし、影響の大きさ・問題が起きる可能性・前回の監査からの変化（新しい機能、組織変更、外部委託の開始など）で点数を付けて、順位の高いものから年間の対象と時期を決めます。
2. **個別監査計画書を作る** … 監査の目的、範囲（システム・業務・対象期間）、判断尺度（社内規程、システム管理基準など）、主な監査手続、日程、担当者、報告先を書き、監査対象部門に通知します。
3. **予備調査をする** … 資料の提出を依頼し（規程、体制図、システム構成図、権限の一覧、作業の記録、前回の指摘への対応状況など）、担当者にヒアリングします。分かったことから、本調査で確かめる点を **監査手続書**（確かめること・技法・証拠・件数の一覧）にまとめます。
4. **本調査をする** … 監査手続書に沿って証拠を集め、結果を監査調書に記録します。調書には、手続の目的、実施したこと、結果、入手した証拠の保存場所を書き、別の人が読んでも同じ結論にたどり着けるようにします。件数が多いものはサンプルを抽出し、抽出の方法も記録します。
5. **評価して指摘事項をまとめる** … 判断尺度と食い違う点を、次の形で整理するのが一般的です。書いた内容は、報告の前に監査対象部門と事実関係を確認します。
   - **事実（状況）**: 何が、どれだけ起きていたか（件数・割合）
   - **判断尺度（基準）**: 本来どうあるべきか（規程の条項など）
   - **原因**: なぜ食い違いが生じたか
   - **影響（リスク）**: 放置すると何が起こりうるか
   - **改善提案**: 原因に対して何をすべきか
6. **報告する** … 監査報告書を監査の依頼者（経営者など）に提出し、指摘事項ごとに重要度（高・中・低など）を付けます。報告会（講評会）で監査対象部門に説明します。
7. **改善計画を受け取り、フォローアップする** … 監査対象部門が作った改善計画（対策・担当・期限）を受け取り、期限が来たら、記録などの証拠で実施状況を確かめます。口頭の「対応済み」だけで完了にはしません。

### チェックリストの例（アクセス権管理）

チェックリストは、判断尺度の項目ごとに「何を、どの証拠で確かめるか」を書いた表です。予備調査で分かった実態に合わせて、毎回見直します。

| No. | 確かめること | 確かめ方（技法） | 証拠 |
| --- | --- | --- | --- |
| 1 | 権限の付与は、申請と上長の承認に基づいているか | 付与の記録からサンプルを抽出し、申請・承認の記録と突き合わせる（突合・照合法） | 権限申請書、承認の記録 |
| 2 | 退職者・異動者の権限が速やかに削除・変更されているか | 権限保有者の一覧と人事の在籍・所属の一覧を全件突き合わせる（突合・照合法） | 権限一覧、人事の一覧 |
| 3 | 権限の定期的な見直し（棚卸し）が規程どおりの頻度で行われているか | 実施記録を閲覧する（ドキュメントレビュー法） | 棚卸しの記録 |
| 4 | 特権 ID（管理者の権限）の利用は記録され、点検されているか | 操作ログを分析し、点検の記録と照らす（CAAT） | 操作ログ、点検記録 |
| 5 | 大量のデータの持出しが、申請に基づいて行われているか | ダウンロードの記録を抽出し、申請と突き合わせる（CAAT、突合・照合法） | ダウンロードの記録、申請書 |

### よくある失敗と対策

| 失敗 | 対策 |
| --- | --- |
| 毎年同じ対象を同じ手続で監査し、新しいリスクを見落とす | 年度計画の前にリスク評価をやり直し、新しい機能や外部委託など「変化」を必ず点数に入れる |
| チェックリストへの回答（「実施している」）だけで結論を出す | 回答を裏付ける記録・ログなどの証拠を入手する。回答は予備調査の材料と考える |
| 指摘が「規程違反がある」だけで、原因と影響が書かれていない | 事実・判断尺度・原因・影響・改善提案の形で書く。原因に対する提案でなければ再発する |
| サンプルの選び方が恣意的で、結論の範囲が分からない | 抽出の方法と件数を調書に記録し、結論は母集団の範囲に限って述べる |
| 事実関係を確かめずに報告し、監査対象部門と対立する | 報告書の案の段階で事実関係を確認する（監査の結論そのものを相手に合わせて変えるわけではない） |
| 改善計画を受け取って終わり、実施されない | 期限ごとにフォローアップし、未完了の項目は依頼者に報告する |

## 事例

架空の企業 **ツバメ情報システム**（[プロジェクトマネジメントの事例](../../project-management/schedule/) でヨヤクルに事前決済機能を加えた会社）の内部監査室が、ヨヤクルの顧客データの取扱いを監査します。内部監査室は社長直属の2名で、この監査は改善のための助言を目的としています（数値・状況は架空の設定です）。

**① 年度計画**: 監査の対象になりうる領域を 1〜5点で評価しました。

| 対象 | 影響の大きさ | 起こる可能性 | 変化 | 合計 |
| --- | --- | --- | --- | --- |
| ヨヤクル（顧客データとアクセス権） | 5 | 3 | 5 | **13** |
| ケアノート（介護記録） | 5 | 2 | 2 | 9 |
| 受託開発の開発環境 | 3 | 3 | 2 | 8 |
| 社内の会計システム | 4 | 2 | 1 | 7 |

ヨヤクルは飲食店の顧客の氏名・電話番号・来店履歴を預かっており、事前決済の開始で利用者も増えるため、最優先にしました。

**② 個別監査計画**: 目的は「ヨヤクルの顧客データにアクセスできる人が業務上必要な人に限られ、その管理が規程どおりに行われているかを確かめ、改善を提案する」。範囲は本番のデータベースと店舗サポート用の管理画面、対象期間は直近6か月、判断尺度は社内のアクセス管理規程（システム管理基準のアクセス管理に関する項目も参照）です。日程は予備調査 2週、本調査 3週、報告 2週としました。

**③ 予備調査**: 規程、権限の一覧、権限申請の記録を取り寄せ、運用担当者にヒアリングしました。「退職者の権限は人事から連絡があれば削除する」「棚卸しは年1回」という説明でした。規程では棚卸しは半年ごとと定めているため、本調査では上のチェックリストの No.1〜3 と No.5 を手続に選びました。

**④ 本調査の結果**（監査調書に記録）:

| 手続 | 結果 |
| --- | --- |
| No.1 直近6か月の権限付与からサンプル 25件を抽出 | 2件は障害対応で急いだため、承認の記録がなかった |
| No.2 権限保有者 42名を人事の一覧と全件突合 | 退職者 2名のアカウントが有効なまま（退職後 1か月と 3か月）。異動者 1名に元の部署の権限が残っていた。ログを確かめると、退職後のログインはなかった |
| No.3 棚卸しの記録を閲覧 | 前回の棚卸しは 10か月前で、規程の半年ごとを守っていない |
| No.5 顧客データの一括ダウンロード記録（18回）を抽出し、申請と突合 | 15回は月次の統計作業で申請あり。3回は開発者が障害調査のために行ったもので、申請がなかった |

割合で見ると、権限の不備は $\dfrac{3}{42} \fallingdotseq 7.1\%$、承認の記録がない付与は $\dfrac{2}{25} = 8\%$ です。サンプルの結果は、抽出した対象期間の付与の記録についての結論として扱います。

**⑤ 指摘事項**: 退職者・異動者の権限について、次のようにまとめました。

| 要素 | 内容 |
| --- | --- |
| 事実 | 権限保有者 42名のうち 3名（退職者 2名、異動者 1名）に不要な権限が残っていた |
| 判断尺度 | アクセス管理規程「退職・異動の際は速やかに権限を削除・変更する」「半年ごとに棚卸しを行う」 |
| 原因 | 人事から運用担当者への連絡が担当者の判断に任されており、決まった仕組みがない。棚卸しも行われておらず、漏れに気付けなかった |
| 影響 | 退職者のアカウントが悪用されると、顧客の個人情報が漏えいするおそれがある |
| 改善提案 | 人事の退職・異動の情報を毎週運用担当者に連携する手順を決める。棚卸しを規程どおり半年ごとに行い、結果をヨヤクル事業部長が承認する |
| 重要度 | 高 |

ほかに「承認の記録がない権限付与」（重要度 中）、「申請のない一括ダウンロード」（重要度 高）を指摘事項としました。報告書の案はヨヤクル事業部と事実関係を確認したうえで社長に提出し、報告会で説明しました。

**⑥ フォローアップ**: 3か月後、ヨヤクル事業部の改善計画の実施状況を確かめました。退職・異動の情報の連携は、直近 12週分の連携記録と権限の削除記録を突き合わせて実施を確認し、棚卸しも実施記録と事業部長の承認を確認したので「改善済み」としました。一括ダウンロードに承認の手順を組み込む改修は開発中だったため「対応中」とし、次の期限に改めて確認することを社長に報告しました。

## 例題

**問1** 監査対象の業務で作成された出荷伝票と、販売管理システムに記録された出荷データを突き合わせて、入力漏れがないかを確かめた。用いた監査技法はどれか。

- ア インタビュー法
- イ ウォークスルー法
- ウ 突合・照合法
- エ 現地調査法

**解き方** 複数の記録（原始資料である伝票とシステムの記録）を突き合わせているので、正解は **ウ** です。

**問2** システム監査人が監査調書を作成する目的として、最も適切なものはどれか。

- ア 監査対象部門が改善計画を作成するときの手順書とするため
- イ 監査の結論に至った過程を記録し、監査報告書の作成の基礎資料と監査結果の裏付けとするため
- ウ 監査の依頼者に、監査報告書の代わりに提出するため

**解き方** 監査調書は監査人が実施した手続と入手した証拠、評価の過程を記録し、監査意見の根拠とする文書です。正解は **イ** です。

## 試験対策のポイント

- **ip**: 監査の流れ（計画 → 予備調査・本調査 → 評価・結論 → 報告 → フォローアップ）の順番と、監査報告書の提出先（監査の依頼者）を押さえます。
- **fe**: 監査証拠と監査調書の役割、フォローアップで監査人が行うこと（改善状況の確認であり、改善の実施ではない）が問われます。
- **ap**: 状況の説明から監査技法の名前を選ぶ問題が頻出です。特に CAAT のテストデータ法・監査モジュール法・ITF法・並行シミュレーション法は、「何を監査人が用意し、どこで処理するか」で見分けます。リスクアプローチに基づく計画や、どの監査証拠で何を確かめるかも問われます。
