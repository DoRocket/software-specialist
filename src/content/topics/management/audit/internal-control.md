**内部統制** は、組織が業務を健全かつ効率的に進めるために、自ら構築して運用する仕組みです。整備・運用の責任は経営者にあります。
**ITガバナンス** は、取締役会などが IT の利活用のあるべき姿を示し、その実現を方向付ける活動です。どちらも、システム監査が「何を確かめるか」の土台になります。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| コントロール（統制） | リスクを抑えるために業務やシステムに組み込む手続・仕組み（承認、照合、入力チェック、アクセス制限など） |
| 整備と運用 | 整備はコントロールを適切に設計して業務に組み込むこと、運用はそれを実際に継続して行うこと。評価もこの2つに分けて行う |
| 不備 | コントロールがない、設計が足りない、または設計どおりに行われていない状態 |
| 財務報告 | 決算書（財務諸表）など、会社の財政状態や経営成績を外部に報告するもの |

## 内部統制の目的と基本的要素

内部統制を実現するには、**業務プロセスの明確化**、**職務分掌**、**実施ルールの設定**、**チェック体制の確立** が必要です。
金融商品取引法に基づく「財務報告に係る内部統制の評価及び監査の基準」では、内部統制の4つの目的と6つの基本的要素が示されています。

| 4つの目的 | 内容 |
| --- | --- |
| 業務の有効性及び効率性 | 事業活動の目的を達成するため、業務の有効性と効率性を高める |
| 報告の信頼性 | 組織内外への報告（財務報告など）の信頼性を確保する |
| 事業活動に関わる法令等の遵守 | 法令や規範を守る（コンプライアンス） |
| 資産の保全 | 資産の取得・使用・処分が正当な手続・承認の下で行われるようにする |

| 6つの基本的要素 | 内容 | 例 |
| --- | --- | --- |
| 統制環境 | 組織の気風を決め、ほかの要素の基礎となる | 経営者の誠実性・倫理観、経営方針、組織構造、権限と責任 |
| リスクの評価と対応 | 目的の達成を妨げるリスクを識別・分析・評価し、対応を選ぶ | 新システム導入に伴うリスクの洗い出し |
| 統制活動 | 経営者の命令・指示が適切に実行されるための方針と手続 | 承認、職務分掌、照合、記録の保全 |
| 情報と伝達 | 必要な情報が識別・把握・処理され、組織内外に正しく伝わるようにする | 報告ルート、内部通報制度 |
| モニタリング | 内部統制が有効に機能しているかを継続的に評価する | 日常的な点検、内部監査による独立的評価 |
| IT（情報技術）への対応 | 組織の内外の IT に適切に対応する | IT 環境への対応、IT の利用及び IT の統制 |

米国の **COSO**（トレッドウェイ委員会支援組織委員会）が公表した内部統制のフレームワークは、目的を3つ（業務・報告・コンプライアンス）、構成要素を5つ（統制環境・リスク評価・統制活動・情報と伝達・モニタリング活動）としています。
日本の基準はこれに **資産の保全** と **IT への対応** を加えた形です。COSO は、内部統制を全社的なリスク管理に広げた **ERM**（全社的リスクマネジメント）のフレームワークも公表しています。

### 内部統制の限界

内部統制を整備しても、次のような場合には有効に機能しないことがあります。

- 判断の誤り、不注意、**複数の担当者による共謀**
- 当初想定していなかった組織内外の環境の変化や、定型外の取引
- **経営者が不当な目的で内部統制を無視・無効化** する場合
- 費用と便益との比較（費用をかけすぎる統制は採用されない）

## IT への対応と IT 統制

IT への対応は「**IT 環境への対応**」と「**IT の利用及び統制**」に分かれます。IT の統制は、範囲の広さによって次の3つに分けて考えます。

| 区分 | 役割 | 具体例 |
| --- | --- | --- |
| IT 全社的統制 | 全社的な内部統制のうち IT に関するもの。組織全体の IT 統制の方針・体制を決める | IT 戦略・方針の策定、IT に関する規程の整備、IT 部門の組織と責任の明確化、全社的な IT リスクの評価 |
| IT 全般統制 | 業務処理統制が有効に働く **環境（基盤）** を保証する。複数の業務システムに共通する統制 | システムの開発・保守の管理（変更管理）、システムの運用管理、アクセス管理などのセキュリティ確保、外部委託先の管理 |
| IT 業務処理統制 | 個々の業務システムの中で、承認された取引が正しく処理・記録されることを確保する | 入力データの完全性・正確性・正当性のチェック、エラーデータの修正と再処理、マスタデータの維持管理、利用者の認証と操作範囲の限定 |

見分け方の目安は次のとおりです。

- 特定の業務システムの **処理そのもの** に組み込まれている → **業務処理統制**（例: 受注システムで、受注数量が在庫数を超えたら警告する）
- 複数のシステムを支える **開発・運用・保守の仕組み** → **全般統制**（例: 本番環境へのプログラムの移行は、承認を受けた担当者だけが行う）
- **会社全体の方針・体制** → **全社的統制**（例: 取締役会で IT に関する基本方針を決める）

全般統制に不備があると、その上で動く業務処理統制も信頼できなくなります。そのため、監査では全般統制の有効性もあわせて評価します。

## 職務分掌

**職務分掌** は、業務の権限と責任を複数の担当者に分け、1人に集中させないことです。担当者どうしが互いにけん制し合うことで、誤りや不正を防ぎ、見つけやすくします。

| 分ける業務 | ねらい |
| --- | --- |
| 申請と承認 | 自分で申請したものを自分で承認できないようにする |
| 発注と検収 | 架空の発注や、納品されていない物品の支払いを防ぐ |
| 開発と運用 | 開発者が本番環境のプログラムやデータを勝手に変更できないようにする |
| データの入力と、入力結果の照合 | 入力の誤りを別の担当者が発見できるようにする |

## 内部統制報告制度と法令遵守

**内部統制報告制度**（J-SOX と呼ばれることもある）は、金融商品取引法に基づき、上場会社の経営者が財務報告に係る内部統制の有効性を評価して **内部統制報告書** を作成し、それを公認会計士または監査法人が監査する制度です。
また、会社法でも、大会社などの取締役会に対して、業務の適正を確保するための体制（内部統制システム）の整備について決定することを求めています。

業務担当者が自分たちのコントロールを自ら評価する手法を **CSA**（Control Self Assessment：統制自己評価）といいます。法令や社内規程の遵守状況を継続的に評価・改善するための取組の1つです。

## ITガバナンス

ITガバナンスは、コーポレートガバナンス（企業統治）の構成要素の1つで、取締役会などがステークホルダのニーズに基づいて、組織の価値と信頼を高めるために、IT 利活用のあるべき姿を示す IT 戦略と方針を策定し、その実現を方向付ける活動です。
これに対して **IT マネジメント** は、IT 戦略の目標を達成するために、経営者などが IT の利活用に関するコントロールを実行し、その結果を報告する体制を整備・運用する活動です。

IT ガバナンスの国際規格を国内規格にした **JIS Q 38500** では、取締役会などの統治機関が行う3つのタスクを示しています。

| タスク | 内容 |
| --- | --- |
| 評価（Evaluate） | 現在と将来の IT の利用を評価する |
| 指示（Direct） | IT 戦略・方針の策定と実行を指示する |
| モニタ（Monitor） | 方針への適合と、計画に対する実績を監視する |

あわせて、責任・戦略・取得・パフォーマンス・適合・人間行動の6つの原則を示しています。

ITガバナンスを実現する取組には、システム監査、情報セキュリティ監査、ソフトウェア資産管理などがあり、組織の IT 全体に責任を持つ役職として **CIO**（最高情報責任者）、情報セキュリティに責任を持つ役職として **CISO**（最高情報セキュリティ責任者）を置きます。
データの品質や利用のルールを組織として統制する **データガバナンス** も、ITガバナンスと関連する考え方です。

### 関連するフレームワーク

| フレームワーク | 内容 |
| --- | --- |
| COBIT | ISACA が公表している、IT ガバナンスと IT マネジメントのためのフレームワーク。IT に関する目標とプロセスを体系化し、管理の状況を評価する手段を示す |
| 成熟度モデル | プロセスがどの程度確立・改善されているかを段階で評価する考え方。現状と目標の差を把握するのに使う |
| PRM-IT | IT 部門の業務プロセスを体系化したプロセス参照モデル |
| システム管理基準 | 経済産業省が公表している、IT ガバナンスと IT マネジメントの実践規範（詳しくは「システム監査基準とシステム管理基準」） |

## 実際の進め方

内部統制は「業務を見える形にする → リスクを洗い出す → コントロールを対応付ける → 有効かを評価する → 直す」の順に作り、毎年見直します。

1. **対象の業務を決める** … 金額が大きい業務、誤りや不正が起きやすい業務、新しく始めた業務を優先します。
2. **業務を文書にする** … **業務記述書**（誰が、何を、どのシステムで、どの書類・データを使って行うか）と **業務フロー図**（部門ごとの列に作業を並べ、書類・データの流れと承認の位置を示す図）を作ります。
3. **リスクを洗い出す** … 業務の各段階で「何がうまくいかないと、どんな誤り・不正（漏れ・重複・金額の誤り・承認のない処理など）が起きるか」を考えます。
4. **コントロールを対応付ける（RCM）** … リスクごとに、それを抑えるコントロールを書いた表を **RCM（リスク・コントロール・マトリクス）** と呼びます。各コントロールについて、次の点を書きます。
   - **予防的** か（誤りを起こさせない。例: 承認がないと次の処理に進めない）、**発見的** か（起きた誤りを見つける。例: 2つの記録の照合）
   - **手作業** か **IT による統制**（IT 業務処理統制）か。IT による統制は、その前提となる IT 全般統制（変更管理、アクセス管理など）も対応付ける
   - 頻度（取引ごと、日次、月次）、実施者、残る証拠
5. **整備状況を評価する** … コントロールが、設計どおりに行われればリスクを抑えられる作りになっているかを確かめます。1件の取引を最初から最後まで追うウォークスルーがよく使われます。
6. **運用状況を評価する** … 一定の期間、コントロールが実際に行われていたかを、サンプルを抽出して記録で確かめます。件数は、コントロールの頻度とリスクの大きさに応じて社内の方針で決めます。自動化された IT 業務処理統制は、同じ条件なら毎回同じように動くため、IT 全般統制が有効であることを確かめたうえで、少ない件数（例: 条件ごとに1件ずつのテスト）で確かめることが多くあります。
7. **不備を評価して直す** … 設計が足りない **整備上の不備** と、設計どおりに行われていない **運用上の不備** を区別します。ほかのコントロールでリスクが抑えられていないか（補完するコントロール）も確かめ、影響の大きさに応じて是正します。
8. **日常的に点検する** … 業務の担当者自身が定期的に自己点検（CSA）し、内部監査が独立した立場で評価します（モニタリング）。

### よくある失敗と対策

| 失敗 | 対策 |
| --- | --- |
| 業務フロー図がシステムの画面の流れだけで、承認や照合の位置が分からない | 部門ごとの列で作業を並べ、承認・照合・記録の位置を記号で示す |
| リスクが「誤りが起きる」のように抽象的で、コントロールと結び付かない | 「どの段階で、何が、どう誤るか」まで具体的に書く |
| 照合のコントロールに「差異が出たらどうするか」が決まっていない | 許容する差異の範囲、調査の担当、結果の記録を手順に含める |
| 担当者が休むと、月次のコントロールが行われない | 代わりに行う人を決め、実施の記録を残す |
| IT 業務処理統制だけを評価し、プログラムの変更管理を見ていない | IT による統制には、それを支える IT 全般統制を必ず対応付けて評価する |
| 一度作った RCM を更新しない | 業務やシステムが変わったら RCM を見直す。毎年の評価の前に変更点を確かめる |

## 事例

架空の企業 **ツバメ情報システム** は、ヨヤクルに事前決済機能（[プロジェクトマネジメントの事例](../../project-management/schedule/)）を加え、店舗から「事前決済オプション」の料金（月額の基本料と、決済1件あたりの利用料）を受け取るようになりました。カードの代金そのものは決済代行会社 P社 から各店舗に支払われ、ツバメが受け取るのはオプションの料金だけです。
新しく始まった「オプション料金の請求」の業務について、経理部と内部監査室が内部統制を整えて評価します（数値・状況は架空の設定です）。

**① 業務の流れ**: 業務記述書と業務フロー図で、次の流れを整理しました。

| 段階 | 部門 | 作業 | 使う記録 |
| --- | --- | --- | --- |
| 1 | カスタマーサポート | 店舗のオプション申込みを受け、契約マスタに登録する | 申込書、契約マスタ |
| 2 | （システム） | 月末に、店舗ごとの決済件数を集計する（取消された決済は利用料の対象外） | 決済の記録、集計結果 |
| 3 | 経理 | 集計件数を P社 から届く月次の取扱報告の件数と照合する | 集計結果、P社 の取扱報告 |
| 4 | （システム） | 料金マスタから請求額を計算し、請求データを作る | 料金マスタ、請求データ |
| 5 | 経理 | 入金を請求データと照合して消し込み、上長が承認する | 入金明細、消込の記録 |

**② RCM**: 段階ごとのリスクとコントロールを対応付けました。

| No. | リスク | コントロール | 予防／発見 | 手作業／IT | 頻度 |
| --- | --- | --- | --- | --- | --- |
| C1 | 申込みのない店舗が契約マスタに登録され、誤って請求される | 経理担当者が、契約マスタの月中の追加分を申込書と照合する | 発見 | 手作業 | 月次 |
| C2 | 決済件数が重複・漏れて集計される | 集計プログラムは取引 ID の重複を除き、取消済みの決済を対象外にする | 予防 | IT（業務処理統制） | 毎回 |
| C3 | 集計の誤りに気付かない | 集計件数を P社 の取扱報告と照合し、差異を調査して記録する | 発見 | 手作業 | 月次 |
| C4 | 請求額の計算を誤る | 請求額は料金マスタからシステムが自動で計算する | 予防 | IT（業務処理統制） | 毎回 |
| C5 | 入金の消込を誤る、不正に処理する | 消込の担当者と承認者を分け（職務分掌）、上長が承認する | 発見 | 手作業 | 入金ごと |
| C6 | 集計・請求のプログラムが無断で変更され、C2・C4 が正しく動かなくなる | 本番環境への変更は承認された変更要求に基づいて行う（変更管理） | 予防 | IT（全般統制） | 変更ごと |
| C7 | 料金マスタが権限のない人に変更される | 料金マスタの変更権限を経理部の2名に限り、変更ログを経理部長が月次で確認する | 予防・発見 | IT（全般統制）と手作業 | 月次 |

C2・C4 は C6・C7 の全般統制に支えられています。全般統制が働いていないと、プログラムやマスタが書き換えられても気付けないためです。

**③ 整備状況の評価**: ある店舗の6月分の請求を、申込書 → 契約マスタ → 集計 → P社 との照合 → 請求 → 入金の消込まで1件追いました（ウォークスルー）。その結果、C3 の手順に「どの程度の差異なら許容するか」「差異の原因を誰が調べるか」が書かれていないことが分かりました。P社 の報告は締め日の違いで数件ずれることがあり、そのたびに担当者の判断で処理されていました。**整備上の不備** として、許容範囲（締め日の違いによるもので、翌月に解消するもの）と調査の担当を手順に加えました。

**④ 運用状況の評価**: 評価期間の6か月について、次のように確かめました。

| コントロール | 確かめ方 | 結果 |
| --- | --- | --- |
| C3（月次） | 6か月分すべての照合記録を閲覧 | 1か月分（担当者の休暇の月）の記録がなかった |
| C5（入金ごと） | 入金 25件を抽出し、消込と承認の記録を確認 | 25件すべてで、担当者と承認者が別の人で承認の記録があった |
| C2（自動） | 重複・取消を含むテストデータで集計プログラムの動作を確認（テストデータ法） | 重複は除かれ、取消済みは対象外になった |
| C6（全般統制） | 内部監査室の変更管理の監査（[システム監査基準とシステム管理基準](../audit-standards/) の事例）の結果を利用 | 通常の変更は有効。緊急の変更の事後承認に不備があり、改善中 |

C3 で記録がない割合は $\dfrac{1}{6} \fallingdotseq 17\%$ で、**運用上の不備** です。翌月の照合で前月分の差異も確かめていたかを調べましたが、確かめていなかったため、補完するコントロールもありませんでした。対策として、C3 の代わりに行う人（経理部のもう1名）を決め、照合記録を経理部長が月初に確認することにしました。
C6 の緊急変更の不備は、集計プログラムが緊急に変更された場合に C2 の信頼性が下がるおそれがあるため、改善が終わるまで、緊急変更があった月は C3 の照合の差異を経理部長が個別に確認することにしました。

## 例題

**問1** 次の統制のうち、IT 業務処理統制に当たるものはどれか。

- ア 情報システム部門の責任と権限を規程で定める。
- イ 本番環境へのプログラムの移行は、変更の承認を得たうえで運用担当者が行う。
- ウ 経費精算システムで、上長の承認がない申請は支払処理に進まないようにする。
- エ サーバの運用手順書を作成し、手順どおりに運用されているかを点検する。

**解き方** アは全社的統制、イ（変更管理）とエ（運用管理）は複数のシステムを支える全般統制です。ウは特定の業務システムの処理に組み込まれた統制なので、正解は **ウ** です。

**問2** 内部統制における職務分掌の例として、最も適切なものはどれか。

- ア プログラムの開発者が、本番環境に自分でプログラムを移行する。
- イ 購買担当者が発注を行い、別の担当者が納品物の検収を行う。
- ウ 経理担当者が、伝票の入力と入力内容の承認を1人で行う。

**解き方** ア・ウは1人に権限が集中しています。発注と検収を分けているイが正解です。

## 試験対策のポイント

- **ip**: 内部統制の意味（組織が自ら構築・運用する仕組み）、職務分掌、モニタリング、IT ガバナンスの意味と責任者（取締役会など）が問われます。
- **fe**: 6つの基本的要素の名前と内容、IT 全般統制と IT 業務処理統制の区別、内部統制報告制度、JIS Q 38500 の評価・指示・モニタが出題されます。
- **ap**: 具体的な統制が「全社的・全般・業務処理」や「6つの基本的要素」のどれに当たるかを判別する問題、内部統制の限界、COBIT などのフレームワークの位置付けが問われます。
