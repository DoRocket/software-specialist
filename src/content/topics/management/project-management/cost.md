コストの対象群は、プロジェクトに必要なコストを見積もって予算を作り、実績を監視して予算内に収めるためのプロセスです。
ソフトウェアの規模や工数の見積り技法（ファンクションポイント法・COCOMO など）は [ソフトウェア開発管理技術](../../../development/software-management/) で扱ったので、ここではプロジェクト全体の予算の組み立て方と、EVM を使った予測を中心に学びます。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| 工数（人月・人週） | 作業量を「人数 × 期間」で表したもの。1人が1か月でこなす量が 1人月（[資源のマネジメント](../resource/) 参照） |
| 単価 | 要員 1人月（または 1人週）あたりの費用。工数 × 単価 で人件費を見積もる |
| 予備（リザーブ） | 見積りどおりに進まない場合に備えて、見積りとは別に確保しておく予算 |
| EVM の基本指標 | PV（計画価値）・EV（出来高）・AC（実コスト）と、そこから求める SV・CV・SPI・CPI。[プロジェクトマネジメント](../) で説明している |

## コストの対象群のプロセス

| プロセス | 内容 | 主なアウトプット |
| --- | --- | --- |
| コストの見積り | 活動やワークパッケージごとに必要な資源のコストを見積もる | コスト見積り |
| 予算の作成 | 見積りを積み上げ、時間軸に沿って配分した承認済みの予算を作る | 予算（コストベースライン） |
| コストの管理 | 実コストと予算を比べ、差異の原因を分析して是正処置をとる | 実コスト、予想コスト、変更要求 |

## コストの見積り技法

| 技法 | 考え方 | 長所 | 短所 |
| --- | --- | --- | --- |
| 類推見積り | 過去の類似プロジェクトの実績コストを基に、規模や難しさの違いを補正する | 早く、手間が少ない。初期段階で使える | 類似性の判断に頼るため精度は低め |
| パラメトリック見積り | 過去データから得た統計的な関係（単価 × 数量など）で計算する | 根拠となるデータが良ければ精度が高い | 使うモデルや単価が実態に合わないと外れる |
| ボトムアップ見積り | WBS のワークパッケージや活動ごとに見積もり、積み上げる | 精度が高い | 詳細な WBS が必要で、手間がかかる |
| 三点見積り | 楽観値・最可能値・悲観値から期待値を求める | 不確かさを見積りに反映できる | 3つの値を用意する必要がある |

プロジェクトの初期は情報が少ないので類推見積りで概算し、計画が詳しくなるにつれてボトムアップ見積りで精度を上げる、という使い分けが一般的です。
三点見積りの計算方法は [時間のマネジメント](../schedule/) と同じです。

### 例題（パラメトリック見積り）

過去の実績から、画面1本あたりの開発工数は 0.5人月、要員の単価は 1人月あたり 100万円と分かっている。画面 40本のシステムの開発コストを見積もれ。

**解き方** 工数は $40 \times 0.5 = 20$ 人月、コストは $20 \times 100 =$ **2,000万円** です。
「1本あたりの工数」のような係数（パラメータ）が実績から得られていることが前提です。

## 予算の作成とコストベースライン

承認されたコストの計画値を **コストベースライン** といい、EVM の PV（計画価値）の基準になります。
時間軸に沿って累積すると、初めは緩やかに、中盤で急に、終盤でまた緩やかに増える **S字カーブ** になるのが一般的です。

予算は、見積りに **予備（リザーブ）** を加えて段階的に組み立てます。

| 予備 | 備える対象 | 管理する人 |
| --- | --- | --- |
| コンティンジェンシー予備 | 特定済みのリスク（起こるかもしれないと分かっている事象）への対応 | プロジェクトマネージャ。コストベースラインに **含める** |
| マネジメント予備 | 特定されていない、予見できない事象 | 経営層など。コストベースラインに **含めず**、使うには承認が必要 |

$$
\def\arraystretch{2.2}
\begin{array}{ll}
\text{コストベースライン} &{}= \text{ワークパッケージのコスト見積りの合計} + \text{コンティンジェンシー予備} \\
\text{プロジェクト予算} &{}= \text{コストベースライン} + \text{マネジメント予備}
\end{array}
$$

### 例題（予算の構成）

ワークパッケージのコスト見積りの合計が 1,800万円、特定済みリスクに備えるコンティンジェンシー予備が 200万円、マネジメント予備が 100万円である。コストベースラインとプロジェクト予算を求めよ。

**解き方** コストベースラインは $1{,}800 + 200 =$ **2,000万円**、プロジェクト予算は $2{,}000 + 100 =$ **2,100万円** です。
EVM の BAC（完成時総予算）はコストベースラインの総額で、マネジメント予備は含みません。

## コストの管理と EVM による予測

EVM の基本指標（PV・EV・AC、SV・CV、SPI・CPI）は [プロジェクトマネジメント](../) で扱いました。
コストの管理では、現時点の評価にとどまらず、**このまま進むと最終的にいくらかかるか** を予測して手を打ちます。

| 指標 | 意味 |
| --- | --- |
| BAC（完成時総予算） | コストベースラインの総額 |
| EAC（完成時総コスト見積り） | 完成までにかかると予測される総コスト |
| ETC（残作業コスト見積り） | 今から完成までにかかると予測されるコスト（$\text{EAC} - \text{AC}$） |
| VAC（完成時差異） | $\text{BAC} - \text{EAC}$。負なら予算超過の見込み |
| TCPI（残作業効率指数） | 予算内に収めるために、残作業で必要なコスト効率 |

EAC の求め方は、今後の進み方をどう仮定するかで変わります。

| 仮定 | 計算式 |
| --- | --- |
| これまでの差異は一時的で、残作業は当初の予算どおりに進む | $\text{EAC} = \text{AC} + (\text{BAC} - \text{EV})$ |
| 今後も現在のコスト効率（CPI）が続く | $\text{EAC} = \text{AC} + \dfrac{\text{BAC} - \text{EV}}{\text{CPI}} = \dfrac{\text{BAC}}{\text{CPI}}$ |
| 今後はコスト効率とスケジュール効率の両方が影響する | $\text{EAC} = \text{AC} + \dfrac{\text{BAC} - \text{EV}}{\text{CPI} \times \text{SPI}}$ |

残作業の予算 $\text{BAC} - \text{EV}$ を、仮定した効率で割り戻して実コストに換算している、と考えると覚えやすくなります。

### 例題（EAC と TCPI）

BAC が 1,000万円のプロジェクトで、ある時点の PV が 500万円、EV が 400万円、AC が 500万円だった。

1. 今後も現在の CPI が続くとした場合の EAC と VAC を求めよ。
2. 残作業は当初予算どおりに進むとした場合の EAC を求めよ。
3. 予算 1,000万円に収めるために必要な TCPI を求めよ。

**解き方** まず効率指数を求めます。$\text{CPI} = \dfrac{400}{500} = 0.8$、$\text{SPI} = \dfrac{400}{500} = 0.8$ です。

1. $\text{EAC} = \dfrac{1{,}000}{0.8} =$ **1,250万円**、$\text{VAC} = 1{,}000 - 1{,}250 =$ **−250万円**（250万円の超過見込み）
2. $\text{EAC} = 500 + (1{,}000 - 400) =$ **1,100万円**
3. 残作業の予算は $1{,}000 - 400 = 600$ 万円、使える残りの予算は $1{,}000 - 500 = 500$ 万円なので、

$$
\text{TCPI} = \frac{\text{BAC} - \text{EV}}{\text{BAC} - \text{AC}} = \frac{600}{500} = 1.2
$$

これまで 0.8 だったコスト効率を、残作業では **1.2** に上げなければ予算内に収まりません。TCPI が 1 を大きく超える場合、予算どおりの完了は現実的でないと判断し、予算の見直し（変更要求）を検討します。

参考までに、CPI と SPI の両方が影響する仮定では $\text{EAC} = 500 + \dfrac{600}{0.8 \times 0.8} = 500 + 937.5 = 1{,}437.5$ 万円となり、どの仮定を置くかで予測が大きく変わることが分かります。

## 実際の進め方

コストの管理は、見積りを積み上げて予算を作る段階と、毎週（または毎月）実績を集めて EVM で評価する段階に分かれます。

1. **見積りの単位を WBS にそろえる** … ワークパッケージごとに見積もり、合計をプロジェクトの見積りにします。WBS と予算の単位がそろっていないと、後で「どの作業で超過したか」を追えません。
2. **見積りの根拠を残す** … 工数 × 単価、外部の見積書、類似プロジェクトの実績など、数字の出どころを書きます。初期の概算（類推見積り）と詳細な見積り（ボトムアップ見積り）の差も記録しておくと、次の概算の精度が上がります。
3. **予備を分けて積む** … リスク登録簿の EMV などからコンティンジェンシー予備を、組織のルール（例: 見積りの数%）でマネジメント予備を決めます。見積りの中に余裕を隠さず、予備として見える形にします。
4. **時間軸に配分する** … ワークパッケージの予算を、スケジュールに沿って週や月に割り振ります。これを累積したものが PV（計画価値）の曲線です。
5. **出来高（EV）の測り方を先に決める** … 進捗率を担当者の感覚で聞くと EV があいまいになるので、ワークパッケージごとに測り方を決めておきます（下の表）。
6. **実コスト（AC）を集める** … 社内の作業は工数の記録（人週 × 単価）、外部への支払いは請求・検収の記録から集めます。AC と EV の締め日をそろえることが大切です。
7. **指標を計算して差異の原因を分析する** … SV・CV・SPI・CPI、EAC・TCPI を求め、どのワークパッケージで差が出たかを表で確かめます。
8. **対策を決めて報告する** … 差異が組織で決めたしきい値（例: CPI が 0.9 未満）を超えたら、原因と対策、予備を使うかどうかを定例会やステアリングコミッティで報告します。予算そのものを変えるときは変更管理の手続を通します。

### 出来高（EV）の測り方

| 測り方 | 方法 | 向いている作業 |
| --- | --- | --- |
| 0/100 法 | 完了するまで 0%、完了したら 100% | 1〜2週間で終わる小さな作業、外部への委託（検収で完了） |
| 50/50 法 | 開始したら 50%、完了したら 100% | 数週間かかるが、途中の進み具合を測りにくい作業 |
| 重み付けマイルストーン法 | 途中の節目ごとに重みを決めておく（例: 設計書レビュー完了で 40%） | 期間の長い作業 |
| 進捗率（単位数） | 完了の基準を満たした単位の割合（例: 画面 12本中 6本完了で 50%） | 同じ種類の単位が並ぶ作業（画面、テストケース） |
| LOE（作業量に比例しない支援作業） | 期間の経過に合わせて EV を PV と同じ値とする | プロジェクトマネジメント、会議、問合せ対応 |

LOE の作業は EV が PV と常に等しいので、SV は 0 になります。LOE を多く含めると遅れが見えにくくなるため、成果物を作る作業には使いません。

### ワークシート（EVM の状況表）

| ワークパッケージ | 予算 | PV | EV | AC | CV（EV−AC） | 進捗の測り方 | コメント |
| --- | --- | --- | --- | --- | --- | --- | --- |
| （ワークパッケージ名） | | | | | | 0/100 法 など | 差異の原因 |
| 合計 | BAC | | | | | | |

### よくある失敗と対策

| 失敗 | 対策 |
| --- | --- |
| AC と PV だけを比べ、「予算どおりに使っているので順調」と判断する | 必ず EV を測り、EV と比べて SV・CV を出す（AC = PV でも、遅れと超過が同時に起きていることがある） |
| 進捗率を担当者の感覚で聞き、EV が実態より大きくなる | ワークパッケージごとに出来高の測り方と完了の基準を事前に決める |
| 外部への支払いや経費が遅れて計上され、AC が実態より小さく見える | 締め日を決め、まだ請求されていない分も作業の実績から見込んで計上する |
| 見積りに余裕を隠し、どこに予備があるか分からない | コンティンジェンシー予備とマネジメント予備を分けて明示する |
| 要件の追加を変更管理に通さず、少しずつ費用が膨らむ | 追加の要望は変更要求として起票し、費用・期間への影響を見積もってから判断する |
| EAC を1つの仮定だけで報告する | 「差異は一時的」「今の効率が続く」など複数の仮定で幅を示し、どれが現実的かを原因の分析から説明する |

## 事例

[時間のマネジメント](../schedule/) の事例で計画した、ツバメ情報システムの「ヨヤクル事前決済機能」プロジェクトの予算を作り、第8週末の状況を評価します（数値は架空の設定です）。

**① 企画段階の概算（類推見積り）**: 介護記録 SaaS「ケアノート」で請求機能を作ったときの実績は 1,500万円でした。決済代行会社との接続が加わるので規模を 1.2倍と見て、$1{,}500 \times 1.2 = 1{,}800$ 万円と概算し、企画を承認してもらいました。

**② 計画段階の見積り（ボトムアップ見積り）**: WBS のワークパッケージごとに工数を積み上げました。社内の要員の単価は 1人週あたり 20万円（1人月 = 4人週、80万円）としています。
店舗管理画面は K社 に委託するので K社 の見積り（定額 480万円）を使い、自社の実績の係数でも確かめました（パラメトリック見積り）。画面 12本、1本あたり 2人週の実績から $12 \times 2 = 24$ 人週、$24 \times 20 = 480$ 万円で、K社 の見積りは妥当と判断しました。

| ワークパッケージ | 工数 | 見積り |
| --- | --- | --- |
| A 要件定義 | 9人週（3人 × 3週） | 180万円 |
| B 接続申込み・審査 | 4人週（1人 × 4週） | 80万円 |
| C 基本設計 | 9人週（3人 × 3週） | 180万円 |
| D 決済連携の開発 | 12人週（3人 × 4週） | 240万円 |
| E 店舗管理画面（K社 に委託） | — | 480万円 |
| F 結合テスト | 12人週（4人 × 3週） | 240万円 |
| G 受入れテスト・試行 | 6人週（3人 × 2週） | 120万円 |
| プロジェクトマネジメント | 12人週（0.75人 × 16週） | 240万円 |
| 合計 | 64人週 ＋ 委託 | **1,760万円** |

社内分は $64 \times 20 = 1{,}280$ 万円、委託を加えて $1{,}280 + 480 = 1{,}760$ 万円です。概算の 1,800万円との差は小さく、概算の妥当性も確かめられました。

**③ 予備と予算**: [リスク登録簿](../risk/) の EMV の合計 −140万円をもとにコンティンジェンシー予備を 140万円、会社のルールでマネジメント予備を 100万円としました。

$$
\def\arraystretch{2.2}
\begin{array}{ll}
\text{コストベースライン（BAC）} &{}= 1{,}760 + 140 = 1{,}900 \text{ 万円} \\
\text{プロジェクト予算} &{}= 1{,}900 + 100 = 2{,}000 \text{ 万円}
\end{array}
$$

**④ 出来高の測り方**: A〜D と F・G は作業ごとの完了の基準による進捗率、委託の E は検収で完了とする 0/100 法、プロジェクトマネジメントは LOE（EV = PV）としました。

**⑤ 第8週末の状況**: 計画では、第8週末までに A・B・C が終わり、D の4週のうち1週分（$240 \div 4 = 60$ 万円）が進んでいるはずでした。プロジェクトマネジメントは 16週のうち 8週分（$240 \times \dfrac{8}{16} = 120$ 万円）です。

| ワークパッケージ | 予算 | PV | EV | AC | 状況 |
| --- | --- | --- | --- | --- | --- |
| A 要件定義 | 180 | 180 | 180 | 200 | 完了。終盤に「キャンセル料の自動請求」を変更管理を通さずに検討し、1人週超過 |
| B 接続申込み・審査 | 80 | 80 | 40 | 60 | 追加資料の作成中で 50%（リスク R1 が発生） |
| C 基本設計 | 180 | 180 | 180 | 180 | 完了 |
| D 決済連携の開発 | 240 | 60 | 60 | 60 | ファストトラッキングで予定どおり第8週に開始、25% |
| E 店舗管理画面 | 480 | 0 | 0 | 0 | 第7週に開始。検収は第10週の予定（0/100 法） |
| F・G | 360 | 0 | 0 | 0 | 未着手 |
| プロジェクトマネジメント | 240 | 120 | 120 | 120 | LOE |
| 合計（万円） | 1,760 | **620** | **580** | **620** | |

AC と PV がどちらも 620万円なので、AC と PV だけを見ると「計画どおりにお金を使っている」ように見えます。EV と比べると次のとおりです。

$$
\def\arraystretch{2.2}
\begin{array}{ll}
\text{SV} &{}= 580 - 620 = -40 \text{ 万円} \qquad \text{SPI} = \dfrac{580}{620} \fallingdotseq 0.94 \\
\text{CV} &{}= 580 - 620 = -40 \text{ 万円} \qquad \text{CPI} = \dfrac{580}{620} \fallingdotseq 0.94
\end{array}
$$

スケジュールの遅れとコストの超過が同時に起きています。完成時の見込みを2つの仮定で求めました。

$$
\def\arraystretch{2.2}
\begin{array}{ll}
\text{EAC（差異は一時的）} &{}= \text{AC} + (\text{BAC} - \text{EV}) = 620 + (1{,}900 - 580) = 1{,}940 \text{ 万円} \\
\text{EAC（今の CPI が続く）} &{}= \dfrac{\text{BAC}}{\text{CPI}} = 1{,}900 \times \dfrac{620}{580} \fallingdotseq 2{,}031 \text{ 万円} \\
\text{TCPI} &{}= \dfrac{\text{BAC} - \text{EV}}{\text{BAC} - \text{AC}} = \dfrac{1{,}320}{1{,}280} \fallingdotseq 1.03
\end{array}
$$

検算: $1{,}940 - 1{,}900 = 40$ で、これまでの CV（−40万円）がそのまま残る計算と一致します。また $2{,}031 \times \dfrac{580}{620} \fallingdotseq 1{,}900$ で BAC に戻ります。

**⑥ 原因の分析と対策**: BAC にはコンティンジェンシー予備が含まれているので、EAC が BAC を超えるということは、マネジメント予備に手を付けるおそれがあるという意味です。今の効率が続くと EAC はプロジェクト予算の 2,000万円も超えます。

- 差異の原因は、A の要件の追加（20万円）と、B の審査の追加資料（20万円、リスク R1 の発生）で、開発作業そのものの効率が悪いわけではありません。原因を断てば「差異は一時的」の仮定（1,940万円）に近づくと判断しました。
- 「キャンセル料の自動請求」は変更要求として起票し、第2段階に回すことを [ステアリングコミッティ](../communication/) に提案しました。
- 残作業では TCPI 1.03 を目安に、CPI を週次で追います。CPI が 0.94 のまま改善しない場合は、今の CPI が続く仮定で EAC を見直し、マネジメント予備の使用を経営層に相談します。

## 試験対策のポイント

- **fe**: 見積り技法の名前と考え方の対応（特に類推見積りとパラメトリック見積りの区別）、コストベースラインの意味、EVM の指標計算が問われます。EAC は「今後も CPI が続く」場合の $\text{BAC} \div \text{CPI}$ を確実に計算できるようにします。
- **ap**: コンティンジェンシー予備とマネジメント予備の違い（ベースラインに含むか、誰が管理するか）、仮定の違いによる EAC の計算、TCPI から対策を判断する問題が出題されます。
