品質の対象群は、成果物が要求を満たすように品質の基準を決め、作業の進め方と成果物の両面から確かめるためのプロセスです。
調達の対象群は、プロジェクトの外部から製品やサービスを購入するために、調達を計画し、供給者を選んで契約し、契約どおりに進んでいるかを管理するためのプロセスです。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| KLOC | プログラムの規模の単位で、1,000行（Kilo Lines Of Code）。欠陥数などを規模で割って比べるときに使う |
| 欠陥（バグ） | 成果物が要求や仕様を満たしていない箇所。レビューやテストで見つける |
| 受入れテスト | 発注者（または利用部門）が、納品された成果物が要求を満たしているかを確かめるテスト |
| 検収 | 納品物を検査して受け取りを確定すること。支払の条件になることが多い |

## 品質の対象群のプロセス

| プロセス | 内容 | 主なアウトプット |
| --- | --- | --- |
| 品質の計画 | 品質要求事項と品質基準を決め、それを満たす方法を計画する | 品質計画 |
| 品質保証の遂行 | 計画したプロセスどおりに作業が行われているかを、監査やレビューで確かめる | 変更要求、是正処置 |
| 品質管理の遂行 | 成果物を検査・測定し、品質基準を満たしているかを確かめる | 検査報告書、是正処置、予防処置 |

**品質保証** と **品質管理** の違いがよく問われます。

| | 品質保証（QA） | 品質管理（QC） |
| --- | --- | --- |
| 対象 | 作業の **プロセス**（進め方） | 作業の結果である **成果物** |
| 目的 | 品質の問題を作り込まないようにする（予防） | 品質の問題を見つけて取り除く（検出） |
| 例 | 開発標準が守られているかの品質監査、プロセスの改善 | レビューやテストでの欠陥の検出、検査 |

品質管理で集めた測定値（欠陥数、レビュー指摘数など）は、管理図・パレート図などの **データ表現技法** を選んで分析します。各図の使い方は [企業活動と業務分析](../../../strategy/corporate-activities/) の QC七つ道具で扱っています。

### 品質コスト（COQ）

品質に関わるコストは、問題を防ぐための **適合コスト** と、問題が起きたことで生じる **不適合コスト** に分けられます。

| 分類 | コストの種類 | 例 |
| --- | --- | --- |
| 適合コスト | 予防コスト | 教育・訓練、標準類の整備、設計レビュー |
| 適合コスト | 評価コスト | テスト、検査、品質監査 |
| 不適合コスト | 内部失敗コスト | 出荷前に見つかった欠陥の手直し・再テスト |
| 不適合コスト | 外部失敗コスト | 出荷後の障害対応、損害賠償、信用の低下 |

欠陥は後の工程で見つかるほど修正のコストが大きくなるため、予防や早期の評価にコストをかけて、失敗コストを減らすのが基本的な考え方です。
品質を上げるための対策は、かかる費用と得られる効果を比べる **費用便益分析** で採否を判断します。

## 調達の対象群のプロセス

| プロセス | 内容 | 主なアウトプット |
| --- | --- | --- |
| 調達の計画 | 何を外部から調達するか（内製か外部調達かの判断）、どの契約形態にするかを決める | 調達計画、調達作業範囲記述書（SOW） |
| 供給者の選定 | 情報提供・提案・見積りを依頼し、評価して供給者を選び、契約を結ぶ | 選定された供給者リスト、契約書又は注文書 |
| 調達の運営管理 | 供給者が契約どおりに作業しているかを監視し、検収・支払・契約変更を管理する | 変更要求など |

**SOW（調達作業範囲記述書）** は、調達する作業の範囲・成果物・要求事項を供給者に示す文書で、供給者が提案や見積りを作る基になります。
RFI（情報提供依頼書）・RFP（提案依頼書）による供給者選定の流れは [システム戦略とシステム企画](../../../strategy/system-strategy/) で扱っています。

## 契約形態とコスト超過リスク

調達で結ぶ契約は、代金の決め方によって大きく3つに分けられます。どの形態を選ぶかで、**作業が見積りより増えたときのコストを誰が負担するか** が変わります。

| 契約形態 | 代金の決め方 | コスト超過のリスクを負う人 | 向いている場面 |
| --- | --- | --- | --- |
| 定額契約 | 作業全体の代金を契約時に固定する | **売り手**（供給者） | 要求事項やスコープが明確に決まっているとき |
| 実費償還契約 | 実際にかかったコストを支払い、それに利益分の **フィー** を上乗せする | **買い手**（発注者） | 作業範囲が不明確で、事前に見積もりにくいとき |
| タイムアンドマテリアル（T&M）契約 | 作業時間 × 単価 ＋ 材料費で支払う | **買い手**（作業量が増えるほど支払が増える） | 小規模な作業、要員の補強、作業範囲がすぐには決められないとき |

- 定額契約には、目標を上回る成果に報奨を上乗せする **定額インセンティブフィー契約** などの派生形があります。
- 実費償還契約には、フィーを定額にする **実費プラス定額フィー契約**、成果に応じてフィーを変える **実費プラスインセンティブフィー契約** などがあります。
- T&M 契約は、定額契約と実費償還契約の中間的な性質をもちます。支払の膨張を防ぐため、上限額を決めておくことがあります。

### 例題（契約形態ごとの負担の比較）

10人月と見積もった作業を外部に委託する。供給者の原価は 1人月あたり 80万円で、次の3つの契約案がある。実際には作業が 12人月かかった場合、発注者の支払額と供給者の利益はそれぞれいくらか。

- 案1: 定額契約で、代金 900万円
- 案2: 実費償還契約（実費プラス定額フィー）で、フィー 100万円
- 案3: T&M 契約で、単価 1人月あたり 90万円

**解き方** 供給者の実際の原価は $12 \times 80 = 960$ 万円です。

| 案 | 発注者の支払額 | 供給者の利益 |
| --- | --- | --- |
| 案1: 定額 | 900万円（増えない） | $900 - 960 =$ **−60万円**（赤字） |
| 案2: 実費償還 | $960 + 100 =$ **1,060万円** | 100万円（変わらない） |
| 案3: T&M | $12 \times 90 =$ **1,080万円** | $1{,}080 - 960 =$ 120万円 |

見積りどおり 10人月で終わっていれば、支払額はどの案も 900万円（案2は $800 + 100$、案3は $10 \times 90$）で、供給者の利益も 100万円で同じです。
作業が増えたとき、**定額契約では供給者が、実費償還契約と T&M 契約では発注者が** 超過分を負担することが分かります。

このため、発注者から見ると定額契約はコスト超過のリスクを供給者に移す **転嫁**（[リスクのマネジメント](../risk/) 参照）にあたります。ただし、供給者はリスクに備えた分を代金に上乗せしやすく、要求事項があいまいなまま定額契約を結ぶと、仕様の解釈をめぐる争いや品質の低下を招くおそれがあります。

なお、ここでの契約形態は代金の決め方による分類です。仕事の完成を約束するか、作業の遂行を約束するかという法的な契約類型（請負・準委任）は、[法務と知的財産](../../../strategy/legal/) で扱っています。

## 実際の進め方

### 品質: 指標で確かめる

1. **品質目標を、測れる指標と基準値にする** … 「高品質にする」ではなく、レビュー指摘密度・テスト密度・欠陥密度などの指標と、上限・下限のある基準値で決めます。基準値は、自社の過去のプロジェクトの実績から作るのが一般的です。決済の金額のように誤りが許されない部分は、「二重決済 0件」のような個別の目標も置きます。
2. **品質計画を作る** … どの成果物を誰がどの方法でレビュー・テストするか、指標をいつ測るか、工程を終えてよい条件（終了基準）を決めます。
3. **測る** … レビュー記録・テスト記録から、規模（ページ数、KLOC）あたりの件数を計算します。
4. **基準値と比べて原因を考える** … 上限を超えたら作り込みの品質を、**下限を下回ったらレビューやテストの不足** を疑います。件数が少ないことは、品質が良いことの証拠とは限りません。指摘や欠陥を原因別に分類し、パレート図で多いものから手を打ちます。
5. **対策をとる** … 成果物への対策（追加のテスト、再レビュー）と、プロセスへの対策（チェックリストの追加、設計の進め方の見直し）を分けて考えます。後者が品質保証にあたります。
6. **収束を確かめる** … テストの終盤は、新たに見つかる欠陥が減っているか（信頼度成長曲線が平らになっているか）を見て、終了を判断します。

主な指標の計算式は次のとおりです。

$$
\def\arraystretch{2.2}
\begin{array}{ll}
\text{レビュー指摘密度} &{}= \dfrac{\text{レビューの指摘件数}}{\text{レビューした文書のページ数}} \\
\text{テスト密度} &{}= \dfrac{\text{テストケース数}}{\text{プログラムの規模（KLOC）}} \\
\text{欠陥密度} &{}= \dfrac{\text{見つかった欠陥数}}{\text{プログラムの規模（KLOC）}}
\end{array}
$$

ワークシート（品質指標の評価表）の型:

| 指標 | 基準値（下限〜上限） | 実績 | 判定 | 考えられる原因と対策 |
| --- | --- | --- | --- | --- |
| テスト密度 | | | 範囲内／超過／不足 | |
| 欠陥密度 | | | | |

### 調達: 委託先を選んで受け入れる

1. **内製か外部調達かを決める** … 社内の要員とスキル、期間、費用に加え、「その技術やノウハウを社内に残したいか」で判断します。
2. **SOW を書く** … 作業範囲、成果物、納期、前提とする資料、**受入れ基準**、報告の方法、中間レビューの時期、窓口を書きます。受入れ基準があいまいだと、検収のときに争いになります。
3. **候補を探して提案を依頼する** … RFI で情報を集めて候補を絞り、RFP で提案と見積りを依頼します。
4. **評価基準と重みを、提案を受け取る前に決める** … 技術・実績、提案内容、価格、体制・品質管理などの項目と重みを先に決めておくと、価格だけ、印象だけで選ぶことを防げます。
5. **契約を結ぶ** … 契約形態（定額・実費償還・T&M）と、法的な契約類型（請負・準委任）、検収の条件、変更の手続、再委託の可否、機密保持を決めます。
6. **作業を監視する** … 定例会や中間レビューで進捗と品質を確かめます。請負契約では、委託先の要員に発注者が直接作業を指示すると偽装請負になるおそれがあるので、依頼は委託先の責任者を通します。
7. **受け入れて検収する** … 受入れ基準に沿って受入れテストを行い、基準を満たしたら検収して支払います。
8. **評価を記録する** … 品質・納期・対応のよさを記録し、次の調達の参考にします。

ワークシート（供給者の評価表）の型:

| 評価項目 | 重み | A社 | B社 | C社 |
| --- | --- | --- | --- | --- |
| （技術・実績 など） | 合計 100 になるように | 1〜5点 | | |
| 合計（重み × 点数） | | | | |

### よくある失敗と対策

| 失敗 | 対策 |
| --- | --- |
| 欠陥が少ないので品質が良いと判断する | テスト密度やレビュー時間と合わせて見る。下限を下回ったらテスト・レビューの不足を疑う |
| 指標の基準値を他社や一般論の数字から持ってくる | 自社の過去の実績から作り、プロジェクトの特徴（新技術、外部連携の多さ）で補正する |
| 欠陥を直すだけで、同じ種類の欠陥が繰り返し出る | 原因別に分類し、設計やレビューの進め方（プロセス）を直す |
| 受入れ基準を決めずに委託し、検収でもめる | SOW と契約に受入れ基準を書く。中間レビューで早めに認識をそろえる |
| 価格だけで委託先を選ぶ | 評価項目と重みを事前に決め、複数の観点で点数を付ける |
| 請負契約の委託先の要員に、自社の担当者が直接指示する | 窓口を委託先の責任者に決め、依頼は窓口を通す |
| 委託先に任せきりで、納品されて初めて品質が分かる | 中間レビューと進捗報告を契約に入れ、途中の成果物を確かめる |

## 事例

[時間のマネジメント](../schedule/) から続く、ツバメ情報システムの「ヨヤクル事前決済機能」プロジェクトです（数値・状況は架空の設定です）。

**① 内製か外部調達か**: 決済連携（D）は今後の機能追加のためにノウハウを社内に残したいので内製にしました。店舗管理画面（E）は、社内の要員が D に集中していることと、画面開発を得意とする会社があることから、外部に委託することにしました。

**② SOW と供給者の選定**: 基本設計（C）で画面の仕様を固めてから SOW を作り、3社に RFP を出しました。SOW には、対象（店舗管理画面 12本）、成果物（プログラム、画面設計書、テスト結果報告書）、納期（第10週末）、中間レビュー（第8週・第9週）、受入れ基準（受入れテストの全ケース合格、重大な欠陥 0件）、窓口（双方の責任者）を書きました。
評価項目と重みは RFP を出す前に決めておきました。

| 評価項目 | 重み | K社 | L社 | M社 |
| --- | --- | --- | --- | --- |
| 技術・類似の実績 | 30 | 5 | 3 | 4 |
| 提案内容 | 25 | 4 | 3 | 5 |
| 価格 | 25 | 4（480万円） | 5（420万円） | 2（560万円） |
| 体制・品質管理 | 20 | 4 | 3 | 4 |
| 合計 | 100 | **430** | 350 | 375 |

$$
\def\arraystretch{2.2}
\begin{array}{ll}
\text{K社} &{}= 5 \times 30 + 4 \times 25 + 4 \times 25 + 4 \times 20 = 150 + 100 + 100 + 80 = 430 \\
\text{L社} &{}= 3 \times 30 + 3 \times 25 + 5 \times 25 + 3 \times 20 = 90 + 75 + 125 + 60 = 350 \\
\text{M社} &{}= 4 \times 30 + 5 \times 25 + 2 \times 25 + 4 \times 20 = 120 + 125 + 50 + 80 = 375
\end{array}
$$

最も安い L社 ではなく、合計点の高い K社 を選びました。仕様が基本設計で固まっていることから、**定額契約**（請負契約）としました。手直しの費用を K社 が負担するので、[リスク登録簿](../risk/) の R3 の転嫁にあたります。

**③ 中間レビュー（品質保証の観点）**: 基準値は自社の過去の実績から、設計書のレビュー指摘密度を 0.5〜1.5件/ページとしています。

| 回 | ページ数 | 指摘件数 | 指摘密度 | 判定 |
| --- | --- | --- | --- | --- |
| 第1回（第8週） | 40 | 88 | $\dfrac{88}{40} = 2.2$ | 上限超過 |
| 第2回（第9週） | 30 | 27 | $\dfrac{27}{30} = 0.9$ | 範囲内 |

第1回の指摘の多くは「店舗では予約の確認と返金を同じ人が同時に行うことが多い」といった業務の前提の理解不足が原因でした。そこで、K社 の責任者を通してサポート課長による業務の説明会を開き、第2回では基準の範囲に収まりました。

**④ 結合テスト（品質管理の観点）**: 決済連携（D）の規模は 8 KLOC で、基準値はテスト密度 40〜60件/KLOC、結合テストの欠陥密度 2.0〜4.0件/KLOC です。第12週末（結合テストの1週目）の値は次のとおりでした。

$$
\def\arraystretch{2.2}
\begin{array}{ll}
\text{テスト密度} &{}= \dfrac{240}{8} = 30 \text{ 件/KLOC} \\
\text{欠陥密度} &{}= \dfrac{12}{8} = 1.5 \text{ 件/KLOC}
\end{array}
$$

どちらも下限（テスト密度 40、欠陥密度 2.0）を下回っています。欠陥が少ないのは品質が良いからではなく、テストが足りないためと判断しました。テストケースを見直すと正常な流れに偏っており、通信のタイムアウト、同じ予約に対する決済依頼の二重送信、返金の一部取消、P社からの結果通知の遅れなどの異常系が不足していました。
120件を追加して計 360件（$\dfrac{360}{8} = 45$ 件/KLOC）とし、第14週末までの欠陥は計 26件（$\dfrac{26}{8} = 3.25$ 件/KLOC）で、どちらも基準の範囲に入りました。

26件を原因別に分けると、返金処理 11件、タイムアウトの扱い 7件、画面表示 5件、その他 3件で、返金処理とタイムアウトで $\dfrac{11 + 7}{26} \fallingdotseq 69\%$ を占めました（パレート分析）。返金処理の設計を再レビューし、「同じ依頼を2回受けても1回分しか処理しない」ための依頼番号の扱いを設計の標準に追加しました（[トランザクション](../../../database/transaction/) の考え方）。最終週に新たに見つかった欠陥は 0件で、収束を確認してテストを終えました。

**⑤ 受入れと検収**: K社 から第10週末に納品された店舗管理画面を、開発リーダとサポート課長が受入れテスト（60ケース）で確かめたところ、欠陥が 6件見つかり、うち1件は「返金操作の確定ボタンを続けて押すと返金の依頼が2回送られる」という重大なものでした。受入れ基準（重大な欠陥 0件）を満たさないので、契約に基づき K社 の負担で修正してもらい、再テストで全ケースの合格を確かめて第11週に検収しました。
検収の後、K社 の評価（品質・納期・対応）を記録し、次の委託先選定の参考にすることにしました。

## 試験対策のポイント

- **fe**: 品質保証（プロセスを確かめる）と品質管理（成果物を確かめる）の区別、調達の対象群のプロセスの順序、契約形態ごとにコスト超過のリスクを誰が負うかが問われます。
- **ap**: 品質コストの分類（予防・評価・内部失敗・外部失敗）、SOW の役割、状況に合った契約形態の選択（スコープが明確なら定額、不明確なら実費償還など）や、契約形態ごとの支払額の計算が出題されます。
