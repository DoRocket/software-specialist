稼働中のサービスで起きる障害の多くは、ソフトウェアの更新や設定の変更など **何かを変えたとき** に起きます。
そこで、変更を **評価・承認してから実施する**（変更管理）、承認された変更を **確実に本番環境へ届ける**（リリース及び展開管理）、
そして変更の対象となる **構成の情報を正確に保つ**（構成管理）という 3 つのプロセスを組み合わせて、変更によるリスクを抑えます。
後半では、変更要求票の書き方、CAB での審議、リリース判定のチェックリストを、架空の SaaS の機能追加で通して見ます。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| 本番環境（稼働環境） | 利用者が実際に使っているシステム。ここでの失敗はそのままサービスの停止につながる |
| 受入れ試験 | 展開してよいかを確かめるための試験。本番とできるだけ同じ構成の環境で行う |
| 計画停止 | 作業のために、事前に告知してサービスを止めること。時間帯や回数を SLA で決めていることが多い（[サービスレベル管理](../service-level/)） |
| 段階的な展開 | 一部の利用者や拠点から順に展開し、問題がないことを確かめてから範囲を広げる方法。問題が起きても影響を一部にとどめられる |
| 機能フラグ | 設定だけで特定の機能を有効・無効にできる仕組み。プログラムを入れ替えずに機能だけを止める切り戻しに使える |

## 仕組み

### 3 つのプロセスの役割

| プロセス | 目的 | 主なもの |
| --- | --- | --- |
| 変更管理 | 変更の影響・リスクを評価し、**承認された変更だけ** を計画・構築・試験する | 変更要求（RFC）、変更諮問委員会（CAB）、切り戻し計画 |
| リリース及び展開管理 | 試験済みの変更（リリース）を、**稼働環境へ計画どおりに展開** する | リリースの受入れ基準、受入れ試験環境、展開計画 |
| 構成管理 | サービスを構成する要素（構成品目）を識別・記録し、**構成情報を正確に維持** する | 構成品目（CI）、構成管理データベース（CMDB）、版 |

### 変更管理

変更管理は、サービスの追加・廃止を含むすべての変更を、**変更要求（RFC: Request For Change）** として受け付けるところから始まります。

1. **記録・分類**: 変更要求を記録し、変更のカテゴリーを決める
2. **優先度の決定**: 緊急性と影響の大きさから優先度を決める
3. **承認**: リスク、事業上の利益、実現可能性、財務への影響を考慮して、実施するかどうかを決める
4. **計画・構築・試験**: 承認された変更を計画し、開発（構築）して試験する。**失敗したときに元に戻す（又は修正する）手順** も計画し、可能なら試験しておく
5. **展開**: 試験された変更をリリース及び展開管理に渡し、稼働環境に展開する
6. **レビュー**: 変更が目的を果たしたか、問題が起きなかったかを確認する（**変更実施後のレビュー、PIR: Post Implementation Review**）

変更が失敗したときに、変更前の状態へ戻すことを **ロールバック（切り戻し）** といいます。
切り戻しの手順を用意していない変更は、失敗したときにサービスを長時間止めてしまうので、承認の段階で確認します。

影響の大きい変更の可否を審議し、変更の承認者に助言する会議体が **変更諮問委員会（CAB: Change Advisory Board）** です。
業務部門・開発・運用・サービスデスク・供給者など、変更の影響を受ける関係者で構成します。

### 変更のカテゴリー

| カテゴリー | 内容 | 例 |
| --- | --- | --- |
| 標準変更 | リスクが低く、手順が確立していて、**あらかじめ承認されている** 変更。毎回の審議は不要 | 定型の手順による PC のメモリ増設、決まった手順でのアカウント権限の付与 |
| 通常の変更 | 変更要求ごとに評価し、必要に応じて CAB で審議して承認する変更 | 業務システムの機能追加、サーバの OS のバージョンアップ |
| 緊急変更 | 重大な障害の解消やセキュリティ上の脆弱性への対応など、**通常の手順を待てない** 変更。少人数で迅速に評価・承認する | 攻撃に悪用されている脆弱性を修正するプログラムの適用 |

緊急変更でも **承認を省略してよいわけではありません**。評価・承認を迅速化するだけで、記録を残し、実施後のレビューも行います。
シラバスには、このほかに **プロジェクト変更** も変更のカテゴリーの例として挙がっています。

### リリース及び展開管理

**リリース** は、稼働環境に展開するためにまとめた、1 つ以上の変更されたサービスやサービスコンポーネントの集まりです。

| 用語 | 内容 |
| --- | --- |
| リリースの種類 | 計画的にまとめて行うリリースのほか、緊急変更に対応する **緊急リリース** がある |
| リリースの受入れ基準 | 展開してよいかを判断する基準。事前に決めておき、受入れ試験で満たしていることを確認する |
| 受入れ試験環境 | 稼働環境（本番環境）とできるだけ同じ構成で、展開前の試験を行う環境 |
| 稼働環境 | 利用者が実際にサービスを使っている環境 |
| 展開 | リリースを稼働環境に移すこと。全拠点に一斉に行う方法と、一部から段階的に広げる方法がある |

リリースの成功・失敗を監視して分析し、改善の機会を見つけます。リリースの結果や今後のリリース予定は、サービスデスク（問合せ対応の準備）やインシデント管理（リリース直後の障害への備え）にも共有します。

開発と組み合わせた自動化の考え方として、変更を常に稼働環境へリリースできる状態に保つ **継続的デリバリー** と、試験に通った変更を自動的に稼働環境まで展開する **継続的デプロイ** があります。

### 構成管理と CMDB

**構成品目（CI: Configuration Item）** は、サービスを提供するために管理が必要な構成要素です。
ハードウェアやソフトウェアだけでなく、ネットワーク機器、ドキュメント、ライセンスなども CI になり得ます。

| 用語 | 内容 |
| --- | --- |
| 構成識別 | 何を CI として管理するかを決め、識別できるようにする |
| 構成情報 | CI の種類・版（バージョン）・設置場所・所有者・**他の CI との関係** などの情報 |
| CMDB（構成管理データベース） | 構成情報を記録するデータベース（文書化された構成情報の例） |
| 構成ベースライン | ある時点で正式に確認した構成。変更の基準点や、切り戻しの戻り先になる |
| 構成監査 | 定められた間隔で、記録された構成情報と実際の構成が一致しているかを検証する |

構成情報は、他のプロセスの土台になります。
変更管理は CMDB で **CI 間の関係** をたどって変更の影響範囲を評価し、インシデント管理は障害が起きた CI に依存するサービスを把握します。
変更を実施したら構成情報を必ず更新し、実際の構成と食い違わないようにします。

なお、サービスに使われている資産を管理する **資産管理**（IT アセットマネジメント）、特にソフトウェアのライセンスを適正に管理する **ソフトウェアアセットマネジメント（SAM）** も、構成管理と近い関係にあるプロセスです。
ライセンス数を超えたインストールは契約違反になるため、保有ライセンス数と実際の導入数を照合します。

### インシデント管理・問題管理とのつながり

| 流れ | 内容 |
| --- | --- |
| 問題管理 → 変更管理 | 問題管理で特定した根本原因を取り除く修正を、RFC として提出する |
| 変更管理 → リリース及び展開管理 | 承認・試験された変更をリリースとして稼働環境に展開する |
| リリース及び展開管理 → 構成管理 | 展開した結果に合わせて CMDB の構成情報を更新する |
| 変更 → インシデント | 変更が原因でインシデントが起きたら、切り戻しなどで回復し、PIR で原因を振り返る |

## 実際の進め方

### 変更要求票（RFC）に書くこと

変更要求票は、審議する人が「なぜ・何を・どんな危険があり・失敗したらどうするか」を判断できる材料です。一般的な項目の例です。

| 項目 | 書くこと | 審議での確認点 |
| --- | --- | --- |
| 変更番号・申請者・申請日 | 一意の番号と責任者 | 記録として追跡できるか |
| 変更の内容 | 何を、どう変えるか | 範囲が具体的か（「改善」だけでなく対象の機能・設定まで） |
| 理由と期待する効果 | なぜ変えるか（問題管理からの恒久対策、事業上の要求など） | 変えないとどうなるか |
| 対象の構成品目（CI） | 変更するサーバ・プログラム・設定など | CMDB と一致しているか |
| 影響範囲 | CMDB の CI 間の関係からたどった、影響を受けるサービス・利用者・他システム | 見落としている依存先はないか |
| リスクの評価 | 起こりうる失敗と、その起こりやすさ・影響の大きさ | 影響が大きいものに対策があるか |
| 試験の計画と結果 | どの環境で、何を試験したか（性能・移行・切り戻しの試験を含む） | 受入れ基準を満たしているか |
| 実施日時と停止の有無 | 作業時間帯、計画停止の要否と告知の予定 | 利用の少ない時間か、他の変更や繁忙期と重ならないか |
| 作業手順 | 手順書（担当者、確認の箇所） | 第三者が読んで実施できるか |
| 切り戻しの手順と判断基準 | どうやって戻すか、どの状態になったら戻すか、戻すのに何分かかるか | 戻す判断を誰がいつするか決まっているか |
| 承認 | 変更のカテゴリー（標準・通常・緊急）、承認者、承認日 | — |

### CAB での審議

CAB（変更諮問委員会）は、影響の大きい通常の変更について、関係者の立場から危険を洗い出し、承認者に助言します。審議は次の観点で行います。

1. **必要性**: 変更の理由と効果は妥当か。今やるべきか
2. **影響とリスク**: 影響範囲に漏れはないか。失敗したときの影響と、その対策は十分か
3. **準備**: 試験の結果、作業手順、要員、切り戻しの手順と判断基準はそろっているか
4. **日程**: 利用の少ない時間帯か。ほかの変更と重ならないか。繁忙期など **変更を控える期間**（変更凍結期間）を定めている場合は、それに当たらないか
5. **周知**: 利用者への告知、サービスデスクと運用担当への共有の予定はあるか

結論は「承認」「条件付き承認（〇〇の試験結果の提出を条件に）」「差戻し」などとして記録します。

### リリース判定のチェックリスト

展開の直前に、展開してよいかを最終確認するのが **リリース判定**（Go / No-Go 判定とも呼ばれる）です。チェックリストの例です。

| 区分 | 確認すること |
| --- | --- |
| 品質 | 受入れ基準（機能・性能・移行）を試験の結果が満たしている。未解決の不具合があれば、その影響と回避策を承認者が了承している |
| 切り戻し | 切り戻しの手順を試験済みで、判断基準（例: エラー率が何%を超えたら戻す）と所要時間が決まっている |
| 作業 | 手順書のレビューが済み、作業者と確認者、連絡先がそろっている |
| 監視 | 展開後に見る指標（エラー率、応答時間など）と、その正常の範囲が決まっている |
| 周知 | 利用者への告知、サービスデスクへの説明（想定問答）、インシデント管理の当番への共有が済んでいる |
| 記録 | 展開後に CMDB を更新する担当が決まっている |

### よくある失敗と対策

| 失敗 | 対策 |
| --- | --- |
| 「小さな修正だから」と RFC を出さずに本番を直接変え、障害になる | 標準変更として事前承認する範囲を決め、それ以外は必ず RFC を出すルールにする |
| 切り戻し手順を書いたが一度も試しておらず、いざというとき戻せない | 受入れ試験環境で切り戻しも試験し、所要時間を測る |
| 試験環境のデータ量や構成が本番と違い、本番でだけ性能の問題が出る | 本番相当のデータ量・構成での性能試験を受入れ基準に入れる |
| 一斉に展開して、問題が全利用者に広がる | 段階的に展開し、各段階で監視の指標を確かめてから広げる |
| 展開後に CMDB を更新せず、次の変更で影響範囲を見誤る | リリース判定のチェック項目に CMDB の更新を入れ、構成監査で照合する |
| PIR を行わず、同じ失敗を繰り返す | 変更ごとに PIR を行い、変更成功率などの指標で傾向を見る |

## 事例

架空の企業 **ツバメ情報システム** の予約・顧客管理 SaaS **「ヨヤクル」** で、予約時に来店客がクレジットカードで前払いできる **事前決済オプション** をリリースしたときの流れです（数値・状況は架空の設定です）。
直前の 10 月 24 日には、検索機能のリリースが原因で 45 分の停止が起きています（[インシデント管理と問題管理](../incident-problem/) の事例）。その事後レビューで、受入れ基準に本番相当のデータ量での性能試験を加え、新機能は機能フラグで段階的に公開することが決まっていました。

**① 変更要求票（抜粋）**

| 項目 | 内容 |
| --- | --- |
| 変更の内容 | 予約画面に事前決済の画面を追加し、決済代行サービスと連携する。予約の表に決済状態の列を追加する |
| 理由と期待する効果 | 無断キャンセル対策として店舗の要望が多い。事業計画で平均月額を上げる柱の機能 |
| 対象の CI | 予約アプリケーション、予約データベース、決済代行との接続設定 |
| 影響範囲 | 全店の予約受付、店舗管理画面、月次の請求処理（CMDB で、予約の表を参照するシステムとして請求処理が見つかった） |
| リスクと対策 | 決済代行との通信障害で予約できなくなる → 決済に失敗しても予約は仮受付として残す。表の列追加で処理が遅くなる → 本番相当のデータで性能試験 |
| 実施日時 | 11 月 11 日（火）3:00〜5:00 の計画停止の枠で列を追加し、機能は無効のまま展開。その後、機能フラグで段階的に公開 |
| 切り戻しの判断基準 | 決済のエラー率が 1% を超える、又は予約画面の応答時間（95 パーセンタイル値）が 2 秒を超えたら、機能フラグで無効化（5 分以内） |

**② CAB の審議**: 開発・運用・サービスデスク・営業・経理の担当が出席しました。経理から「請求処理が予約の表の新しい列を想定していない」との指摘があり、請求処理の試験を追加することを条件に **条件付き承認** となりました。また、12 月は忘年会シーズンで予約が最も多いため、12 月 1 日から 1 月 5 日までを変更凍結期間とし、それまでに全店への公開を終える日程にしました。

**③ リリース判定（11 月 10 日）**: チェックリストを確認し、本番の 1.2 倍のデータ量での性能試験（応答時間の 95 パーセンタイル値 1.5 秒）、切り戻しの試験（機能フラグの無効化 2 分）、請求処理の試験がすべて合格していることを確かめて **Go** と判定しました。サービスデスクには、想定問答（「事前決済をやめたい」「返金はどうするか」など）を共有しました。

**④ 段階的な展開**

| 段階 | 公開する店舗 | 見た指標 | 結果 |
| --- | --- | --- | --- |
| 1（11 月 12 日） | 希望した 125 店（約 5%） | 決済のエラー率、応答時間 | エラー率 0.3%、問題なし |
| 2（11 月 17 日） | 750 店（約 30%） | 同上と問合せ件数 | 「返金の操作が分からない」問合せが多く、画面の案内を改善 |
| 3（11 月 25 日） | 全店 | 同上 | 問題なし。CMDB を更新 |

**⑤ 変更実施後のレビュー（PIR）**: 1 か月後、事前決済を使い始めた店舗の無断キャンセル率が下がったか、決済が原因のインシデントがなかったかを確認しました。
あわせて、この四半期の変更全体の結果を集計しました。変更 48 件のうち、切り戻しになったものが 2 件、変更が原因のインシデントになったものが 1 件（10 月 24 日の停止）でした。

$$
\text{変更成功率} = \frac{48 - (2 + 1)}{48} = \frac{45}{48} = 93.75\%
$$

次の四半期は、受入れ基準の見直しの効果を、この変更成功率の推移で確かめることにしました。

## 例題

**問1** 稼働中のサーバに、ベンダから提供された修正プログラムを適用することになった。変更管理として最も適切な手順はどれか。

- ア　修正プログラムは提供元が試験済みなので、受け付けた担当者がすぐに稼働環境へ適用する。
- イ　変更要求を記録し、影響範囲とリスクを評価して承認を得たうえで、切り戻し手順を用意し、受入れ試験環境で試験してから適用する。
- ウ　適用後に障害が起きた場合は問題管理で原因を調べればよいので、承認は適用後にまとめて行う。
- エ　障害が発生していないので、修正プログラムは適用せずに記録だけを残す。

**解き方** 変更は記録 → 評価 → 承認 → 計画・試験（切り戻し手順を含む）→ 展開の順に行います。提供元で試験済みでも、自社の環境での影響は評価・試験が必要です。正解は **イ** です。

**問2** 次の説明のうち、構成管理の活動に該当するものはどれか。

- ア　変更の可否を、関係者で構成する会議体で審議する。
- イ　サーバの機種・OS の版・接続しているネットワーク機器との関係を記録し、定期的に実際の構成と照合する。
- ウ　試験済みのプログラムを全拠点の稼働環境に配付する。
- エ　利用者からの問合せを単一の窓口で受け付ける。

**解き方** ア は変更管理（CAB）、ウ はリリース及び展開管理、エ はサービスデスクです。CI とその関係を記録し、構成監査で照合する **イ** が構成管理です。

## 試験対策のポイント

- **ip**: 変更管理・リリース及び展開管理・構成管理の目的の違いと、CMDB が構成情報を管理するデータベースであることを押さえます。
- **fe**: RFC から承認・試験・展開・PIR までの流れ、CAB の役割、標準変更と緊急変更の違い、切り戻し計画の必要性が問われます。事例の活動がどのプロセスに当たるかを選ぶ問題も頻出です。
- **ap**: 変更の影響範囲を CMDB の CI 間の関係で評価する方法、緊急変更でも記録・レビューを省かないこと、リリースの受入れ基準と受入れ試験環境の設定、問題管理・変更管理・リリース及び展開管理・構成管理の連携が問われます。
