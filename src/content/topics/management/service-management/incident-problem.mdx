サービスが止まったとき、まず必要なのは **利用者が業務を再開できるようにすること** です。一方で、同じ障害が何度も起きるなら **原因そのものを取り除く** 必要があります。
この 2 つの目的を別々のプロセスに分けたのが **インシデント管理** と **問題管理** です。両者の違いは、どの試験でも最もよく問われるポイントです。

## 仕組み

### インシデントと問題

| 用語 | 意味 | 例 |
| --- | --- | --- |
| インシデント | サービスに対する **計画外の中断**、サービスの **品質の低下**、又はまだ顧客・利用者へのサービスに影響していない事象 | Web サイトが表示されない、応答が極端に遅い、ディスク使用率が警告値を超えた |
| 問題 | 1 つ以上のインシデントの **原因**（まだ発生していない潜在的なものも含む） | 特定の条件でメモリを使い切るプログラムの不具合 |
| 既知の誤り | **根本原因が特定されている** が、まだ恒久的に解決されていない問題 | 不具合の箇所は判明し、修正版の提供待ち。それまでは再起動で回避できる |
| 回避策（ワークアラウンド） | 根本原因は残したまま、インシデントの影響を減らす又はなくすための一時的な方法 | 待機系への切替え、サービスの再起動、別の手順での入力 |

「まだサービスに影響していない事象」もインシデントに含まれる点に注意します。停止の予兆を早めに扱うことで、実際の停止を防げるからです。

### 目的の違い

| | インシデント管理 | 問題管理 |
| --- | --- | --- |
| 目的 | 中断したサービスを **できるだけ早く回復** させる | インシデントの **根本原因を特定して取り除き**、発生・再発を防ぐ |
| 優先すること | 回避策による迅速な回復（原因の究明は後回しでよい） | 原因の分析と恒久的な対策 |
| 時間の感覚 | 分・時間単位で、解決目標時間までに回復する | 日・週単位で、腰を据えて分析する |
| 起点 | 利用者からの連絡、監視ツールの警告 | インシデントの記録とその傾向の分析 |
| 主な成果 | サービスの回復、インシデントの記録 | 既知の誤りの記録、変更要求（RFC）による恒久対策 |

インシデント管理が「火を消す」役、問題管理が「火元を調べて燃えないようにする」役です。
問題管理は、インシデントが起きた後に対応する（事後的な）だけでなく、インシデントの記録の傾向を分析して **まだ起きていないインシデントを予防する** 活動も含みます。

### インシデント管理の手順

インシデントは、次の順に定められた手順に従って扱います。

1. **記録し、分類する**: 受付日時、連絡者、現象、影響範囲などを記録し、種類（ハードウェア、ソフトウェア、ネットワークなど）で分類する
2. **優先順位付けをする**: **影響**（影響度）と **緊急度** を考慮して優先度を決める
3. **必要であればエスカレーションする**: 自分で解決できない、又は目標時間内に解決できないときに引き継ぐ
4. **解決する**: 回避策などでサービスを回復する
5. **終了する**: 利用者に回復を確認し、記録を完成させて終了（クローズ）する

よく起きるインシデントは、対応手順をあらかじめ定めておくと（**インシデントモデル**）、毎回同じ品質で素早く対応できます。

### 優先度の決め方

**影響度** は「どれだけ多くの利用者・業務に影響するか」、**緊急度** は「どれだけ早く解決しなければならないか」です。
2 つを組み合わせたマトリックスで優先度を決めると、担当者による判断のぶれを防げます。次は一例で、具体的な区分は組織ごとに決めます。

| 影響度 ＼ 緊急度 | 高 | 中 | 低 |
| --- | --- | --- | --- |
| **高**（全社・基幹業務が停止） | 1（最優先） | 2 | 3 |
| **中**（一部の部署に影響） | 2 | 3 | 4 |
| **低**（個人の作業に影響） | 3 | 4 | 5 |

優先度ごとに **解決目標時間** を決めておき（例: 優先度 1 は 2 時間以内）、SLA の回復目標とそろえます。
影響が特に大きいものは **重大なインシデント** として、文書化された特別な手順で管理し、トップマネジメントに通知します。

### エスカレーション

| 種類 | 引き継ぐ先 | 目的 | 例 |
| --- | --- | --- | --- |
| 機能的エスカレーション | より **専門的な知識・技術** を持つ担当（二次サポート・三次サポート、供給者） | 技術的に解決する | サービスデスクで直せないので、ネットワークの専門チームに引き継ぐ |
| 階層的エスカレーション | より **上位の管理者** | 判断・権限・資源の追加を得る | 解決目標時間を超えそうなので、部門長に報告して要員の追加を求める |

機能的エスカレーションは「横（専門家）へ」、階層的エスカレーションは「上（管理者）へ」と覚えます。両方を同時に行うこともあります。

### 問題管理の手順

問題管理も、記録・分類 → 優先順位付け → 必要ならエスカレーション → 可能であれば解決 → 終了 の流れで進めます。中心となるのは **根本原因分析** です。

| 手法・活動 | 内容 |
| --- | --- |
| 傾向分析 | インシデントの記録を集計し、多発している現象や機器を見つける（パレート図で件数の多い順に並べる、など） |
| 根本原因分析 | 「なぜ起きたか」を繰り返し問う（なぜなぜ分析）、特性要因図で原因を整理する、などの方法で真の原因を突き止める |
| 既知の誤りの記録 | 原因は分かったが恒久的に解決できていない場合、影響を減らす処置（回避策）とともに記録し、インシデント管理で使えるようにする |
| 解決策の実施 | 原因を取り除くための修正は、**変更管理** の方針に従って変更要求（RFC）として扱う |
| 予防処置 | 同じ原因によるインシデントが起きないよう、他の同種の機器・システムにも対策を広げる |

問題管理は修正作業を自分で勝手に本番環境へ適用するのではなく、必ず変更管理を通す点が重要です（[変更管理・リリース及び展開管理・構成管理](../change-release/)）。

### サービス要求管理

利用者からの連絡は、障害の報告ばかりではありません。パスワードの再設定、PC の貸出し、アカウントの追加、使い方の問合せなど、**あらかじめ決まった手順で実現できる依頼** を **サービス要求** といい、インシデントとは別に **サービス要求管理** で扱います。
サービス要求も、記録・分類 → 優先順位付け → 実現 → 終了 の流れで処理し、実現の手順を指示書にまとめて担当者が使えるようにします。

| 連絡の内容 | 扱うプロセス |
| --- | --- |
| 「メールが送れなくなった」 | インシデント管理（サービスの中断） |
| 「新しく入った社員のアカウントを作ってほしい」 | サービス要求管理（決まった手順で実現できる依頼） |
| 「同じエラーが毎週月曜日に起きる。原因を調べてほしい」 | 問題管理（根本原因の分析） |
| 「業務システムに新しい機能を追加したい」 | 変更管理（変更要求） |

## 例題

**問1** 次の対応のうち、問題管理の活動に該当するものはどれか。

- ア　利用者からの障害連絡を受け付け、受付番号を付けて記録した。
- イ　サーバが停止したので、待機系に切り替えて業務を再開させた。
- ウ　過去 3 か月のインシデントの記録を分析し、同じ原因による停止が繰り返されていることを突き止めた。
- エ　解決目標時間内に回復できない見込みとなったので、上位の管理者に報告した。

**解き方** ア（記録）、イ（回避策による回復）、エ（階層的エスカレーション）はいずれもインシデント管理の活動です。インシデントの傾向を分析して根本原因を突き止める **ウ** が問題管理です。

**問2** 優先度を上の表で決める組織で、次の 2 件のインシデントが同時に発生した。先に対応すべきものはどちらか。

- A: 全社の受注システムの応答が遅くなっているが、処理は完了している（影響度: 高、緊急度: 中）
- B: 1 人の社員の PC が起動しないが、今日中に提出する資料が入っている（影響度: 低、緊急度: 高）

**解き方** 表から A は優先度 2、B は優先度 3 なので、**A** を先に対応します。B は本人にとっては緊急ですが、影響の範囲が小さいためです。

## 試験対策のポイント

- **ip**: 「迅速な回復」がインシデント管理、「根本原因の究明と再発防止」が問題管理、という対応を事例で選べるようにします。サービスデスクがエスカレーションを行う窓口であることも押さえます。
- **fe**: 優先度が影響度と緊急度で決まること、機能的エスカレーションと階層的エスカレーションの違い、回避策と既知の誤りの意味が問われます。サービス要求とインシデントの区別も出題されます。
- **ap**: インシデントの記録を問題管理に生かす傾向分析、既知の誤りの記録をインシデント対応の迅速化に使う仕組み、問題の解決策を変更管理に引き渡す流れ、重大なインシデントの基準と報告の手順など、プロセス間の連携が問われます。
