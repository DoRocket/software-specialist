ITサービスマネジメントは、情報システムを「サービス」として捉え、利用者と合意した品質で継続的に提供するための管理活動です。
システムを作ることではなく、運用段階でサービスの品質を維持・改善することに重点があります。
このページでは全体像と SLA・主な管理プロセス・サービスデスクの要点をまとめ、各プロセスの詳しい内容と計算問題は下位のトピックで扱います。

## ITIL と関連規格

**ITIL** は、英国政府が取りまとめた ITサービスマネジメントのベストプラクティス集です。現在の版は ITIL 4 です。
ITサービスマネジメントの国際規格としては ISO/IEC 20000 があり、日本では JIS Q 20000 として規格化されています。ITIL は「事例集」、JIS Q 20000 は「要求事項を定めた規格（認証の基準）」という違いがあります。

## サービスマネジメントのプロセス

シラバス（基本情報・応用情報）の「サービスマネジメントシステムの計画及び運用」には、JIS Q 20000 の考え方に沿って次のプロセスが並んでいます。
ITパスポートでは、このうちサービスレベル管理・インシデント管理・問題管理・構成管理・変更管理・リリース及び展開管理・サービス可用性管理・サービス継続管理などの名前と目的が問われます。

| まとまり | プロセス | 何をするか | 詳しく学ぶトピック |
| --- | --- | --- | --- |
| サービスの計画と資産 | サービスの計画、サービスカタログ管理、資産管理、構成管理 | 提供するサービスと、それを支える資産・構成品目を把握する | [変更管理・リリース及び展開管理・構成管理](./change-release/) |
| 顧客・供給者との関係 | 事業関係管理、サービスレベル管理、供給者管理 | 顧客とサービスレベルを合意し、外部の供給者も含めて管理する | [サービスレベル管理と可用性・キャパシティ](./service-level/) |
| 需要と供給 | サービスの予算業務及び会計業務、需要管理、容量・能力管理 | 費用を管理し、将来の需要に見合う能力（キャパシティ）を用意する | [サービスレベル管理と可用性・キャパシティ](./service-level/) |
| 設計・構築・移行 | 変更管理、サービスの設計及び移行、リリース及び展開管理 | 変更を評価・承認し、確実に本番環境へ展開する | [変更管理・リリース及び展開管理・構成管理](./change-release/) |
| 解決と実現 | インシデント管理、サービス要求管理、問題管理 | 中断したサービスを回復し、根本原因を取り除く | [インシデント管理と問題管理](./incident-problem/) |
| サービスの保証 | サービス可用性管理、サービス継続管理、情報セキュリティ管理 | 合意した可用性を守り、災害時にもサービスを継続する | [サービスレベル管理と可用性・キャパシティ](./service-level/)、[サービス継続と事業継続](./continuity/)、[情報セキュリティマネジメント](../../security/management/) |

このほか、日々の運用（システム運用管理・運用オペレーション・サービスデスク）と、データセンタなどの施設・設備を扱う [ファシリティマネジメント](./facility/) もサービスマネジメントの範囲です。

## SLA

**SLA（Service Level Agreement、サービスレベル合意書）** は、サービス提供者と利用者の間で、提供するサービスの内容と品質の目標値を合意した文書です。

| SLA の項目例 | 内容 |
| --- | --- |
| サービス時間 | 平日 9時〜18時、24時間365日 など |
| 可用性（稼働率） | 月間稼働率 99.9% 以上 など |
| 応答時間 | 画面応答 3秒以内 など |
| 障害対応 | 受付から回復までの目標時間 など |

SLA で合意したサービスレベルを維持・改善するために、計画・監視・報告・見直しを繰り返す活動を **SLM（サービスレベル管理）** といいます。

## 主な管理プロセス

| プロセス | 目的 | ポイント |
| --- | --- | --- |
| インシデント管理 | 中断したサービスを **できるだけ早く回復** させる | 根本原因の究明よりも、回避策などによる迅速な復旧を優先する |
| 問題管理 | インシデントの **根本原因** を突き止め、再発を防止する | 原因が判明し回避策がある状態を「既知の誤り」として記録する |
| 変更管理 | 変更による影響やリスクを評価し、承認された変更だけを実施する | 変更の可否を審議する場として CAB（変更諮問委員会）を設けることがある |
| リリース管理及び展開管理 | 承認された変更を本番環境へ確実に展開する | 展開前のテストや切り戻し手順を準備する |
| 構成管理 | サービスを構成する要素（構成品目、CI）の情報を正確に維持する | 構成情報は CMDB（構成管理データベース）で管理する |

インシデント管理と問題管理の違いは最頻出です。例えば「サーバ停止に対して予備機へ切り替えて業務を再開した」のはインシデント管理、「停止の原因となったソフトウェアの不具合を特定して修正を依頼した」のは問題管理です。

## サービスデスク

利用者からの問合せや障害報告を受け付ける **単一の窓口（SPOC: Single Point Of Contact）** です。受け付けた内容を記録し、自ら解決できないものは専門部署へ引き継ぎます（エスカレーション）。

| 形態 | 特徴 |
| --- | --- |
| ローカルサービスデスク | 利用者の拠点ごとに設置する |
| 中央サービスデスク | 1か所に集約して設置する |
| バーチャルサービスデスク | 物理的には分散しているが、通信技術で1つの窓口のように見せる |
| フォロー・ザ・サン | 時差のある複数拠点で引き継ぎ、24時間対応する |

よくある問合せと回答を FAQ として公開し、利用者自身で解決してもらう取組みもサービスデスクの負荷軽減に有効です。

## 例題

**問** SLA で月間稼働率 99.9% 以上と合意した。1か月を30日とすると、許容される停止時間は最大何分か。

**解き方** 1か月の総時間は $30\text{日} \times 24\text{時間} \times 60\text{分} = 43{,}200\text{分}$ です。停止が許されるのは $1 - 0.999 = 0.001$ の割合なので、$43{,}200 \times 0.001 =$ **43.2分** です。

## 試験対策のポイント

- **ip**: SLA・サービスデスク・インシデント管理の意味と、インシデント管理と問題管理の違いを押さえます。
- **fe**: 事例文がどの管理プロセスに該当するかを選ぶ問題や、稼働率から許容停止時間を求める計算が出題されます。
- **ap**: SLA の項目設定、変更管理とリリース管理の役割分担、サービス可用性や容量（キャパシティ）の管理など、運用設計の観点から問われます。
