**ヒューマンインタフェース** は、人とシステムの接点となる部分です。画面の部品の選び方や操作方法、情報の並べ方ひとつで、システムの使いやすさは大きく変わります。
ここでは GUI の部品、使いやすさを表す **ユーザビリティ** と **UX**、誰もが使えることを目指す **アクセシビリティ** と **ユニバーサルデザイン** の考え方を学びます。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| GUI 部品 | ボタン、入力欄、選択肢など、画面を組み立てる部品 |
| タスク | 利用者がシステムを使って達成したいこと（「4名で予約する」など）。ユーザビリティテストでは参加者に実行してもらう課題 |
| コントラスト比 | 文字の色と背景の色の明るさの比。大きいほど読みやすい（最大 21:1） |
| スクリーンリーダー | 画面の内容を音声で読み上げるソフトウェア。目の見えない人や見えにくい人が使う |
| 代替テキスト | 画像の代わりに読み上げられる、画像の内容を表す文章 |

## 仕組み

### GUI の部品

**GUI**（Graphical User Interface）は、アイコンやウィンドウなどの視覚的な表示とマウス・タッチ操作によって、直感的に操作できるインタフェースです。

| 部品 | 特徴・使いどころ |
| --- | --- |
| ラジオボタン | 複数の選択肢から **1 つだけ** 選ぶ（性別、支払方法など） |
| チェックボックス | 複数の選択肢から **いくつでも** 選ぶ / ある項目のオン・オフを切り替える |
| リストボックス | 一覧から選ぶ。選択肢が多いときに使い、スクロールで表示する |
| プルダウンメニュー | クリックすると選択肢が下に開く。画面の場所をとらない（都道府県の選択など） |
| テキストボックス | 自由な文字列を入力する（氏名、住所など） |
| ポップアップメニュー | 右クリックなどで、その場に操作の候補を表示する |
| ツールチップ | マウスポインタを重ねた（ホバー）ときに説明を小さく表示する |
| アコーディオン | 見出しをクリックすると内容が開閉する。FAQ などで情報を折りたたむ |

タッチパネルでは、**タップ**（軽く触れる）、**スワイプ**（なでるように動かす）、**フリック**（素早く払う）、**ピンチ**（2 本の指で拡大・縮小）、**ロングプレス**（長押し）などの操作を組み合わせる **マルチタッチインタフェース** が使われます。
音声で操作する **VUI**（Voice User Interface）や、身振りで操作するジェスチャーインタフェースもあります。

### ユーザビリティと UX

**ユーザビリティ** は「特定の利用者が、特定の利用状況で、目的を達成するために用いる際の、**有効さ・効率・満足度** の度合い」（JIS Z 8521 / ISO 9241-11）と定義される、使いやすさの指標です。
一方、**UX**（User Experience）は、製品やサービスを利用する前後を含めた **体験全体** を指し、使いやすさに加えて楽しさや満足感も含む、より広い概念です。

| 考え方・手法 | 内容 |
| --- | --- |
| 人間中心設計 | 利用者の利用状況を把握し、要求を明確にし、設計案を作って利用者による評価を繰り返す設計プロセス（JIS Z 8530 / ISO 9241-210） |
| UX デザインの五段階モデル | 戦略 → 要件 → 構造 → 骨格 → 表層 の順に、抽象的なものから具体的なものへ設計を進める |
| シグニファイア | 「ここを押せる」「ここを引く」など、適切な操作を利用者に気づかせる手掛かり |

### ユーザビリティ評価

| 手法 | 内容 |
| --- | --- |
| ヒューリスティック評価 | **専門家** が経験則（ヒューリスティクス）に照らして問題点を洗い出す。利用者を集めずに実施できる |
| ユーザビリティテスト | **実際の利用者** にタスクを実行してもらい、その様子を観察して問題点を見つける |
| 思考発話法 | 利用者に、考えていることを声に出しながら操作してもらう |
| 回顧法 | 操作を終えた後に、利用者に操作中の考えを振り返って話してもらう |
| A/B テスト | 2 つの案を利用者に無作為に割り当てて提示し、成果（クリック率など）を比較する |

### アクセシビリティとユニバーサルデザイン

| 用語 | 意味 |
| --- | --- |
| アクセシビリティ | 高齢者や障害のある人を含め、**利用できるかどうか**（情報やサービスへの到達のしやすさ）。日本では JIS X 8341、Web では国際的なガイドライン WCAG がある |
| ユニバーサルデザイン | 年齢・文化・障害の有無・能力の違いにかかわらず、**最初からできる限り多くの人が使えるように** 設計する考え方 |
| バリアフリー | 既存の障壁（バリア）を、特定の人のために **後から取り除く** 考え方 |

ユニバーサルデザインには、「誰でも公平に使える」「使い方が簡単ですぐわかる」「うっかりミスや危険につながりにくい」など **7 原則** があります。
情報システムでは、音声読み上げへの対応、色だけに頼らない表示、操作を取り消せる Undo 機能、意味が一目でわかる **ピクトグラム** の利用などが例です。

### 画面設計と Web デザイン

画面は、入力の流れが自然になるよう項目を並べ、色の使い方や操作方法を統一し、操作ガイダンスを表示するように設計します。
誤った入力を受け付けないために、次のような **入力チェック** を行います。

| チェック | 内容 |
| --- | --- |
| ニューメリックチェック | 数値であるべき項目に数字以外が入っていないか |
| フォーマットチェック | 日付の形式や桁数など、決められた形式どおりか |
| リミットチェック（範囲チェック） | 値が上限・下限の範囲内か（月が 1〜12 など） |
| 組合せチェック | 複数の項目の組合せに矛盾がないか（2 月 30 日がないか など） |
| 照合チェック | マスタファイルなどに登録されたデータと一致するか |
| チェックディジット（チェックキャラクター） | コードに付けた検査用の数字で、入力ミスを検出する |

Web デザインでは、**CSS**（スタイルシート）でサイト全体のデザインを統一し、複数の Web ブラウザで同じように表示されること（クロスブラウザ）に配慮します。
画面の幅に応じてレイアウトを自動的に切り替える **レスポンシブ Web デザイン**（CSS の **メディアクエリ** で実現する）や、スマートフォンでの表示を優先して設計する **モバイルファースト** が一般的です。

## 実際の進め方

### ユーザビリティテストの進め方

1. **目的と対象を決める** … 「予約完了までの迷いを減らしたい」のように、何を確かめるかを一文にします。完成品でなくても、紙や画像をつなげた試作品（プロトタイプ）でテストできます。早い段階ほど直す費用が小さくなります。
2. **タスクを作る** … 「12月18日の金曜19時に、4名でコースを予約して予約金を払ってください」のように、具体的な場面として渡します。「予約ボタンを押して」のように操作の答えになる言葉（画面上のラベル）は使いません。
3. **参加者を集める** … 想定する利用者に近い人を選びます。開発者や社内の詳しい人では、つまずきが見つかりません。少人数（5人程度）でも主な問題の多くが見つかるとよく言われ、少人数で「テスト → 改善 → テスト」を繰り返すやり方が一般的です。
4. **実施する** … 参加者に思考発話法で操作してもらい、進行役は **操作を助けず** に観察します（「どうすればいいですか」と聞かれたら「どうすると思いますか」と返す）。記録係が、つまずいた場面・発言・時間を記録します。
5. **測る** … ユーザビリティの3つの観点に合わせて測ります。

| 観点 | 指標の例 |
| --- | --- |
| 有効さ | タスクの達成率（助けなしで最後までできた人の割合）、誤操作の回数 |
| 効率 | タスクにかかった時間、画面の遷移数・タップ数 |
| 満足度 | テスト後のアンケート（5段階評価など）、インタビューでの感想 |

6. **問題を整理し、重大度を付けて直す** … 同じ問題を何人が経験したか、タスクの達成を妨げたかで重大度（高・中・低）を付け、高いものから直します。直したら再びテストして、改善したかを同じ指標で確かめます。

### ワークシート: 観察記録

| 参加者 | タスク | 達成 | 時間 | つまずいた場面 | 発言・様子 | 問題 ID |
| --- | --- | --- | --- | --- | --- | --- |
| P1 | T1 | ○ ／ × ／ 助けありで○ | 〈分:秒〉 | 〈画面と操作〉 | 〈そのまま書き取る〉 | 〈まとめた問題の番号〉 |

### アクセシビリティの確認

Web のアクセシビリティは、国際的なガイドライン **WCAG** の達成基準（日本の JIS X 8341-3:2016 は WCAG 2.0 と一致する内容）に照らして確認します。よく確認される観点は次のとおりです。

| 観点 | 確認すること |
| --- | --- |
| 代替テキスト | 意味のある画像に、内容を表す代替テキストがあるか。飾りの画像は読み上げられないようにしているか |
| 色のコントラスト | 文字と背景のコントラスト比が十分か。WCAG 2 のレベル AA では、通常の文字で 4.5:1 以上、大きな文字で 3:1 以上 |
| 色だけに頼らない | 必須項目や誤りを、赤色だけでなく文字や記号でも示しているか |
| キーボード操作 | マウスを使わずにキーボードだけで全操作ができ、いまどこを操作しているか（フォーカス）が見えるか |
| フォーム | 入力欄に見出し（ラベル）が結び付いているか。誤りの内容と直し方を文字で示しているか |
| 拡大 | 文字を 200% に拡大しても、内容が欠けたり重なったりしないか |
| 時間制限 | 時間制限がある場合、事前に知らせ、延長できるか |
| 読み上げ | スクリーンリーダー（画面読み上げソフト）で、見出し・ボタン・表が意味の通る順で読み上げられるか |

自動チェックツールは、コントラスト比や代替テキストの有無など機械的に判定できる項目を素早く見つけられますが、「代替テキストの内容が適切か」「読み上げの順序で意味が通るか」は人が確かめる必要があります。自動チェックと人による確認を組み合わせます。

### よくある失敗と対策

| 失敗 | 何が起きるか | 対策 |
| --- | --- | --- |
| 開発者や社内の人だけで使いやすさを判断する | 操作に慣れているため、初めての利用者のつまずきが見えない | 想定利用者に近い人でユーザビリティテストを行う |
| テスト中に進行役が操作を教えてしまう | 本当は解決できなかった問題が「達成」に数えられる | 助けずに観察し、助けた場合は「助けありで達成」と記録する |
| 参加者の要望（「ボタンを大きく」）をそのまま仕様にする | 原因に合わない対策になる | 発言ではなく行動（どこで何に迷ったか）から原因を考える |
| 完成直前に一度だけテストする | 大きな問題が見つかっても直す時間がない | 試作品の段階から小さく何度も行う |
| アクセシビリティを最後にまとめて対応する | 色や画面構成の作り直しが必要になる | デザインの段階でコントラストや色の使い方を決め、部品ごとに確認する |
| 自動チェックツールの結果だけで「対応済み」とする | 読み上げで意味が通らないなどの問題が残る | キーボード操作やスクリーンリーダーで人が確認する |

## 事例

[開発プロセスモデル](../../development/process-models/) の事例で、架空の企業 **ツバメ情報システム** の予約 SaaS「ヨヤクル」に、来店客が予約時に予約金を支払う機能が加わりました。スプリントレビューで店から「予約金の額が分かりにくい」という意見が出たため、来店客向けのスマートフォンの予約画面でユーザビリティテストを行いました（数値・状況は架空の設定です）。

**① 目的とタスク**: 目的は「予約金付きの予約を、迷わず完了できるようにする」。タスクは T1「12月18日の金曜19時に、4名でコースを予約して予約金を払ってください」、T2「その予約を取り消してください」の2つです（カード決済はテスト用の環境を使用）。

**② 参加者と実施**: 普段スマートフォンで飲食店を予約する 20〜60 代の 5 名に、1人 30 分で思考発話法により操作してもらいました。進行役1名、記録係1名です。

**③ 結果（改善前）**:

| タスク | 達成率 | 平均時間 |
| --- | --- | --- |
| T1 予約と支払い | 3 / 5 | 4 分 10 秒 |
| T2 取消し | 4 / 5 | 1 分 50 秒 |

**④ 見つかった問題と対策**:

| ID | 問題（観察された行動） | 人数 | 重大度 | 対策 |
| --- | --- | --- | --- | --- |
| U-1 | 予約金の額が決済画面に移るまで表示されず、金額を見て驚いて前の画面に戻った | 3 | 高 | 人数を選んだ直後に「予約金 3,000 円 × 4 名 = 12,000 円」とキャンセル規定を表示する |
| U-2 | 電話番号をハイフン付きで入力すると入力欄が赤枠になるだけで、理由が分からず進めなかった | 2 | 高 | ハイフンの有無にかかわらず受け付ける。誤りは文字で「電話番号は数字 10〜11 桁で入力してください」と表示する（色だけに頼らない） |
| U-3 | 人数のプルダウンで 20 項目をスクロールし、選び間違えた | 2 | 中 | 「−」「＋」ボタンで 1〜20 名を選ぶ部品に変える |
| U-4 | 取消しのボタンが予約詳細の一番下にあり、見つけるまでスクロールを往復した | 1 | 中 | 予約詳細の上部に「予約を変更・取消し」を置く |
| U-5 | カレンダーの日付が小さく、隣の日を押してしまった | 1 | 低 | 日付の押せる範囲を広げる |

**⑤ 入力チェックの見直し**: U-2 をきっかけに、予約画面の入力チェックを整理しました。

| 項目 | チェック | 内容 |
| --- | --- | --- |
| 人数 | リミットチェック | 1〜20 名の範囲か |
| 電話番号 | フォーマットチェック | ハイフンを除いて数字 10〜11 桁か |
| 来店日と時刻 | 組合せチェック | その曜日の営業時間内の時刻か（定休日の日付と時刻の組合せを受け付けない） |
| クーポンコード | 照合チェック | 店が発行したクーポンとして登録されているか |

**⑥ アクセシビリティの確認**: 自動チェックツールとキーボード操作・スクリーンリーダーでの確認を行い、次の点を直しました。

- 予約金の注意書きの薄い灰色の文字はコントラスト比が 4.5:1 に届かなかったため、濃い色に変更した
- 決済画面の「15 分で仮予約が取り消されます」という時間制限を、画面の最初に文字で知らせ、残り時間が少なくなったら延長できるボタンを付けた
- 店舗の写真に、料理や店内の様子を表す代替テキストを付けた
- 「−」「＋」ボタンに、読み上げ用に「人数を減らす」「人数を増やす」という名前を付けた

**⑦ 再テスト**: 別の 5 名で同じタスクを行ったところ、T1 の達成率は 5 / 5、平均時間は 2 分 30 秒になりました。改善の効果を同じ指標で確かめられたので、この画面をリリースしました。

## 例題

**例題1** 会員登録画面に次の項目を設ける。最も適切な GUI 部品をそれぞれ答えなさい。

1. 会員種別（一般 / 学生 / シニアのうち 1 つ）
2. 興味のある分野（複数選択可）
3. 居住する都道府県（47 項目から 1 つ）

**解き方**

1. 少数の選択肢から 1 つだけ選ぶので **ラジオボタン**
2. いくつでも選べるので **チェックボックス**
3. 選択肢が多く、画面の場所をとらないほうがよいので **プルダウンメニュー**（またはリストボックス）

**例題2** 生年月日の「月」の入力欄に 13 が入力されたときに誤りを検出できる入力チェックはどれか。

**解き方**: 値が 1〜12 の範囲に収まっているかを確かめればよいので、**リミットチェック（範囲チェック）** です。
「4 月 31 日」のように、月と日の **組合せ** で初めて誤りがわかる場合は組合せチェックになります。

## 試験対策のポイント

- **ITパスポート**: GUI 部品の使い分け（ラジオボタンとチェックボックスの違いは定番）、タッチ操作の名称、ユニバーサルデザイン・アクセシビリティ・ユーザビリティの意味、レスポンシブ Web デザインが中心です。
- **基本情報技術者**: 入力チェックの種類、ユーザビリティ評価の手法（ヒューリスティック評価とユーザビリティテストの違い）、人間中心設計、UX デザインの五段階モデルが問われます。
- **応用情報技術者**: ユニバーサルデザインの 7 原則の適用例、思考発話法・回顧法・認知的ウォークスルーなど評価手法の使い分け、Web アクセシビリティ（WCAG）への配慮など、設計判断の観点で問われます。
- ユニバーサルデザインは「最初から全員のために」、バリアフリーは「後から障壁を取り除く」と対比で覚えます。
