アプリケーション層には用途ごとに多くのプロトコルがあります。ここでは試験で頻出のものを用途別に整理します。
ポート番号は [TCP と UDP](../../transport/tcp-udp/) の表もあわせて確認してください。

## Web

| プロトコル | 内容 |
| --- | --- |
| HTTP | Webブラウザと Webサーバの間で、HTML や画像などをやり取りする。要求（リクエスト）と応答（レスポンス）の繰り返し |
| HTTPS | HTTP を **TLS** で暗号化したもの。通信の盗聴・改ざんを防ぎ、サーバ証明書で接続先の真正性を確認する |

HTTP 自体は状態を持たない（ステートレスな）プロトコルのため、ログイン状態などの管理には **Cookie** やセッションIDを使います。

### 主な HTTP メソッドとステータスコード

| メソッド | 用途 |
| --- | --- |
| GET | リソースの取得 |
| POST | データの送信（フォームの送信など） |
| PUT / DELETE | リソースの更新・削除 |

| ステータスコード | 意味 |
| --- | --- |
| 200 番台 | 成功（200 OK） |
| 300 番台 | リダイレクト（301 恒久的な移動 など） |
| 400 番台 | クライアントエラー（404 Not Found、403 Forbidden など） |
| 500 番台 | サーバエラー（500 Internal Server Error、503 Service Unavailable など） |

## 電子メール

| プロトコル | 役割 | 特徴 |
| --- | --- | --- |
| SMTP | **送信・転送** | メールソフト → メールサーバ、メールサーバ → メールサーバへの送信に使う |
| POP3 | **受信** | メールをサーバから **端末にダウンロード** して読む。基本的に受信後はサーバから削除する |
| IMAP4 | **受信** | メールを **サーバ上で管理** したまま読む。複数の端末で同じ状態（既読・フォルダ）を共有できる |
| MIME | 拡張 | 日本語や画像・添付ファイルなどを電子メールで扱えるようにする規格 |
| S/MIME | 暗号化・署名 | 公開鍵暗号を使ってメール本文の暗号化とデジタル署名を行う |

> 送信は SMTP、受信は POP3 か IMAP。スマートフォンと PC の両方で同じメールを読むなら IMAP が向いています。

## ファイル転送・遠隔操作・その他

| プロトコル | 内容 |
| --- | --- |
| FTP | ファイル転送。制御用（21番）とデータ転送用（20番）で別のコネクションを使う。通信は暗号化されない |
| SSH | 遠隔地のコンピュータに **暗号化** された通信路でログインし操作する。SFTP や SCP でファイル転送にも使う |
| Telnet | 遠隔ログイン。通信が **暗号化されない** ため、現在は SSH が推奨される |
| NTP | ネットワーク上の機器の **時刻を同期** する。ログの時刻をそろえるために重要 |
| SNMP | ネットワーク機器の状態を **監視・管理** する。管理対象（エージェント）が異常を通知する機能（トラップ）もある |

## 実務での見え方

### Web: やり取りを自分の目で見る

- **ブラウザの開発者ツール**（多くのブラウザで F12 キーなどで開く）の「ネットワーク」タブには、ページを開いたときのリクエストが1つずつ並び、メソッド・ステータスコード・かかった時間・ヘッダを確かめられます。1ページを表示するのに、HTML・画像・スクリプトなど数十件のリクエストが送られていることが分かります。
- コマンドでは `curl` が便利です（macOS・Linux のほか、最近の Windows にも標準で入っています）。

```
curl -I https://www.minato.example/     # 応答のステータス行とヘッダだけを表示
curl -v https://www.minato.example/     # TLS の接続やリクエストの中身も含めて詳しく表示
```

`curl -I` の結果は、例えば次のようになります（形式を示すための例です）。

```
HTTP/2 200
content-type: text/html; charset=UTF-8
```

ステータスコードが返ってきたなら、名前解決・TCP の接続・HTTP のやり取りまでは成功しています。
ブラウザに「このサイトにアクセスできません」のような **ブラウザ自身のエラー** が出るときは、HTTP より下（DNS や TCP の接続）で失敗しています。
この違いで、ネットワークの問題かサーバ（アプリケーション）の問題かを切り分けられます。

HTTPS で「証明書が無効」と警告されるときは、証明書の期限切れや名前の不一致のほか、**PC の時刻が大きくずれている** ことも原因になります。証明書の有効期間を PC の時計で判定するためで、NTP による時刻同期は HTTPS にも関わっています。

### メール: メールソフトの設定に出てくる番号

メールソフトやスマートフォンにメールアカウントを設定すると、次のようなプロトコルとポートを指定します（実際の値は利用するサービスの案内に従います）。

| 用途 | プロトコル | よく使われるポート |
| --- | --- | --- |
| 受信 | IMAP4 を TLS で暗号化（IMAPS） | 993 |
| 受信 | POP3 を TLS で暗号化（POP3S） | 995 |
| 送信 | SMTP のサブミッション（STARTTLS で暗号化し、SMTP-AUTH で認証） | 587 |
| 送信 | SMTP を TLS で暗号化（SMTPS） | 465 |

### 機器の管理・時刻・監視

- **遠隔操作**: サーバやネットワーク機器の操作には SSH を使います（例: `ssh admin@192.168.20.10`）。初めて接続するときは相手の「ホスト鍵」の確認を求められ、以後は鍵が変わると警告が出ます。偽のサーバへの接続に気付くための仕組みです。Telnet は機器側で無効にしておきます。
- **時刻**: OS は通常、自動で NTP サーバと時刻を合わせています。Windows では `w32tm /query /status`、Linux では `timedatectl` で同期の状態を確かめられます。
- **監視**: 監視ソフトが SNMP で機器の通信量やポートの状態を定期的に取得し、グラフ化や異常の通知に使います。古い版（v1・v2c）は「コミュニティ名」という合言葉が暗号化されずに流れるので、認証と暗号化ができる **SNMPv3** を使うのが望ましいです。

## 事例

[みなと事務所](../../)（社員30名・2フロア）で使っているアプリケーションプロトコルを整理すると、次のようになります。

| 用途 | プロトコル（ポート） | 相手 |
| --- | --- | --- |
| 自社サイトの閲覧・更新 | HTTPS（TCP 443） | レンタルサーバ 198.51.100.20 |
| メール | ブラウザからは HTTPS、メールソフトからは IMAPS（993）と SMTP サブミッション（587） | クラウドのメールサービス |
| ファイル共有 | SMB（TCP 445） | NAS 192.168.20.10 |
| 機器の設定 | 管理画面は HTTPS、スイッチは SSH。Telnet は無効 | ルータ・スイッチ・AP |
| 時刻 | NTP（UDP 123）。ルータが外部の NTP サーバと同期し、社内の機器はルータを参照 | ルータ |
| 監視 | SNMPv3 で通信量と状態を取得し、異常はトラップで通知 | ルータ・スイッチ・NAS |

**時刻のずれで調査が進まなかった例**: NAS に不審なログインの記録が残ったため、ルータのログ（どこからの通信か）と突き合わせようとしたところ、NAS の時計が約7分遅れていて、どの通信が対応するのか特定に手間取りました。
NAS の NTP 設定が無効になっていたのが原因で、ルータを参照するよう設定し直しました。ログを突き合わせる場面が来る前に、すべての機器で時刻を同期しておくことが大切です。

**ステータスコードでの切り分けの例**: サイトをリニューアルした翌日、「お知らせのページが開けない」と取引先から連絡がありました。`curl -I` で古い URL を確かめると `404` が返っていたので、ネットワークではなくサイト側の問題と分かりました。
URL の構成が変わっていたため、古い URL から新しい URL へ `301`（恒久的な移動）で転送する設定をレンタルサーバに追加して解決しました。

## 試験対策のポイント

- **ITパスポート**: 「メール送信は SMTP、受信は POP3/IMAP」「POP と IMAP の違い」「HTTPS は通信を暗号化する」が頻出。
- **基本情報**: 各プロトコルの役割に加え、TCP/UDP の別と代表的なポート番号もセットで覚える。
- **応用情報**: TLS の仕組み（証明書による認証と鍵交換）、メールの送信ドメイン認証、ファイアウォールで許可すべき通信の設計などに発展する。
