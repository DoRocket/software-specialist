IP がパケットを届けるには、いくつかの補助的なプロトコルが必要です。代表が **ARP** と **ICMP** です。

## ARP（Address Resolution Protocol）

IP でパケットを送るとき、実際に同じネットワーク上の相手（または次のルータ）にフレームを届けるには、相手の **MACアドレス** が必要です。
ARP は **IPアドレスから MACアドレスを求める** プロトコルです。

### 動作の流れ

1. PC-A が「IPアドレス 192.168.1.20 の機器の MACアドレスを教えて」という **ARP要求** を **ブロードキャスト** で送る
2. 同じネットワーク内の全機器が受け取るが、該当する IPアドレスを持つ PC-B だけが自分の MACアドレスを入れた **ARP応答** を **ユニキャスト** で返す
3. PC-A は結果を **ARPテーブル（ARPキャッシュ）** に一定時間保存し、以後の通信に使う

宛先が別のネットワークにある場合は、宛先そのものではなく **デフォルトゲートウェイ（ルータ）の MACアドレス** を ARP で求めて、ルータにフレームを渡します。

> IPv6 では ARP の代わりに ICMPv6 の **近隣探索（NDP）** が同じ役割を果たします。

### 関連する攻撃

ARP 応答には認証がないため、偽の ARP 応答で通信を自分に向けさせる **ARPスプーフィング（ARPポイズニング）** という攻撃があります。

## ICMP（Internet Control Message Protocol）

IP 通信における **エラーの通知や制御・診断のためのメッセージ** を運ぶプロトコルです。IP は自身でエラーを報告しないため、ICMP がその役割を補います。

| 主なメッセージ | 内容 |
| --- | --- |
| エコー要求 / エコー応答 | 相手に到達できるかを確認する（ping が使う） |
| 宛先到達不能（Destination Unreachable） | 宛先ネットワークやポートに到達できないことを通知 |
| 時間超過（Time Exceeded） | TTL が 0 になりパケットが破棄されたことを通知 |
| リダイレクト | より適切なルータがあることを送信元に通知 |

### ping と traceroute

- **ping**: ICMP エコー要求を送り、エコー応答が返るかで **疎通確認** を行う。往復時間も分かる。
- **traceroute（Windows では tracert）**: TTL を 1, 2, 3… と増やしながらパケットを送り、
  各ルータから返る **時間超過** メッセージを使って **宛先までの経路（経由するルータ）** を調べる。

**TTL（Time To Live）** は IP ヘッダのフィールドで、ルータを1つ通過するたびに 1 減り、0 になるとパケットは破棄されます。
経路がループしてもパケットが永久に回り続けないための仕組みです。

## 実務での見え方

### ARPテーブルを見る

自分の PC の ARPテーブルは、`arp -a`（Windows・macOS・Linux）で表示できます。Linux では `ip neigh` でも同じ情報が見られます。
Windows では例えば次のように表示されます（アドレスと形式は例です）。

```
インターフェイス: 192.168.10.105 --- 0xc
  インターネット アドレス  物理アドレス          種類
  192.168.10.1          00-1a-2b-00-00-01     動的
  192.168.10.255        ff-ff-ff-ff-ff-ff     静的
  224.0.0.251           01-00-5e-00-00-fb     静的
```

- `動的` は ARP で学習した項目で、しばらく通信がないと消えます。`静的` はブロードキャストやマルチキャストのように、計算で決まる対応です。
- 別のネットワークにある機器（例: インターネット上のサーバ）は表に出てきません。その宛先へはデフォルトゲートウェイ（ここでは 192.168.10.1）の MACアドレスを使って送るからです。
- テーブルを消して取り直したいときは、Windows では管理者として `arp -d *`、Linux では `ip neigh flush dev eth0` のように実行します（どちらも管理者権限が必要です）。

### ping の結果を読む

Windows の `ping` では、結果が例えば次のように表示されます（文言は OS の版や言語で異なります）。

```
192.168.10.1 からの応答: バイト数 =32 時間 <1ms TTL=64     ← エコー応答が返った
要求がタイムアウトしました。                                ← 決められた時間内に応答がない
192.168.10.105 からの応答: 宛先ホストに到達できません。      ← 宛先到達不能（ここでは自分の PC が返している）
```

- **タイムアウト** は、相手が止まっている、経路がない、相手やファイアウォールが ICMP を遮断している、などで起きます。原因はこれだけでは決まりません。
- **宛先ホストに到達できません** が自分の PC から返るのは、同じネットワーク内の宛先に ARP を送っても応答がなかったときによく見られます。ルータから返る場合は、ルータがその先へ届けられなかったことを示します。
- 応答の **TTL** は、相手が送ったときの初期値（OS によって 64 や 128 などが多い）から、途中のルータの数だけ減った値です。おおよその距離の目安になります。

### ICMP を止めすぎない

セキュリティのために ICMP をすべて遮断すると、`ping` や `traceroute` で調べられなくなるだけでなく、通信に必要な通知まで届かなくなることがあります。
例えば、経路の途中で送れるパケットの大きさ（MTU）が小さいとき、それを送信元に知らせるのも ICMP の宛先到達不能メッセージです。これが届かないと「小さなやり取りはできるのに、大きなデータだけ届かない」という分かりにくい障害になります。
外部からのエコー要求は止めても、エラー通知のメッセージは通す、というように種類を選んで制限するのが一般的です。

## 事例

[みなと事務所](../../)（社員30名・2フロア）の機器用ネットワーク（192.168.20.0/24）は、すべて固定アドレスで運用しています。

ある週から「4階の複合機（192.168.20.22）で、ときどき印刷できない」という相談が続きました。担当者は ARP と ICMP を使って調べました。

1. 4階の複合機の電源を切り、機器用ネットワークにつないだ管理用の PC から `ping 192.168.20.22` を実行すると、**応答が返ってきた**。電源を切った機器が応答するはずはないので、同じアドレスを使う別の機器がいると分かる。
2. 続けて `arp -a` を見ると、192.168.20.22 に対応する MACアドレスが、台帳にある複合機の MACアドレスと違っていた。MACアドレスの上位24ビット（OUI）から製造者を調べると、複合機とは別のメーカーだった。
3. その週に業者が設置した入退室管理の装置が、手動で 192.168.20.22 を設定していたことが分かった。

同じアドレスの機器が2台あると、ARP の応答がどちらから返るかによって、ルータの ARPテーブルの MACアドレスが入れ替わり、通信が届いたり届かなかったりします。
「ときどき」印刷できなかったのはこのためです。入退室管理の装置を空いている 192.168.20.23 に変更してアドレスの台帳に追記し、
以後は「機器用ネットワークに機器をつなぐときは台帳でアドレスを確認してから」というルールにしました。

## 試験対策のポイント

- **基本情報**: ARP の目的（IP → MAC）と、要求がブロードキャスト・応答がユニキャストであること。ping が ICMP を使うこと。
- **応用情報**: traceroute の原理（TTL と時間超過）、ARP スプーフィングなど、トラブルシュートやセキュリティの文脈で問われる。
