**TCP**（Transmission Control Protocol）と **UDP**（User Datagram Protocol）は、トランスポート層の代表的なプロトコルです。
アプリケーションは、用途に応じてどちらを使うかを選びます。

## 比較

| 項目 | TCP | UDP |
| --- | --- | --- |
| 接続 | **コネクション型**（通信前に接続を確立する） | **コネクションレス型**（いきなり送る） |
| 信頼性 | 高い。確認応答・再送・順序制御を行う | なし。届いたか・順序が正しいかを保証しない |
| 速度・負荷 | 制御が多い分オーバーヘッドが大きい | 制御が少なく高速・低負荷 |
| ヘッダ長 | 20バイト〜（オプションで可変） | **8バイト固定** |
| 宛先 | 1対1（ユニキャスト）のみ | ブロードキャスト・マルチキャストにも使える |
| 主な用途 | Web（HTTP/HTTPS）、メール（SMTP, POP3, IMAP）、ファイル転送（FTP）、SSH | DNS の問合せ、DHCP、NTP、音声通話（VoIP）、動画のライブ配信 |

音声通話やライブ配信では、遅れて届いたデータを再送しても役に立たないため、
多少の欠落を許容してでも遅延の小さい UDP が選ばれます。

3回のやり取りで双方が通信の準備ができたことを確認します。終了時は FIN を使って接続を解放します。

### その他の制御

| 仕組み | 内容 |
| --- | --- |
| シーケンス番号と確認応答（ACK） | 送ったデータに番号を付け、受信側は「どこまで受け取ったか」を返す。順序の並べ替えにも使う |
| 再送制御 | 一定時間内に ACK が返らなければ再送する |
| フロー制御（ウィンドウ制御） | 受信側が受け取れる量（ウィンドウサイズ）を通知し、ACK を待たずにその範囲までまとめて送ることで効率を上げつつ、受信側があふれないようにする |
| 輻輳（ふくそう）制御 | ネットワークの混雑を検知したら送信量を減らし、混雑を悪化させないようにする |

## ポート番号

ポート番号は 0〜65535 の 16 ビットの値で、通信相手のアプリケーションを識別します。
**IPアドレス + ポート番号** の組で通信の端点が決まります。

| 範囲 | 名称 | 用途 |
| --- | --- | --- |
| 0〜1023 | ウェルノウンポート | 代表的なサービス用に予約 |
| 1024〜49151 | 登録済みポート | 特定のアプリケーション用に登録 |
| 49152〜65535 | 動的・プライベートポート | クライアント側が一時的に使う |

### 代表的なウェルノウンポート

| ポート番号 | プロトコル | TCP/UDP |
| --- | --- | --- |
| 20, 21 | FTP（20: データ転送、21: 制御） | TCP |
| 22 | SSH | TCP |
| 23 | Telnet | TCP |
| 25 | SMTP | TCP |
| 53 | DNS | UDP（ゾーン転送や大きな応答では TCP） |
| 67, 68 | DHCP（67: サーバ、68: クライアント） | UDP |
| 80 | HTTP | TCP |
| 110 | POP3 | TCP |
| 123 | NTP | UDP |
| 143 | IMAP | TCP |
| 443 | HTTPS | TCP（HTTP/3 では UDP 上の QUIC） |

メール送信では、利用者のメールソフトからサーバへの送信に **サブミッションポート（587）** を使い、
**SMTP-AUTH** で利用者を認証する運用が一般的です（迷惑メール対策の **OP25B** と組み合わせる）。

## 実務での見え方

### 接続の一覧を見る

PC がいまどこと TCP/UDP で通信しているか、どのポートで待ち受けているかは、次のコマンドで見られます（`#` の後は説明です）。

```
netstat -an        # Windows・macOS: 接続と待受けの一覧（-n で名前に変換せず番号で表示）
netstat -ano       # Windows: 最後の列にプロセスID（どのプログラムの通信か）を表示
ss -tan            # Linux: TCP の接続の一覧（-u にすると UDP）
ss -tlnp           # Linux: 待ち受けている TCP ポートとプログラム（他の利用者のものは管理者権限が必要）
lsof -i -P         # macOS: ネットワークを使っているプログラムとポート
```

Windows の `netstat -an` では、例えば次のように表示されます（形式を示すための例です）。

```
  プロトコル  ローカル アドレス        外部アドレス           状態
  TCP         0.0.0.0:445            0.0.0.0:0              LISTENING
  TCP         192.168.10.105:52814   198.51.100.20:443      ESTABLISHED
  TCP         192.168.10.105:52815   198.51.100.20:443      TIME_WAIT
  UDP         0.0.0.0:5353           *:*
```

| 表示 | 意味 |
| --- | --- |
| `LISTENING`（Linux の `ss` では `LISTEN`） | そのポートで接続を待ち受けている（サーバ側） |
| `ESTABLISHED` | 3ウェイハンドシェイクが済み、接続が確立している |
| `SYN_SENT` | SYN を送ったが SYN + ACK が返ってこない。相手に届いていない、途中で遮断されている、などを疑う |
| `TIME_WAIT` | 接続を終えた直後の状態。しばらくすると消える |

2行目は「自分の 52814番ポートから、自社サイトの 443番（HTTPS）へ接続中」という意味です。自分側のポートはクライアントが一時的に使う番号です。
一時的に使うポートの範囲は OS によって異なり、例えば Linux では 32768番からの範囲を使う設定が多く見られます。UDP にはコネクションがないので、状態の欄は空です。

### 特定のポートにつながるか確かめる

`ping` は ICMP なので、通っても「そのアプリのポートにつながる」ことまでは分かりません。ポートへの接続は次のように確かめます。

```
Test-NetConnection www.minato.example -Port 443    # Windows PowerShell（TcpTestSucceeded が True なら成功）
nc -vz www.minato.example 443                      # macOS・Linux（nc がある場合）
```

- 「接続が拒否された（refused）」と出るのは、相手の機器までは届いたが、そのポートで待ち受けるプログラムがない場合です（TCP の RST が返る）。
- 「タイムアウト」は、途中のファイアウォールなどで黙って捨てられている可能性があります。
- UDP は接続を確立しないので、同じ方法では確かめにくく、アプリの動作やログで確認することが多くなります。

### ファイアウォールのルールはポートで書く

ルータやファイアウォールのフィルタは、「送信元・宛先の IPアドレス」と「プロトコル（TCP/UDP）・ポート番号」の組で、許可するか拒否するかを決めます。
多くの機器は、内側から始まった接続を覚えておき、その戻りのパケットを自動で通します（ステートフルインスペクション）。そのため、ルールは「どこからどこへの接続を始めてよいか」の向きで考えます。

## 事例

[みなと事務所](../../)（社員30名・来客用 Wi-Fi あり）のルータでは、ネットワーク間のフィルタをポート番号で設定しています（主なものだけ抜粋）。

| 送信元 | 宛先 | プロトコル・ポート | 動作 | 目的 |
| --- | --- | --- | --- | --- |
| 社員用 | NAS（192.168.20.10） | TCP 445 | 許可 | ファイル共有（SMB） |
| 社員用 | 複合機（192.168.20.21・.22） | TCP 631、TCP 9100 | 許可 | 印刷（IPP、RAW 印刷） |
| 来客用・社員用 | ルータ自身 | UDP 67、UDP・TCP 53 | 許可 | DHCP と DNS |
| 来客用 | 社員用・機器用 | すべて | 拒否 | 社内を守る |
| 来客用 | インターネット | TCP 25 | 拒否 | 迷惑メールの送信に使われないようにする |
| 来客用・社員用 | インターネット | 上記以外すべて | 許可 | Web・Web会議など |

Web会議のサービスは、映像や音声を UDP で送るものが多く、UDP が通らない環境では TCP に切り替えて動くものもありますが、遅延が大きくなりがちです。
来客用でも UDP を止めていないのはこのためです。

ある日、ルータの設定を更新した後に「4階から NAS が開けない」と連絡がありました。

1. `ping 192.168.20.10` には応答がある → インターネット層までは問題ない
2. `Test-NetConnection 192.168.20.10 -Port 445` が失敗（TcpTestSucceeded が False） → トランスポート層で止まっている
3. NAS 自身の管理画面ではファイル共有のサービスは動いていた → 途中のフィルタを疑う

ルータの設定を見ると、更新のときに「社員用から NAS への TCP 445 を許可」の行が消えていました。行を戻すと接続できるようになり、以後は設定変更の前後で上のフィルタ表と突き合わせるようにしています。

## 試験対策のポイント

- **ITパスポート**: TCP は信頼性重視、UDP はリアルタイム性重視、という使い分け。ポート番号がアプリケーションの識別に使われること。
- **基本情報**: 3ウェイハンドシェイク、TCP/UDP それぞれを使う代表的なプロトコル、代表的なポート番号（80, 443, 25, 110, 53 など）。
- **応用情報**: ファイアウォールのフィルタリングルール（送信元/宛先ポートの指定）、NAPT のポート変換、ウィンドウ制御による スループットの考え方などが問われる。
