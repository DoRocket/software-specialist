攻撃手法は「どの弱点を狙い、どのセキュリティ要素（CIA）を損なうか」で整理すると理解しやすくなります。
ここでは試験で頻出の手口と、それぞれの代表的な対策をまとめます。

## マルウェア

悪意のあるソフトウェアの総称です。

| 種類 | 特徴 |
| --- | --- |
| ウイルス | 他のプログラムに寄生して感染を広げる |
| ワーム | 単独で動作し、ネットワークを通じて自己複製・拡散する |
| トロイの木馬 | 有用なソフトを装って侵入し、裏で不正な動作をする |
| ランサムウェア | ファイルを暗号化するなどして使えなくし、復旧と引換えに金銭を要求する |
| スパイウェア / キーロガー | 利用者の情報やキー入力を盗み取って送信する |
| ボット | 感染した PC を外部の C&C サーバから遠隔操作できるようにする |

**対策**: OS・ソフトウェアの更新（脆弱性の修正）、マルウェア対策ソフトの導入と定義ファイルの更新、不審な添付ファイルを開かない、ランサムウェアに備えた **オフライン（ネットワークから切り離した）バックアップ**。

## フィッシング

実在の金融機関や EC サイトなどを装ったメールや SMS で偽サイトへ誘導し、ID・パスワードやクレジットカード情報を入力させて盗む手口です。

**対策**: メールのリンクから直接ログインしない、URL やサーバ証明書を確認する、多要素認証の導入、送信ドメイン認証（SPF・DKIM・DMARC）による送信元詐称の検知。

## Web アプリケーションへの攻撃

| 攻撃 | 手口 | 主な対策 |
| --- | --- | --- |
| SQL インジェクション | 入力欄に SQL の一部を入力し、意図しない SQL 文を実行させる | **プレースホルダ（バインド機構）** の利用、特殊文字のエスケープ、DB アカウントの権限最小化 |
| クロスサイトスクリプティング（XSS） | 悪意のあるスクリプトを Web ページに埋め込み、閲覧者のブラウザで実行させる（Cookie の窃取など） | 出力時の **エスケープ（サニタイジング）**、Cookie への HttpOnly 属性付与 |
| クロスサイトリクエストフォージェリ（CSRF） | ログイン中の利用者に罠ページを踏ませ、本人の意図しない処理（送金・投稿など）を正規サイトへ送信させる | 推測困難な **トークン** をフォームに埋め込み照合する、重要処理前の再認証、Cookie の SameSite 属性 |

### SQL インジェクションの例

次のように入力値を文字列連結で SQL 文に組み込むと危険です。

```sql
-- アプリケーションが組み立てる SQL
SELECT * FROM 利用者 WHERE id = '入力値' AND pw = '入力値';

-- id 欄に「' OR '1'='1' --」と入力されると
SELECT * FROM 利用者 WHERE id = '' OR '1'='1' --' AND pw = '';
```

`--` 以降はコメントとして無視され、`'1'='1'` は常に真なので、パスワードを知らなくても全利用者の行が返ります。
プレースホルダを使うと、入力値は SQL 文の構造とは切り離されて「値」としてのみ扱われるため、この攻撃を防げます。

XSS と CSRF はどちらも罠ページなどを経由しますが、XSS は **閲覧者のブラウザでスクリプトを実行させる** 攻撃、CSRF は **正規サイトに本人の権限でリクエストを送らせる** 攻撃という違いがあります。

## DoS 攻撃 / DDoS 攻撃

大量のリクエストやパケットを送り付けてサーバやネットワークを過負荷にし、サービスを停止させる攻撃で、**可用性** を損ないます。

- **DoS**（Denial of Service）: 1台から攻撃する。
- **DDoS**（Distributed DoS）: ボットに感染させた多数の機器（ボットネット）から一斉に攻撃する。送信元が多数あるため、特定の送信元を遮断するだけでは防ぎにくい。
- **SYN フラッド**: TCP の接続確立（3ウェイハンドシェイク）で SYN だけを大量に送り、サーバの接続待ちの資源を使い果たさせる。
- **リフレクション攻撃**: 送信元 IP アドレスを攻撃対象に偽装して DNS などに問い合わせ、応答を対象に集中させる。応答が要求より大きくなるものは **増幅攻撃** とも呼ばれる。

**対策**: ファイアウォールや IPS による異常な通信の遮断、通信量の制限、CDN や ISP の DDoS 対策サービスの利用、サーバの冗長化。

## 標的型攻撃

特定の組織を狙い、業務に関係がありそうな件名・本文のメールでマルウェア付きの添付ファイルや URL を開かせ、侵入後に組織内部で感染を広げて機密情報を盗み出す攻撃です。
長期間にわたって潜伏しながら継続するものは **APT**（Advanced Persistent Threat）とも呼ばれます。
攻撃対象がよく閲覧する Web サイトを改ざんして待ち伏せる **水飲み場型攻撃** もこの一種です。

**対策**: 不審メールへの教育・訓練、入口対策（メールフィルタ）だけでなく **出口対策**（外部への不審な通信の検知・遮断）、ログ監視、ネットワークの分離による多層防御。

## ソーシャルエンジニアリング

技術ではなく **人間の心理や習慣の隙** を突いて情報を盗む手口です。

| 手口 | 内容 |
| --- | --- |
| なりすまし電話 | 上司や保守担当者を装い、パスワードなどを聞き出す |
| ショルダーハッキング | 背後からのぞき見して画面や入力を盗み見る |
| トラッシング | ごみ箱に捨てられた書類や媒体から情報を得る |
| ビジネスメール詐欺（BEC） | 取引先や経営者を装ったメールで偽の口座へ送金させる |

**対策**: 規程と手順の整備（電話でパスワードを教えない、送金先変更は別経路で確認する等）、従業員教育、のぞき見防止フィルタ、シュレッダーや媒体の確実な廃棄。

## 実際の進め方

攻撃の多くはメールから始まります。ここでは、利用者が不審なメールに気付いて報告できるようにするための確認方法と、訓練の進め方を示します。

### 不審なメールの確かめ方

| 確かめる点 | 見るところ | 不審な例 |
| --- | --- | --- |
| 送信者 | 表示名ではなく、実際のメールアドレスのドメイン | 表示名は取引先の担当者名だが、アドレスが似た別のドメイン（`i` と `l`、`rn` と `m` の入れ替えなど） |
| 返信先 | 返信しようとしたときの宛先 | 送信元と違うアドレス（フリーメールなど）に返信させようとしている |
| リンク | マウスを重ねる（スマートフォンでは長押しする）と表示される実際の URL | 表示された文字と実際の URL が違う、ドメインが正規のサービスと違う |
| 文面 | 急がせる表現、普段と違う依頼 | 「本日中に」「アカウントが停止されます」「振込先が変わりました」 |
| 添付ファイル | ファイルの種類 | パスワード付きの圧縮ファイル、マクロの有効化を求める文書、ショートカットファイル |

文面だけで見分けるのは難しくなっているため、**依頼の内容を、メール以外の経路（以前から知っている電話番号など）で確かめる** ことが最も確実な対策です。

### メールのヘッダで送信ドメイン認証の結果を見る

多くのメールソフトでは「メッセージのソースを表示」などの操作でヘッダを見られます。受信側のメールサーバが SPF・DKIM・DMARC を検査した結果は、`Authentication-Results` という行に記録されます（次は形式を示すための例です）。

```text
Authentication-Results: mx.mail.example;
       spf=pass smtp.mailfrom=billing@kaede-prlnt.example;
       dkim=pass header.d=kaede-prlnt.example;
       dmarc=pass header.from=kaede-prlnt.example
```

| 結果 | 意味 |
| --- | --- |
| `spf=pass` | 送信元のメールサーバが、送信元ドメインの許可したサーバだった |
| `dkim=pass` | メールに付いた電子署名を、署名したドメイン（`header.d`）の公開鍵で検証できた |
| `dmarc=pass` | SPF か DKIM の少なくとも一方が成功し、その検査したドメインが画面に表示される From のドメインと一致した |
| `fail` | 上の検査に失敗した。表示された送信元が詐称されている可能性が高い |

`pass` は「そのドメインの正規の送信設定どおりに送られた」ことを示すだけで、**ドメインそのものが本物の取引先かどうかは示しません**。上の例は、取引先 `kaede-print.example` に似せて攻撃者が取得したドメイン `kaede-prlnt.example` から送られたメールで、すべて `pass` になっています。

### 開いてしまったときの報告

- リンクを開いた・ID やパスワードを入力した・添付ファイルを開いた場合は、**すぐに決められた窓口へ報告** する。パスワードを入力した場合は、報告とあわせてそのパスワードを変更する。
- 添付ファイルを開いて PC の様子がおかしい場合は、LAN ケーブルを抜き無線LAN を切る。電源は切らない（理由は [情報セキュリティマネジメント](../management/) の初動手順を参照）。
- 不審なメールは削除せず、窓口の指示に従って転送するか、そのまま残しておく。

### 標的型メール訓練の進め方

1. **目的を決める**: 「開かないこと」だけでなく「**気付いたら報告する** こと」を主な目的にする。開いてしまっても、すぐ報告されれば被害を小さくできる。
2. **計画を承認してもらう**: 経営者の承認を得て、時期・対象・使う文面を決める。実施することは事前に全体に伝えてよいが、日時は伏せる。
3. **文面を作る**: 実際に届いた手口（宅配便の不在通知、パスワードの期限切れ、請求書の送付など）に近い文面にする。実在の取引先の名前を勝手に使うと混乱を招くので避ける。
4. **実施して記録する**: リンクを開いた人数、報告した人数、報告までにかかった時間を記録する。
5. **振り返る**: 結果を全体で共有し、見分けるポイントを説明する。開いた人の名前は公表せず、責めない。
6. **繰り返す**: 文面を変えて定期的に行い、報告率の変化を見る。

**結果の集計表**（例）

| 回 | 文面 | 対象者 | リンクを開いた | 報告した | 最初の報告までの時間 |
| --- | --- | --- | --- | --- | --- |
| 1 | パスワードの期限切れ | 30名 | 7名（23%） | 9名（30%） | 25分 |

### よくある失敗と対策

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| 訓練で開いた人を叱る・名前を出す | 本物のメールを開いたときに報告しなくなる | 報告したことを評価し、開いた人は個別に見分け方を説明する |
| 開封率だけを目標にする | 文面を簡単にすれば数字は良くなり、実際の備えにならない | 報告率と報告までの時間を主な指標にする |
| 報告の窓口があいまい | 気付いた人が誰にも言わずに削除する | 窓口（担当者と連絡方法）を1つに決め、掲示する |
| 送信ドメイン認証の `pass` を「安全」と受け取る | 似たドメインからのメールを信用してしまう | ドメイン名の綴りを確かめ、依頼は別の経路で確認する |
| 送金先の変更をメールだけで受け付ける | ビジネスメール詐欺で、偽の口座に送金してしまう | 送金先の変更は、以前から知っている電話番号に電話して確かめる手順にする |

## 事例

[みなと事務所](../../network/)（社員30名・2フロア）では、[共有アドレスの乗っ取り](../management/) の振り返りで「フィッシングに気付いて報告できる」ことが課題になり、総務課長が標的型メール訓練を始めました。

**1. 1回目の訓練**

「パスワードの有効期限が切れます」という件名で、偽のログイン画面に誘導する訓練メールを全員に送りました。
結果は、リンクを開いた人が 30名中 7名（約23%）、報告した人が 9名（30%）でした。開いた7名のうち、報告したのは1名だけでした。
振り返りでは、「開いてしまったことを言い出しにくかった」という声が多く、所長から「開いてしまっても、すぐ報告してくれれば被害は防げる。報告した人は責めない」と全体に伝えました。
あわせて、メールソフトに「不審メールを報告」ボタンを追加し、総務課長に転送できるようにしました。

**2. 2回目の訓練（3か月後）**

「請求書を送付します」という件名で、ファイル共有サービスを装ったリンクを送りました。
リンクを開いた人は 3名（10%）、報告した人は 22名（約73%）に増え、最初の報告は送信から 4分後でした。リンクを開いた3名も全員が報告していました。

**3. 実際に届いたビジネスメール詐欺**

2回目の訓練の翌月、総務の経理担当に、印刷を発注している取引先「かえで印刷」の担当者名で「今月から振込先の口座が変わりました」というメールが届きました。
過去のやり取りの件名を引用していたため本物らしく見えましたが、経理担当は訓練で学んだとおり送信元のドメインを確かめ、`kaede-print.example` ではなく `kaede-prlnt.example` であることに気付きました。
ヘッダの `Authentication-Results` はすべて `pass` でしたが、取引先の名刺にある電話番号に問い合わせると、振込先の変更はしていないとのことでした。
総務課長は取引先に連絡し、取引先側でメールアカウントの乗っ取りがなかったか調べてもらいました。事務所では、送金先の変更は必ず電話で確認する手順を経理の手順書に書き加えています。

## 試験対策のポイント

- **ITパスポート**: 事例文から攻撃名を答える問題が中心です。ランサムウェア、フィッシング、ソーシャルエンジニアリング（ショルダーハッキング・トラッシング）、標的型攻撃の特徴を区別できるようにします。
- **基本情報**: SQL インジェクション・XSS・CSRF の手口と対策の対応付けが頻出です。「SQL インジェクション → プレースホルダ」「XSS → 出力時のエスケープ」「CSRF → トークン」と結び付けて覚えます。DoS と DDoS の違いも問われます。
- **応用情報**: 午後問題で、ログや通信の記録から攻撃を特定し、入口・内部・出口の多層的な対策を提案する力が問われます。リフレクション攻撃や水飲み場型攻撃など、手口の仕組みまで説明できるようにしておきます。
