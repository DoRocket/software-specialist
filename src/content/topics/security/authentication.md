利用者認証は、システムを使おうとしている人が **本人であるか（主張どおりの人物か）** を確認する仕組みで、真正性を確保するための基本的な対策です。
なお、認証で本人を確かめたうえで「何をしてよいか」の権限を与えることは **認可** と呼び、認証とは区別します。

## 認証の3要素

| 要素 | 確認するもの | 例 | 弱点 |
| --- | --- | --- | --- |
| 知識情報 | 本人だけが **知っている** こと | パスワード、PIN、秘密の質問 | 推測・盗み見・漏えい・使い回し |
| 所有情報 | 本人だけが **持っている** もの | IC カード、スマートフォン、セキュリティトークン | 紛失・盗難 |
| 生体情報 | 本人の **身体や行動の特徴** | 指紋、静脈、虹彩、顔、声紋、署名の筆跡 | 変更できない、誤判定がある |

### 多要素認証と多段階認証

**多要素認証** は、異なる要素を2つ以上組み合わせる方式です（2つなら二要素認証）。1つの要素が破られても、もう一方で不正ログインを防げます。

- パスワード（知識）＋ スマートフォンに届く確認コード（所有） → **多要素認証**
- IC カード（所有）＋ 指紋（生体） → **多要素認証**
- パスワード（知識）＋ 秘密の質問（知識） → 認証を2回行う **多段階認証** だが、要素は1種類なので多要素認証ではない

## パスワードに対する攻撃と管理

| 攻撃 | 手口 | 主な対策 |
| --- | --- | --- |
| 総当たり攻撃（ブルートフォース） | 1つの ID に対し、文字の組合せをすべて試す | 長く複雑なパスワード、一定回数の失敗で **アカウントロック** |
| 辞書攻撃 | 辞書の単語やよく使われる文字列を試す | 推測されやすい語を使わない |
| リバースブルートフォース攻撃 | パスワードを固定し、ID を次々に変えて試す | 同一 ID の失敗回数に依存しない監視（送信元ごとの試行回数の制限など） |
| パスワードリスト攻撃 | 他のサイトから流出した ID とパスワードの組を使ってログインを試す | **パスワードの使い回しをしない**、多要素認証 |

リバースブルートフォース攻撃では1つの ID あたりの失敗は1回程度なので、アカウントロックが働きにくい点がよく問われます。

サーバ側では、パスワードを平文のまま保存せず、**ハッシュ値** にして保存します。
さらに利用者ごとに異なるランダムな値（**ソルト**）を加えてからハッシュ化すると、同じパスワードでもハッシュ値が異なり、あらかじめ計算したハッシュ値の対応表（レインボーテーブル）による解読を防げます。ハッシュ計算を何度も繰り返して解読に時間をかけさせる **ストレッチング** も併用されます。

## ワンタイムパスワード

一度しか使えない使い捨てのパスワードです。盗聴されても次回のログインには使えないため、**リプレイ攻撃**（盗んだ認証情報をそのまま再送する攻撃）に強いのが特徴です。

- **時刻同期方式**: トークン（専用機器やスマートフォンのアプリ）とサーバが、共有する秘密情報と **現在時刻** から同じパスワードを生成する。一定時間（30秒など）ごとに値が変わる。
- **カウンタ同期方式**: 生成のたびに増えるカウンタ値を使って生成する。
- SMS やメールで、その都度パスワード（確認コード）を送る方法もある。

## チャレンジレスポンス認証

パスワードそのものをネットワークに流さずに認証する方式です。

```text
クライアント                         サーバ
   │ ① 利用者ID ─────────────────→ │
   │ ←──────────── ② チャレンジ     │  毎回異なる乱数を生成
   │ ③ レスポンス ────────────────→ │  レスポンス = f(チャレンジ, パスワード)
   │                                 │ ④ サーバも同じ計算をして一致を確認
```

クライアントは、チャレンジとパスワードからハッシュ関数などで **レスポンス** を計算して返します。
チャレンジが毎回変わるため、レスポンスを盗聴されても再利用できず、通信路上にパスワードが現れない点がポイントです。

## シングルサインオン（SSO）

**1回の認証で、複数のシステムやサービスを利用できる** ようにする仕組みです。利用者が覚えるパスワードが減り、管理も一元化できます。

| 方式 | 仕組み |
| --- | --- |
| Cookie 型 | 認証済みであることを示す Cookie を各サーバが確認する（同じドメイン内が前提） |
| リバースプロキシ型 | 利用者のアクセスをリバースプロキシに集め、そこで認証してから各サーバへ中継する |
| フェデレーション型 | 認証を担う **IdP**（Identity Provider）が発行した認証結果を、各サービスが信頼して受け入れる。SAML や OpenID Connect が使われ、組織やドメインをまたいで利用できる |

1組の認証情報が破られるとすべてのサービスに入られてしまうため、SSO の入口では多要素認証を組み合わせるのが望ましいとされます。
なお、OAuth はアクセス権限を他のサービスに委ねる **認可** のための仕組みであり、認証のための OpenID Connect は OAuth 2.0 を拡張したものです。

## 生体認証

身体的特徴（指紋、静脈パターン、虹彩、網膜、顔）や行動的特徴（声紋、署名の筆跡）で本人を確認します。
忘れたり紛失したりしない一方、**漏えいしても変更できない**、体調や加齢で特徴が変わるといった課題があります。

生体情報は毎回まったく同じには読み取れないため、登録データとの類似度が **しきい値** を超えれば本人と判定します。このため2種類の誤りが生じます。

| 指標 | 意味 | 高いと困ること |
| --- | --- | --- |
| 本人拒否率（FRR） | 本人なのに拒否してしまう割合 | **利便性** が下がる |
| 他人受入率（FAR） | 他人なのに受け入れてしまう割合 | **安全性** が下がる |

判定を厳しくすると FAR は下がりますが FRR は上がり、緩くするとその逆になる **トレードオフ** の関係です。安全性を重視するシステムでは FAR を低く設定します。

## その他の認証関連技術

- **CAPTCHA**: ゆがんだ文字の読み取りや画像の選択などをさせ、操作しているのが **人間かプログラム（ボット）か** を判別する。自動化された大量アカウント登録やログイン試行を防ぐ。本人確認の仕組みではない点に注意。
- **リスクベース認証**: いつもと違う端末・場所・時間帯からのアクセスなど、リスクが高いと判断したときだけ追加の認証を求める。
- **パスワードレス認証（FIDO など）**: 端末上で生体認証などを行い、端末内の秘密鍵による署名でサーバに本人であることを証明する。サーバには公開鍵だけを登録するため、サーバから秘密情報が漏えいしない。

## 例題

**問** 次のうち、多要素認証に該当するものはどれか。
ア　パスワードと秘密の質問の答えを入力する　イ　2種類のパスワードを順に入力する　ウ　IC カードをかざしたうえで PIN を入力する　エ　指紋と静脈で認証する

**解き方** 要素の種類で分類します。アとイは知識＋知識、エは生体＋生体で、いずれも1種類です。ウは IC カード（所有）と PIN（知識）の2種類を組み合わせているので、正解は **ウ** です。

## 実際の進め方

### パスワードの運用ルールを決める

パスワードは今も多くの場面で使われるので、多要素認証を入れる前提として、次のようなルールを決めて周知します。

| ルール | 理由 |
| --- | --- |
| **長さ** を重視する（例: 12文字以上。覚えやすい単語を複数つないだものでもよい） | 総当たり攻撃にかかる時間は、文字の種類よりも長さで大きく増える |
| **サービスごとに別のパスワード** にする | 1つのサービスから漏れたとき、パスワードリスト攻撃で他のサービスにも入られるのを防ぐ |
| パスワード管理ソフトの利用を認める | サービスごとに別の長いパスワードを、人が覚えるのは現実的でない |
| 機器やサービスの **初期パスワードは必ず変更** する | ルータ・NAS・複合機などの初期値は、製品の説明書などで公開されていることが多い |
| 漏えいの疑いがあるときはすぐ変更する | 定期的な変更の強制は、末尾の数字だけを変えるような推測されやすい変更を招きやすい |

最後の点について、NIST（米国国立標準技術研究所）のガイドライン SP 800-63B などでは、定期的な変更を強制するのではなく、漏えいの疑いがあるときに変更させる考え方がとられています。

### 多要素認証を導入する手順

1. **対象と優先順位を決める**: インターネットから直接ログインできる入口（メール・VPN・クラウドストレージ・機器の管理画面）を優先し、次に管理者アカウントを対象にする。
2. **方式を選ぶ**: 下の比較表を参考に、利用者が持っている端末と、防ぎたい攻撃に合わせて選ぶ。
3. **予備の手段と例外を決める**: スマートフォンの紛失・故障に備えて、**リカバリコード**（一度だけ使える予備のコード）や予備の認証手段を用意する。どうしても対象外にするアカウントは、理由と期限を決めて記録する。
4. **段階的に展開する**: 管理者 → 少人数での試行 → 全員の順に広げ、手順書と問い合わせ先を用意してから期限を区切って切り替える。
5. **古いログイン方法を止める**: 多要素認証に対応しない古い接続方式（パスワードだけで接続するメールソフトの設定など）が残っていると、そこが抜け道になる。
6. **再設定の手順を決める**: 端末の紛失・機種変更のときに多要素認証を設定し直す手順を決める。電話やメールの依頼だけでリセットすると、それ自体がなりすましの入口になるため、本人確認の方法を決めておく。

| 方式 | しくみ | 長所 | 注意点 |
| --- | --- | --- | --- |
| SMS で確認コードを受け取る | 登録した電話番号にコードが届く | 携帯電話があれば使える | 電話番号の乗っ取りや、偽サイトへのコード入力に弱い |
| 認証アプリのワンタイムパスワード | アプリが時刻同期方式で 30 秒ごとにコードを表示する | 通信できない場所でも使える | 偽サイトに入力したコードを、攻撃者がその場で正規サイトに中継する手口は防げない |
| プッシュ通知の承認 | ログイン時にスマートフォンへ届く通知を承認する | 操作が簡単 | 内容を確かめずに承認する癖がつくと、攻撃者のログインを承認してしまう |
| FIDO（パスキー・セキュリティキー） | 端末内の秘密鍵で署名し、サーバは登録済みの公開鍵で検証する | サイトのドメインと結び付いた鍵を使うため、偽サイトでは認証が成立しにくい | 対応していないサービスがある。端末を失ったときの予備を用意する |

### アカウントの管理（入社・異動・退職）

認証が強くても、使われなくなったアカウントが残っていれば入口になります。アカウントは人の出入りに合わせて管理します。

| 場面 | すること |
| --- | --- |
| 入社 | 申請書に基づいてアカウントを作り、必要な権限だけを与える（最小権限）。初回ログイン時にパスワードを変えさせ、多要素認証を登録させる |
| 異動 | 新しい部署の権限を与えると同時に、前の部署の権限を外す |
| 退職 | 最終日にアカウントを無効にし、多要素認証の登録や VPN の利用権も削除する。共有アカウントのパスワードも変更する |
| 定期 | 年に数回、アカウントの一覧と在籍者の名簿を突き合わせ、不要なアカウントを見つける（棚卸し） |

### よくある失敗と対策

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| 共有アカウントや「急ぎで使う人」を多要素認証の対象外にしたまま忘れる | 例外のアカウントだけが狙われて乗っ取られる | 例外は理由と期限を台帳に記録し、期限が来たら見直す |
| 届いたプッシュ通知を確かめずに承認する | パスワードを盗んだ攻撃者のログインを本人が許可してしまう | 「自分がログインしていない通知は拒否して報告する」と教育する。画面に表示された数字を入力させる方式（番号の照合）があれば有効にする |
| スマートフォンの紛失に備えていない | 本人がログインできなくなり、業務が止まる | リカバリコードの保管方法と、本人確認をしてから再設定する手順を決める |
| 退職者のアカウントを止め忘れる | 退職後もメールや VPN に入れる状態が残る | 退職の手続きの一覧にアカウント停止を入れ、定期的に棚卸しをする |
| パスワードの複雑さだけを細かく決める | 覚えられずにメモを貼る、使い回すといった運用が増える | 長さと使い回しの禁止を重視し、パスワード管理ソフトを認める |

## 事例

[みなと事務所](../../network/)（社員30名・2フロア）では、[リスクアセスメント](../cia/) で「メールアカウントの乗っ取り」のリスク値が最も高かったため、クラウドのメールサービスと、自宅や外出先から NAS を使うためのリモートアクセス VPN に多要素認証を導入しました。

**1. 方式の選定**

社員は全員が業務用スマートフォンを持っているので、二要素目は **認証アプリ（プッシュ通知の承認、使えないときはワンタイムパスワード）** にしました。
プッシュ通知では、ログイン画面に表示された2桁の数字をスマートフォンで入力する **番号の照合** を有効にし、内容を見ずに承認できないようにしました。
VPN は保守業者と相談し、VPN のログインもメールサービスと同じ ID 管理の仕組み（IdP）で認証する設定に変えました。これで VPN にも同じ多要素認証がかかり、退職時は IdP のアカウントを止めるだけでメールと VPN の両方が使えなくなります。

**2. 展開のスケジュール**

| 時期 | 対象 | 内容 |
| --- | --- | --- |
| 1週目 | 総務課長・所長（管理者アカウント） | 設定と手順書の作成。管理者アカウントは先に必須にする |
| 2〜3週目 | 営業の3名 | 試行。外出先で使う人を選び、困ることを洗い出す |
| 4〜5週目 | 全員 | 朝会で説明し、各フロアで登録会を開く。5週目の末日から必須に切り替える |

試行で、2名がノート PC の古いメールソフトでパスワードだけの接続方式を使っていて、必須にすると受信できなくなることが分かりました。全員分の設定を新しい接続方式に切り替えてから、古い接続方式を管理画面で無効にしました。

**3. 運用ルール**

- 自分がログインしていないのに届いた承認要求は **拒否して総務課長に報告** する。
- スマートフォンを紛失・機種変更したときは総務課長に申し出る。総務課長は **対面または所長への確認** で本人であることを確かめてから多要素認証をリセットする。電話やメールの依頼だけではリセットしない。
- リカバリコードは各自が印刷し、自宅など業務用スマートフォンとは別の場所に保管する。
- 退職時は、最終日に総務課長が IdP のアカウントを無効にし、翌月の棚卸しで残っていないことを確かめる。

**4. 残っていた例外**

問い合わせ窓口の共有アドレス（info@minato.example）は、総務の数名が交代で使うため「登録方法を決めてから」として例外にしていました。
この例外が期限を決めないまま残り、後にこのアカウントが乗っ取られることになります（[情報セキュリティマネジメント](../management/) の事例）。
その後、共有アドレスは各自のアカウントから共有メールボックスとして開く方式に変え、共有アカウントへの直接ログインをやめました。

## 試験対策のポイント

- **ITパスポート**: 3要素の分類と多要素認証の判定、ワンタイムパスワード・シングルサインオン・生体認証の特徴、FRR と FAR の意味が頻出です。「本人を拒否＝FRR、他人を受入れ＝FAR」と押さえます。
- **基本情報**: チャレンジレスポンス認証の流れ（パスワードが通信路を流れない理由）、パスワードリスト攻撃やリバースブルートフォース攻撃への対策、ソルトの効果、CAPTCHA の目的が問われます。
- **応用情報**: SAML・OpenID Connect による SSO の構成、OAuth（認可）との違い、FIDO によるパスワードレス認証、リスクベース認証など、方式を比較して設計に生かす問題に備えます。
