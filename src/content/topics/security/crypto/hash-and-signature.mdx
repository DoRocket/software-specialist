ハッシュ関数は任意の長さのデータから固定長の値（ハッシュ値）を作る関数で、データの改ざん検知に使われます。
これと公開鍵暗号の鍵ペアを組み合わせたものが **デジタル署名** で、「誰が作ったか」と「改ざんされていないか」を同時に確認できます。

## ハッシュ関数

暗号技術で使われる **暗号学的ハッシュ関数** には次の性質があります。

| 性質 | 意味 |
| --- | --- |
| 固定長出力 | 入力の長さにかかわらず、出力（ハッシュ値、メッセージダイジェスト）は一定の長さ |
| 一方向性（原像計算困難性） | ハッシュ値から元のデータを求めることが事実上できない |
| 衝突困難性 | 同じハッシュ値になる異なる2つのデータを見つけることが事実上できない |
| 第2原像計算困難性 | あるデータと同じハッシュ値になる別のデータを見つけることが事実上できない |

入力が1ビットでも変わればハッシュ値は大きく変化するため、ハッシュ値を比べることで改ざんを検知できます。

| 方式 | ハッシュ値の長さ | 現状 |
| --- | --- | --- |
| MD5 | 128 ビット | 衝突を見つける攻撃が実用的になっており、安全性が必要な用途には使わない |
| SHA-1 | 160 ビット | 衝突が実際に見つかっており、署名用途での利用は非推奨 |
| SHA-256（SHA-2 ファミリ） | 256 ビット | 現在広く使われている |
| SHA-3 | 224〜512 ビット | SHA-2 とは異なる構造の後継規格 |

ハッシュ値だけを送っても、攻撃者がデータとハッシュ値をまとめて差し替えれば改ざんを検知できません。そこで鍵を組み合わせた MAC やデジタル署名を使います。

## デジタル署名

公開鍵暗号の鍵ペアを、暗号化とは **逆向き** に使います。送信者が **自分の秘密鍵** で署名し、受信者は **送信者の公開鍵** で検証します。

### 署名の生成（送信者 A）

1. 送るメッセージからハッシュ値を求める。
2. そのハッシュ値を **A の秘密鍵** で暗号化（署名処理）して **デジタル署名** を作る。
3. メッセージとデジタル署名を一緒に送る。

### 署名の検証（受信者 B）

1. 受け取ったデジタル署名を **A の公開鍵** で復号（検証処理）し、ハッシュ値①を得る。
2. 受け取ったメッセージから同じハッシュ関数でハッシュ値②を求める。
3. ①と②が一致すれば検証成功。

生成から検証までの流れを、ステップごとに辿ってみましょう。

<DigitalSignatureFlow />

| 一致した場合にわかること | 理由 |
| --- | --- |
| 送信者が A 本人である（真正性） | A の公開鍵で検証できる署名は、A の秘密鍵でしか作れない |
| メッセージが改ざんされていない（完全性） | メッセージが変わればハッシュ値②が①と一致しない |
| A は送信を否認できない（否認防止） | 秘密鍵は A しか持っていない |

なお、デジタル署名だけではメッセージ本文は暗号化されないため、**機密性は確保されません**。機密性も必要な場合は、別途暗号化と組み合わせます。

また、ここで使う「A の公開鍵」が本当に A のものであることを保証するのが、PKI とデジタル証明書の役割です。

## メッセージ認証符号（MAC）

**共通鍵** とメッセージから認証用の短い値（MAC 値）を計算し、メッセージに付けて送る方式です。代表例はハッシュ関数を使う **HMAC** です。

- 受信者は同じ共通鍵で MAC 値を計算し直し、一致すれば改ざんがなく、鍵を共有している相手が作ったことを確認できます。
- ただし送信者と受信者が同じ鍵を持つため、**どちらが作ったかを第三者に証明できず、否認防止にはなりません**。

| 項目 | ハッシュ値のみ | MAC | デジタル署名 |
| --- | --- | --- | --- |
| 使う鍵 | なし | 共通鍵 | 公開鍵暗号の鍵ペア |
| 改ざん検知（完全性） | 偶発的な誤りは検知可、意図的な差替えは不可 | ○ | ○ |
| 作成者の確認（真正性） | × | ○（鍵の共有者であること） | ○ |
| 否認防止 | × | × | ○ |

## 実際の進め方

### ハッシュ値でファイルの改ざん・破損を確かめる

ソフトウェアや機器のファームウェア（機器に組み込まれた制御用のソフトウェア）の配布ページには、ファイルと一緒に SHA-256 のハッシュ値が掲載されていることがあります。
ダウンロードしたファイルのハッシュ値を自分で計算して比べると、途中で壊れたり差し替えられたりしていないかを確かめられます。

```text
# Linux
$ sha256sum nas-fw-4.2.1.bin
17a61e4176c46d197d3c1491a41a237d899b2a6dd64c401ab7d551a69222618b  nas-fw-4.2.1.bin

# macOS
$ shasum -a 256 nas-fw-4.2.1.bin

# Windows（PowerShell。既定のアルゴリズムが SHA256）
PS> Get-FileHash .\nas-fw-4.2.1.bin

Algorithm       Hash                                                                   Path
---------       ----                                                                   ----
SHA256          17A61E4176C46D197D3C1491A41A237D899B2A6DD64C401AB7D551A69222618B       C:\Users\...

# Windows（コマンドプロンプト）
> certutil -hashfile nas-fw-4.2.1.bin SHA256
```

ファイル名とハッシュ値はこの記事のための例です。表示される 64 文字は 16進数で、$256 \div 4 = 64$ 文字（16進数1文字が 4 ビット）になります。
Windows では大文字、Linux では小文字で表示されますが、16進数なので大文字・小文字の違いは同じ値です。

目で 64 文字を比べると見落としやすいので、比較もコマンドに任せます。

```text
# Linux: 「ハッシュ値  ファイル名」の行を書いたファイルを用意して照合する
$ sha256sum -c SHA256SUMS
nas-fw-4.2.1.bin: OK

# 一致しない場合
nas-fw-4.2.1.bin: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match

# PowerShell: 配布ページの値と比べる（文字列の -eq は大文字・小文字を区別しない）
PS> (Get-FileHash .\nas-fw-4.2.1.bin).Hash -eq '17a61e4176c46d197d3c1491a41a237d899b2a6dd64c401ab7d551a69222618b'
True
```

入力が少し違うだけでハッシュ値はまったく変わります。たとえば「見積書 合計 120,000円」と「見積書 合計 720,000円」（1文字だけ違う）を書いたテキストファイルの SHA-256 は、次のように似ても似つかない値になります。

```text
06074ad0b5072726f80ae39ea71813a21ac60e2dcc4a80a2f6555af93d6ceaeb  （120,000円）
32d2da1c6d77e8cc45789a106956fdcc2d3106657bfd24f62766c9c8038e4482  （720,000円）
```

### ハッシュ値の比較で分かること・分からないこと

| 状況 | ハッシュ値の比較で検知できるか | 補う方法 |
| --- | --- | --- |
| ダウンロードの途中でファイルが壊れた | できる | もう一度ダウンロードする |
| 配布ファイルが置かれたミラーサーバでだけ差し替えられた | できる（ハッシュ値を正規のサイトから HTTPS で入手した場合） | ハッシュ値は配布元の公式ページから入手する |
| 配布元のサーバが乗っ取られ、ファイルとハッシュ値の両方が差し替えられた | できない | 配布元の秘密鍵によるデジタル署名を検証する |
| 正規の開発元が配布したが、ファイル自体に問題があった | できない | ハッシュ値は「同じかどうか」しか示さない |

MD5 や SHA-1 のハッシュ値しか掲載されていない場合、偶然の破損は検知できますが、意図的に同じハッシュ値のファイルを作る攻撃には備えられません。SHA-256 などの値や署名が提供されていれば、そちらを使います。

### デジタル署名を確かめる

- **ソフトウェアのコード署名**: 開発元が配布するプログラムに、開発元の秘密鍵で署名したもの。Windows では、実行ファイルのプロパティの「デジタル署名」タブで署名者を確認できる。署名者の名前が期待した開発元と違う、または署名がない場合は実行しない。
- **PDF の電子署名**: 署名付きの PDF を対応するビューアで開くと、署名パネルに「署名は有効」かどうかと署名者が表示される。署名後に内容が変更されていると、無効または変更ありと表示される。
- **機器のファームウェア**: 多くの機器は、更新時にファームウェアに付いた開発元の署名を機器自身が検証し、検証に失敗すると更新を中止する。

いずれも、裏側では本文で説明した「ハッシュ値を求め、署名者の公開鍵で検証する」処理が行われています。

### よくある失敗と対策

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| ファイルと同じ非公式のサイトに載っているハッシュ値と比べる | ファイルと一緒に差し替えられた値と比べても意味がない | ハッシュ値は開発元の公式ページから入手する |
| 64 文字を先頭と末尾だけ目で比べる | 途中が違っていても見落とす | `sha256sum -c` や `-eq` で比べる |
| ハッシュ値が一致したので「安全なソフト」だと判断する | 正規のファイルに問題があった場合や、入手元自体が偽物の場合は防げない | 入手元と署名者を確かめ、不要なソフトは入れない |
| パスワードの保存に、ソルトなしの高速なハッシュ関数をそのまま使う | 漏えいしたとき、事前計算した表や総当たりで元のパスワードが割り出されやすい | パスワードの保存には、ソルトとストレッチングを組み込んだ専用の方式を使う（[認証技術](../../authentication/) を参照） |

## 事例

[みなと事務所](../../../network/)（社員30名・2フロア）では、NAS（192.168.20.10）のファームウェアを更新するとき、総務課長が次の手順で確認しています。

**1. ダウンロードと照合**

NAS の開発元の公式サイトから新しいファームウェアのファイルをダウンロードし、同じページに掲載された SHA-256 の値と比べました。

```text
PS> (Get-FileHash .\nas-fw-4.2.1.bin).Hash -eq '17a61e4176c46d197d3c1491a41a237d899b2a6dd64c401ab7d551a69222618b'
False
```

結果は `False` でした。ファイルのサイズを確かめると、公式ページの記載より小さく、ダウンロードが途中で切れていたことが分かりました。
もう一度ダウンロードすると `True` になり、このファイルで更新することにしました。

**2. 更新**

保守業者の立会いのもと、業務時間外に NAS を更新しました。更新の前には、外付けディスクへのバックアップが最新であることを確かめています。
更新の画面では、NAS 自身がファームウェアの署名を検証し、「署名の検証に成功しました」と表示されてから書き込みが始まりました。
更新後は、NAS の管理画面でファームウェアの版が新しくなったことと、社員の PC から共有フォルダを開けることを確かめ、作業の記録に版とハッシュ値を書き残しました。

**3. 電子契約の確認**

同じころ、取引先との業務委託契約を電子署名付きの PDF で交わすことになりました。
受け取った PDF を開くと署名パネルに「署名は有効」と、取引先の会社名が署名者として表示されました。
事務所側でも署名して返送し、署名済みの PDF は NAS の「契約」フォルダに保存しています。後から内容が書き換えられれば、署名の検証で分かります。

## 試験対策のポイント

- **ITパスポート**: 「デジタル署名は **送信者の秘密鍵** で作成し、**送信者の公開鍵** で検証する」と、署名でわかること（本人であること・改ざんされていないこと）が頻出です。暗号化（受信者の公開鍵で暗号化）との取り違えに注意します。
- **基本情報**: 署名の生成・検証の手順を並べ替える問題、ハッシュ関数の性質（一方向性・衝突困難性）、デジタル署名で確保できない要素（機密性）を選ぶ問題が出ます。
- **応用情報**: MAC とデジタル署名の違い（否認防止の可否）、ハッシュ関数の危殆化と移行、タイムスタンプとの組合せなど、方式を比較して選ぶ力が問われます。
