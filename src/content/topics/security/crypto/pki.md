公開鍵暗号やデジタル署名は、「その公開鍵が本当に相手のものか」が保証されていないと成り立ちません。
**PKI**（Public Key Infrastructure: 公開鍵基盤）は、信頼できる第三者である **認証局（CA）** が公開鍵とその持ち主の対応を **デジタル証明書** で保証する仕組みです。

## なぜ PKI が必要か

攻撃者が「私は B です」と偽って自分の公開鍵を配布すると、A は B 宛てのつもりで攻撃者の公開鍵を使って暗号化してしまい、内容を読まれます（なりすまし・中間者攻撃）。
これを防ぐため、公開鍵に「この鍵は確かに B のものである」という CA の署名を付けたものがデジタル証明書です。

## デジタル証明書

デジタル証明書（公開鍵証明書）の形式は **X.509** として標準化されています。主な記載内容は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| シリアル番号 | 発行した CA の中で証明書を一意に識別する番号 |
| 発行者 | 証明書を発行した CA の名前 |
| 有効期間 | 証明書が有効な開始日時と終了日時 |
| 主体者（サブジェクト） | 証明書の持ち主（Web サーバの場合はドメイン名など） |
| 公開鍵 | 持ち主の公開鍵 |
| CA のデジタル署名 | 上記の内容に対して **CA の秘密鍵** で付けた署名 |

証明書に **持ち主の秘密鍵は含まれません**。

### 発行と検証の流れ

1. 申請者（例: Web サーバの運営者）が鍵ペアを生成し、公開鍵を含む証明書署名要求（CSR）を CA に提出する。
2. CA（実務上は登録局 RA が審査を担う場合もある）が申請者の実在性やドメインの管理権限を確認し、**CA の秘密鍵** で署名した証明書を発行する。
3. 利用者は、証明書の署名を **CA の公開鍵** で検証し、有効期間や失効の有無も確認したうえで、記載された公開鍵を信頼する。

## 証明書チェーン（信頼の連鎖）

CA の公開鍵自体も、上位の CA が発行した証明書で保証されます。この階層構造をたどった最上位が **ルート CA** で、ルート CA の証明書は自分自身で署名した **自己署名証明書** です。

| 階層 | 証明書 | 誰が署名するか |
| --- | --- | --- |
| ルート CA | ルート証明書 | ルート CA 自身（自己署名） |
| 中間 CA | 中間 CA 証明書 | ルート CA |
| サーバ | サーバ証明書 | 中間 CA |

利用者は、サーバ証明書 → 中間 CA 証明書 → ルート証明書 と順に署名を検証し、最後に **OS やブラウザにあらかじめ組み込まれた信頼済みのルート証明書** にたどり着けば、サーバ証明書を信頼します。

## 証明書の失効

秘密鍵の漏えいや記載内容の変更があると、有効期間内でも証明書を **失効** させます。失効の確認方法には次の2つがあります。

| 方式 | 仕組み |
| --- | --- |
| CRL（証明書失効リスト） | CA が失効した証明書のシリアル番号と失効日時を一覧にして公開する。CA の署名付き |
| OCSP | 個々の証明書の失効状態を OCSP レスポンダにオンラインで問い合わせ、リアルタイムに近い状態を得る |

CRL は一覧を定期的に取得する必要があり、リストが大きくなると扱いにくくなります。OCSP はこの点を改善し、証明書1枚単位で問い合わせられます。

## TLS との関係

HTTPS で使われる **TLS** では、PKI が次のように使われます。

1. クライアント（ブラウザ）がサーバに接続すると、サーバは **サーバ証明書**（と中間 CA 証明書）を送る。
2. クライアントは証明書チェーンを検証し、接続先のドメイン名と証明書の主体者が一致すること、有効期間内であることを確認する。これで **サーバの真正性** を確認できる。
3. 鍵交換によりセッション鍵（共通鍵）を共有し、以降の通信を **共通鍵暗号で暗号化** して機密性と完全性を確保する。

このように TLS は、PKI（サーバ認証）、公開鍵暗号と鍵交換（鍵の共有）、共通鍵暗号（高速な暗号化）を組み合わせたプロトコルです。必要に応じて **クライアント証明書** によるクライアント認証も行えます。

## 実際の進め方

### ブラウザで証明書を確かめる

HTTPS のサイトを開いたとき、アドレスバーの左のアイコン（鍵などのマーク）を選ぶと、接続が保護されているかと証明書の情報を表示できます（表示の位置や文言はブラウザによって異なります）。
証明書の詳細では、次の点を確かめます。

| 項目 | 確かめること |
| --- | --- |
| 発行先（主体者、サブジェクト代替名） | 開いているサイトのドメイン名が含まれているか。サーバ証明書のドメイン名は、主体者の CN よりも **サブジェクト代替名（SAN）** の欄で確かめる |
| 発行者 | 中間 CA の名前。証明書の階層（チェーン）を表示すると、ルート CA までの並びが見える |
| 有効期間 | 期限が切れていないか、まもなく切れないか |

なお、証明書が正しく検証できることは「通信相手がそのドメインの持ち主である」ことを示すだけで、サイトの運営者が信頼できるかどうかまでは示しません。フィッシングサイトでも、自分で取得したドメインの証明書を使えば警告は出ません。

### コマンドで確かめる（openssl）

サーバの管理者は、`openssl` コマンドで証明書を確かめられます（Linux・macOS に多くの場合入っています）。次の出力は形式を示すための例で、名前や日付は架空です。

```text
$ openssl s_client -connect www.minato.example:443 -servername www.minato.example < /dev/null
CONNECTED(00000003)
---
Certificate chain
 0 s:CN = www.minato.example
   i:C = JP, O = Example Trust, CN = Example Trust DV CA
   ...
 1 s:C = JP, O = Example Trust, CN = Example Trust DV CA
   i:C = JP, O = Example Trust, CN = Example Trust Root CA
   ...
---
（中略）
Verify return code: 0 (ok)
```

- `Certificate chain` の `0` がサーバ証明書、`1` が中間 CA 証明書です。`s:` は主体者、`i:` は発行者で、0 の発行者が 1 の主体者になっている（チェーンがつながっている）ことが分かります。
- `-servername` は、1台のサーバで複数のドメインを扱うときに、どのドメインの証明書がほしいかを伝える指定（SNI）です。
- 最後の `Verify return code` が `0 (ok)` なら、手元の信頼済みルート証明書までの検証に成功しています。

有効期間などを取り出して見るには、受け取った証明書を `openssl x509` に渡します。

```text
$ openssl s_client -connect www.minato.example:443 -servername www.minato.example < /dev/null 2>/dev/null \
    | openssl x509 -noout -subject -issuer -dates
subject=CN = www.minato.example
issuer=C = JP, O = Example Trust, CN = Example Trust DV CA
notBefore=Jun  1 00:00:00 2026 GMT
notAfter=Aug 30 23:59:59 2026 GMT

# 30日（2,592,000 秒）以内に期限が切れるかどうか
$ openssl s_client ... | openssl x509 -noout -checkend 2592000
Certificate will not expire
```

`-checkend` は、指定した秒数のうちに期限が切れるなら `Certificate will expire` と表示して終了コード 1 を返すので、定期的に実行して期限切れを事前に知らせる仕組みにも使えます（30日 = $30 \times 24 \times 60 \times 60 = 2{,}592{,}000$ 秒）。表示の細かい形式は OpenSSL の版によって異なります。

### よく見る警告と原因

| 症状 | `Verify return code` の例 | 主な原因 | 対処 |
| --- | --- | --- | --- |
| 有効期限切れの警告 | `10 (certificate has expired)` | 更新を忘れた | 更新して入れ替える。手順と期限の管理を見直す |
| 名前が一致しない警告 | （名前は別に確かめる） | 別のドメイン用の証明書を設定した、`www` の有無を SAN に含めていない | 必要なドメイン名をすべて SAN に含めて取り直す |
| 一部の端末でだけ「発行者を確認できない」 | `20 (unable to get local issuer certificate)` | サーバに **中間 CA 証明書** を設定していない | サーバ証明書と中間 CA 証明書をつなげた形（チェーン）で設定する |
| 自己署名証明書の警告 | `18 (self-signed certificate)` | 機器の初期設定の証明書をそのまま使っている | 社外に公開するサーバでは CA の証明書を使う。社内機器では運用で扱いを決める |
| どのサイトでも警告が出る | ― | 端末の時刻が大きくずれている | 端末の時刻を正しく合わせる |

ブラウザは、足りない中間 CA 証明書を自分で補って検証することがあるため、中間 CA 証明書の設定漏れは「PC では見えるが、一部のスマートフォンや他のシステムからはエラー」という形で現れやすくなります。

### 証明書の更新を運用する

1. **証明書の台帳を作る**: 自社が使っている証明書（Web サイト、VPN、機器の管理画面など）を一覧にし、ドメイン名・発行者・期限・更新方法・担当者・期限の通知先を書く。
2. **できるだけ自動で更新する**: 証明書の発行と更新を自動で行う仕組み（ACME というプロトコルを使うものなど）に対応したサーバやレンタルサーバの機能を使う。
3. **期限の通知を個人に頼らない**: CA からの更新案内の宛先を、担当者個人ではなく共有のアドレスにする。台帳の期限をカレンダーに登録する。
4. **更新後に確かめる**: 入れ替えたら、ブラウザと `openssl s_client` で、期限・ドメイン名・チェーン（中間 CA 証明書）を確かめる。
5. **秘密鍵を守る**: 証明書と対になる秘密鍵はサーバの外に持ち出さない。漏えいの疑いがあれば、証明書を失効させて鍵ペアから作り直す。

公的な CA が発行するサーバ証明書の有効期間は、業界団体のルールで段階的に短くされてきており、手作業の更新では漏れや作業の負担が増えています。自動更新を前提に運用を組み立てることが大切です。

### よくある失敗と対策

| 失敗 | 起きること | 対策 |
| --- | --- | --- |
| 更新案内の宛先が退職者や異動者の個人アドレスのまま | 案内に誰も気付かず、期限切れでサイトに警告が出る | 宛先を共有アドレスにし、台帳とカレンダーで期限を管理する |
| サーバ証明書だけを入れ替え、中間 CA 証明書を設定しない | 一部の端末やシステムからだけ接続エラーになる | チェーンで設定し、`openssl s_client` で `0 (ok)` を確かめる |
| 自動更新に任せきりにする | DNS やサーバの設定変更で自動更新が失敗しても気付かない | 失敗の通知を受け取る設定にし、`-checkend` などで期限を定期的に確かめる |
| 社内機器の証明書の警告を「いつものこと」として無視させる | 本物の中間者攻撃の警告も無視する習慣がつく | 警告が出ない構成にするか、社内の機器の扱いを手順書で決める |

## 事例

[みなと事務所](../../../network/)（社員30名・2フロア）の自社サイト www.minato.example（レンタルサーバ 198.51.100.20）で起きた、サーバ証明書の期限切れ障害です。

**1. 発生**

6月1日の朝、取引先から「御社のサイトを開くと、安全ではないという警告が出る」と連絡がありました。総務課長が確かめると、ブラウザに有効期限切れの警告が表示され、`openssl s_client` では次のようになっていました。

```text
notAfter=May 31 23:59:59 2026 GMT
Verify return code: 10 (certificate has expired)
```

証明書は1年ごとに手作業で更新する有料のもので、CA からの更新案内は、サイトを立ち上げたときの担当者（すでに退職）の個人アドレスに送られていました。

**2. 復旧と2つ目の問題**

総務課長は同じ日に新しい証明書を取得してレンタルサーバに設定し、PC のブラウザで警告が消えたことを確かめました。
ところが翌日、取引先から「社内のシステムで御社サイトのお知らせを自動で取り込む処理が、接続エラーで止まっている」と連絡がありました。`openssl s_client` で確かめると、`Certificate chain` に `0`（サーバ証明書）しかなく、`Verify return code: 20 (unable to get local issuer certificate)` と表示されました。
サーバ証明書だけを設定し、中間 CA 証明書を設定していなかったのが原因でした。PC のブラウザは中間 CA 証明書を自分で補っていたため、前日の確認では気付けませんでした。
中間 CA 証明書を設定すると、`Certificate chain` に `1` が表示され、`Verify return code: 0 (ok)` になりました。

**3. 再発防止**

- 証明書を、レンタルサーバの自動更新機能（ACME を使う証明書）に切り替えました。中間 CA 証明書の設定も自動で行われます。
- 事務所で使う証明書の台帳を作りました。

| 証明書 | 発行者 | 期限 | 更新方法 | 担当・通知先 |
| --- | --- | --- | --- | --- |
| www.minato.example | 公的な CA | 約90日（期限の前に自動で更新） | レンタルサーバの自動更新 | 総務課長・共有アドレス |
| ルータ（リモートアクセス VPN） | 公的な CA | 台帳に記載 | 保守業者が手動で更新（期限の60日前にカレンダーで通知） | 保守業者・総務課長 |
| NAS の管理画面 | NAS 自身（自己署名） | 台帳に記載 | 社内からだけ接続するため、管理用 PC にこの証明書を信頼済みとして登録して運用 | 総務課長 |

- 月に1回、`openssl x509 -checkend` で、30日以内に期限が切れる証明書がないかを確かめています。

## 試験対策のポイント

- **ITパスポート**: 認証局の役割（公開鍵の持ち主を証明する）、デジタル証明書が HTTPS で使われることを押さえます。「証明書には秘密鍵は含まれない」も選択肢の判断で役立ちます。
- **基本情報**: 証明書の検証に使う鍵（CA の公開鍵）、CRL に記載される内容（失効した証明書のシリアル番号など）、ルート証明書が自己署名であることが問われます。
- **応用情報**: 証明書チェーンの検証手順、CRL と OCSP の比較、TLS ハンドシェイクでのサーバ認証の流れ、サーバ証明書の種類（DV・OV・EV）など、運用を含めた理解が求められます。
