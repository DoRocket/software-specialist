公開鍵暗号やデジタル署名は、「その公開鍵が本当に相手のものか」が保証されていないと成り立ちません。
**PKI**（Public Key Infrastructure: 公開鍵基盤）は、信頼できる第三者である **認証局（CA）** が公開鍵とその持ち主の対応を **デジタル証明書** で保証する仕組みです。

## なぜ PKI が必要か

攻撃者が「私は B です」と偽って自分の公開鍵を配布すると、A は B 宛てのつもりで攻撃者の公開鍵を使って暗号化してしまい、内容を読まれます（なりすまし・中間者攻撃）。
これを防ぐため、公開鍵に「この鍵は確かに B のものである」という CA の署名を付けたものがデジタル証明書です。

## デジタル証明書

デジタル証明書（公開鍵証明書）の形式は **X.509** として標準化されています。主な記載内容は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| シリアル番号 | 発行した CA の中で証明書を一意に識別する番号 |
| 発行者 | 証明書を発行した CA の名前 |
| 有効期間 | 証明書が有効な開始日時と終了日時 |
| 主体者（サブジェクト） | 証明書の持ち主（Web サーバの場合はドメイン名など） |
| 公開鍵 | 持ち主の公開鍵 |
| CA のデジタル署名 | 上記の内容に対して **CA の秘密鍵** で付けた署名 |

証明書に **持ち主の秘密鍵は含まれません**。

### 発行と検証の流れ

1. 申請者（例: Web サーバの運営者）が鍵ペアを生成し、公開鍵を含む証明書署名要求（CSR）を CA に提出する。
2. CA（実務上は登録局 RA が審査を担う場合もある）が申請者の実在性やドメインの管理権限を確認し、**CA の秘密鍵** で署名した証明書を発行する。
3. 利用者は、証明書の署名を **CA の公開鍵** で検証し、有効期間や失効の有無も確認したうえで、記載された公開鍵を信頼する。

## 証明書チェーン（信頼の連鎖）

CA の公開鍵自体も、上位の CA が発行した証明書で保証されます。この階層構造をたどった最上位が **ルート CA** で、ルート CA の証明書は自分自身で署名した **自己署名証明書** です。

| 階層 | 証明書 | 誰が署名するか |
| --- | --- | --- |
| ルート CA | ルート証明書 | ルート CA 自身（自己署名） |
| 中間 CA | 中間 CA 証明書 | ルート CA |
| サーバ | サーバ証明書 | 中間 CA |

利用者は、サーバ証明書 → 中間 CA 証明書 → ルート証明書 と順に署名を検証し、最後に **OS やブラウザにあらかじめ組み込まれた信頼済みのルート証明書** にたどり着けば、サーバ証明書を信頼します。

## 証明書の失効

秘密鍵の漏えいや記載内容の変更があると、有効期間内でも証明書を **失効** させます。失効の確認方法には次の2つがあります。

| 方式 | 仕組み |
| --- | --- |
| CRL（証明書失効リスト） | CA が失効した証明書のシリアル番号と失効日時を一覧にして公開する。CA の署名付き |
| OCSP | 個々の証明書の失効状態を OCSP レスポンダにオンラインで問い合わせ、リアルタイムに近い状態を得る |

CRL は一覧を定期的に取得する必要があり、リストが大きくなると扱いにくくなります。OCSP はこの点を改善し、証明書1枚単位で問い合わせられます。

## TLS との関係

HTTPS で使われる **TLS** では、PKI が次のように使われます。

1. クライアント（ブラウザ）がサーバに接続すると、サーバは **サーバ証明書**（と中間 CA 証明書）を送る。
2. クライアントは証明書チェーンを検証し、接続先のドメイン名と証明書の主体者が一致すること、有効期間内であることを確認する。これで **サーバの真正性** を確認できる。
3. 鍵交換によりセッション鍵（共通鍵）を共有し、以降の通信を **共通鍵暗号で暗号化** して機密性と完全性を確保する。

このように TLS は、PKI（サーバ認証）、公開鍵暗号と鍵交換（鍵の共有）、共通鍵暗号（高速な暗号化）を組み合わせたプロトコルです。必要に応じて **クライアント証明書** によるクライアント認証も行えます。

## 試験対策のポイント

- **ITパスポート**: 認証局の役割（公開鍵の持ち主を証明する）、デジタル証明書が HTTPS で使われることを押さえます。「証明書には秘密鍵は含まれない」も選択肢の判断で役立ちます。
- **基本情報**: 証明書の検証に使う鍵（CA の公開鍵）、CRL に記載される内容（失効した証明書のシリアル番号など）、ルート証明書が自己署名であることが問われます。
- **応用情報**: 証明書チェーンの検証手順、CRL と OCSP の比較、TLS ハンドシェイクでのサーバ認証の流れ、サーバ証明書の種類（DV・OV・EV）など、運用を含めた理解が求められます。
