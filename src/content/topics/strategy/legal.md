情報システムの開発・利用には、ソフトウェアなどの知的財産を守る法律、不正なアクセスを禁じる法律、個人情報の取扱いを定める法律、外部に作業を依頼するときの契約形態など、さまざまな法的ルールが関わります。
後半では、開発を委託するときに契約書で確認する点と、個人情報の取扱いルールの作り方を、架空の IT 企業の事例で見ます（このページは学習のための説明で、個別の案件についての法的助言ではありません）。

## 前提となる用語

| 用語 | 意味 |
| --- | --- |
| 発注者・受注者 | 仕事を依頼する側と、引き受ける側。準委任では依頼する側を委任者、引き受ける側を受任者ともいう |
| 検収 | 納品された成果物が契約どおりかを発注者が確かめ、受け入れること。請負では、検収の結果が支払いや責任の起点になることが多い |
| 契約不適合責任 | 引き渡した成果物が、種類・品質・数量などで契約の内容に合っていないときに、受注者が負う責任。修補などの対応を求められる |
| 再委託 | 受注者が、引き受けた仕事の一部をさらに別の会社に任せること |
| 個人データ | 個人情報データベース等（検索できるように整理した個人情報の集まり）を構成する個人情報。第三者提供や安全管理のルールはこれが対象 |

## 知的財産権

知的財産権は、大きく **著作権** と **産業財産権** に分かれます。

| 権利 | 保護対象 | 権利の発生 | 存続期間（原則） |
| --- | --- | --- | --- |
| 著作権 | 思想・感情の創作的な表現（文章、音楽、プログラムなど） | 創作した時点で自動的に発生（登録不要） | 著作者の死後70年 |
| 特許権 | 発明（高度な技術的アイデア） | 出願・審査を経て登録 | 出願から20年 |
| 実用新案権 | 物品の形状・構造などの考案 | 出願・登録（実体審査なし） | 出願から10年 |
| 意匠権 | 物品などのデザイン | 出願・審査を経て登録 | 出願から25年 |
| 商標権 | 商品・サービスに使うマーク（ロゴ、名称など） | 出願・審査を経て登録 | 登録から10年（更新可） |

### 著作権とプログラム

- プログラムは著作物として保護されますが、**プログラム言語、規約（プロトコルなど）、解法（アルゴリズム）** は保護されません。
- 法人などの業務に従事する者が職務上作成したプログラムは、契約や勤務規則に別段の定めがなければ、**法人が著作者** になります（職務著作）。
- 開発を外部に委託した場合、契約で権利の帰属を定めなければ、著作権は **実際に作成した側（受託者）** に帰属します。

## 不正アクセス禁止法

正式名称は「不正アクセス行為の禁止等に関する法律」です。アクセス制御機能をもつコンピュータへの不正なアクセスを禁止します。

| 禁止される行為の例 |
| --- |
| 他人の ID・パスワードを無断で使用してログインする（不正アクセス行為） |
| セキュリティ上の弱点を突いてアクセス制御を回避する（不正アクセス行為） |
| 他人の ID・パスワードを本人に無断で第三者に提供する（不正アクセスを助長する行為） |
| 不正アクセスの目的で他人の ID・パスワードを取得・保管する |
| 正規のサイトを装って ID・パスワードの入力を求める（フィッシング行為） |

アクセス制御機能がないコンピュータへのアクセスは、この法律の不正アクセス行為には当たりません。

## 個人情報保護法

正式名称は「個人情報の保護に関する法律」です。

| 用語 | 内容 |
| --- | --- |
| 個人情報 | 生存する個人に関する情報で、特定の個人を識別できるもの（氏名、顔画像など）。個人識別符号（マイナンバー、旅券番号など）を含むもの |
| 要配慮個人情報 | 人種、信条、病歴、犯罪の経歴など、不当な差別や偏見が生じないよう特に配慮が必要なもの。取得には原則として本人の同意が必要 |
| 匿名加工情報 | 特定の個人を識別できず、元の個人情報を復元できないように加工した情報 |

主なルールは次のとおりです。

- 利用目的をできる限り特定し、その範囲内で利用する。
- 個人データを第三者に提供するときは、原則として **本人の同意** が必要（法令に基づく場合などの例外あり）。
- 本人の求めに応じて提供を停止することを前提に、同意なしで第三者提供できる **オプトアウト** の仕組みがあるが、要配慮個人情報には使えない。
- 業務委託先への提供は第三者提供に当たらないが、委託元は委託先を監督する義務を負う。

## 請負・準委任・労働者派遣

システム開発を外部に依頼する際の契約形態です。**誰が作業者に指揮命令するか** が最大のポイントです。

| 形態 | 義務の内容 | 作業者への指揮命令 |
| --- | --- | --- |
| 請負契約 | **仕事の完成** に対して報酬を支払う。成果物が契約内容に適合しない場合、受注者は契約不適合責任を負う | 受注者（請負事業者）が行う |
| 準委任契約 | 事務処理の **遂行** を委託する。受任者は善良な管理者の注意（善管注意義務）をもって業務を行う | 受任者が行う |
| 労働者派遣 | 派遣元が雇用する労働者を派遣先で働かせる | **派遣先** が行う |

- 請負契約なのに発注者が受注者の作業者に直接指示を出すことは、実態が労働者派遣と変わらない **偽装請負** として問題になります。
- 派遣先が、受け入れた派遣労働者をさらに別の会社へ派遣すること（二重派遣）は禁止されています。

## 実際の進め方

### 開発を委託するときに契約書で確認すること

契約書は、トラブルが起きたときに「どちらが、何を、どこまで負うか」を決める根拠です。システム開発の契約でよく確認される項目の例です。経済産業省や IPA がシステム開発のモデル契約書を公表しており、条項を検討するときの参考になります。

| 項目 | 確認すること |
| --- | --- |
| 契約形態 | 工程ごとに、仕事の完成を約束する **請負** か、作業の遂行を委託する **準委任** か。要件定義のように内容を一緒に決める工程は準委任、設計が固まった後の開発は請負、と工程ごとに契約を分ける考え方がある |
| 業務の範囲と成果物 | 何をするか、何を納めるか（プログラム、設計書、試験結果など）。範囲外の作業の扱い |
| 役割分担 | 発注者がすること（要件の決定、資料の提供、受入れ試験など）。発注者の協力が遅れたときの扱い |
| 検収 | 受入れ試験の期間、合格の基準、期間内に結果を通知しなかったときの扱い |
| 契約不適合責任 | 不具合が見つかったときに、受注者が修補などに応じる期間と範囲 |
| 報酬と支払 | 請負は完成・引渡しに対して、準委任は作業の時間や期間に対して支払うのが基本。支払の時期 |
| 仕様の変更 | 変更を申し入れる手続、費用と納期の見直し方 |
| 知的財産権 | 著作権を発注者に譲渡するか、受注者に残して利用を許諾するか。受注者が他の案件でも使う汎用的な部品の扱い |
| 秘密保持・個人情報 | 秘密情報の範囲、個人データを扱う場合の安全管理、契約終了時の返却・削除 |
| 再委託 | 再委託してよいか（事前の承諾を条件にするなど）、再委託先にも同じ義務を負わせるか |
| 損害賠償 | 賠償の範囲と上限 |
| 指揮命令 | 請負・準委任では、作業者への指示は受注者の責任者を通じて行う（偽装請負を防ぐ） |

著作権を譲渡する契約では、プログラムを改変する権利（翻案権など）も譲渡の対象として明記しないと、譲渡した側に残ると推定されるため、明記するのが一般的です。
また、著作者人格権は譲渡できないため、「受注者は著作者人格権を行使しない」と定めることがよくあります。

### 個人情報の取扱いルールの作り方

個人情報保護法の義務を、自社の業務で誰が何をするかに落とし込んだものが、社内の取扱いルール（規程）です。おおむね次の順に作ります。

1. **個人情報を洗い出す** … どの業務で、どんな個人情報を、どこから取得し、何に使い、どこに保管し、誰が見られ、いつ消すかを台帳にまとめます。委託先に渡しているものも含めます。
2. **利用目的を特定し、通知・公表する** … 利用目的をできる限り特定し、プライバシーポリシーなどで公表します。目的に必要のない項目は取得しないようにします。
3. **安全管理措置を決める** … 個人情報保護委員会のガイドラインでは、組織的・人的・物理的・技術的な安全管理措置などに分けて示されています。例えば、責任者と取扱いの手順を決める（組織的）、従業員を教育する（人的）、書類や機器の持出しを管理する（物理的）、アクセスできる人を限定し記録を残す（技術的）といった措置です。
4. **委託先を管理する** … 委託先を選ぶ基準を決め、契約で安全管理・再委託の条件・終了時の削除を定め、取扱いの状況を確認します。委託元には委託先を監督する義務があります。
5. **第三者提供の扱いを決める** … 第三者に提供する場面を洗い出し、原則として本人の同意を得る手順を決めます。
6. **本人からの請求に応じる窓口を作る** … 開示などの請求を受け付ける窓口と手順を決めます。
7. **漏えい等への対応手順を決める** … 発見したときの報告経路、影響の調査、再発防止の手順を決めます。一定の漏えい等が起きたときは、個人情報保護委員会への報告と本人への通知が法律で義務付けられているので、その判断の手順も含めます。
8. **教育と点検を続ける** … 定期的に教育し、ルールが守られているかを点検して見直します。

### よくある失敗と対策

| 失敗 | 対策 |
| --- | --- |
| 請負契約なのに、発注者が受注者の作業者に直接作業を指示する | 指示は受注者の責任者を通じて行う。日々の連絡の窓口を決めておく |
| 契約で著作権の帰属を決めず、後から改修や他社への保守の委託でもめる | 譲渡か利用許諾か、汎用部品の扱いを契約で決める |
| 内容が決まっていない工程まで請負の一括契約にし、仕様変更のたびに紛争になる | 工程ごとに契約を分け、要件が固まってから開発の請負契約を結ぶ |
| 開発や試験に本番の個人データをそのまま使い、委託先から漏えいする | 試験では個人を識別できないよう加工したデータを使う。委託先の取扱いを契約で縛り、確認する |
| 個人情報の所在を把握しておらず、漏えい時に影響範囲が分からない | 台帳で、どこに何があるかを管理し、変更のたびに更新する |
| 利用目的を広く曖昧に書き、新しい使い方が目的の範囲か判断できない | 利用目的を具体的に書き、新しい使い方を始める前に目的との関係を確かめる |

## 事例

架空の企業 **ツバメ情報システム** が、予約・顧客管理 SaaS **「ヨヤクル」** の事前決済の機能を開発したときの、契約と個人情報の扱いです（数値・状況は架空の設定です。法令の当てはめは個別の事情で変わるため、実際の案件では専門家に確認してください）。
決済代行サービスの選定は [システム戦略とシステム企画](../system-strategy/) の事例で扱いました。連携部分の開発は、自社の人員が足りないため、協力会社の K 社（架空）に一部を委託しました。

**① 契約形態**: 工程ごとに契約を分けました。

| 工程 | 契約形態 | 理由 |
| --- | --- | --- |
| 要件定義の支援 | 準委任 | 事前決済の画面や返金の流れを、店舗の意見を聞きながらツバメ情報システムが決める。K 社には専門的な助言と資料作成を依頼する |
| 連携部分の設計・開発・試験 | 請負 | 要件定義で仕様が固まった後なので、完成させる内容を決められる |

**② 契約書の確認**: K 社から示された請負契約の案をチェックリストで確認し、次の点を修正しました。

| 項目 | 当初の案 | 修正後 |
| --- | --- | --- |
| 著作権 | すべて K 社に残し、ツバメ情報システムに利用を許諾 | 連携部分のプログラムの著作権は、翻案権なども含めてツバメ情報システムに譲渡。K 社が以前から持つ汎用的な部品は K 社に残し、利用を許諾。K 社は著作者人格権を行使しない |
| 検収 | 納品後 5 日以内に通知がなければ合格 | 受入れ試験の期間を 15 日とし、合格の基準を別紙で定める |
| 再委託 | 定めなし | 事前の書面による承諾を条件とし、再委託先にも同じ秘密保持・安全管理の義務を負わせる |
| 個人データ | 定めなし | 試験には個人を識別できないよう加工したデータを使い、本番の個人データは渡さない。万一扱う場合の安全管理と、終了時の削除を定める |

開発中は K 社の技術者がツバメ情報システムの事務所で作業する日もあるため、作業の指示は必ず K 社のリーダーを通じて行うことをプロジェクトの全員に周知しました（偽装請負の防止）。

**③ 個人情報の取扱いルールの見直し**: 事前決済の追加で扱う情報が変わるため、台帳を見直しました。

| 個人情報 | 取得元 | 利用目的 | 保管場所 | 見られる人 | 委託先・提供先 |
| --- | --- | --- | --- | --- | --- |
| 予約者の氏名・電話番号・来店履歴 | 予約画面（店舗の顧客として登録） | 予約の受付と店舗への連絡 | ヨヤクルのデータベース | 店舗、ツバメ情報システムのサポート担当（問合せ対応のときだけ） | なし |
| 決済の状態（決済済み・返金済み） | 決済代行サービスからの通知 | 予約と決済の照合 | ヨヤクルのデータベース | 店舗、サポート担当 | なし |

ルールとして、サポート担当が店舗のデータを見るのは問合せの対応中だけとし、閲覧の記録を残して毎月点検することにしました。店舗との利用規約とプライバシーポリシーには、事前決済のために決済代行サービスを利用することを追記しました。
また、漏えい等を発見したときの報告経路（発見者 → 情報セキュリティ責任者 → 事業部長）と、個人情報保護委員会への報告や本人への通知が必要かを判断する手順を、インシデント対応の手順書に加えました（[インシデント管理と問題管理](../../management/service-management/incident-problem/)）。

## 例題

**問** A社はB社とプログラム開発の請負契約を結んだ。A社の担当者がB社の開発者に対して、作業の順序を直接指示した。この行為の問題点は何か。

**解き方** 請負契約では、作業者への指揮命令は受注者（B社）が行います。発注者（A社）が直接指示すると、実態は労働者派遣と同じになり **偽装請負** に当たるおそれがあります。指示はB社の責任者を通じて行う必要があります。

## 試験対策のポイント

- **ip**: 権利の種類と保護対象の対応、著作権が登録不要であること、不正アクセス禁止法の対象行為、契約形態ごとの指揮命令者が頻出です。
- **fe**: プログラムのどの部分が著作権で保護されるか、職務著作・委託開発の権利の帰属、個人情報の第三者提供のルールなど、事例への当てはめが問われます。
- **ap**: 契約形態ごとの責任範囲を踏まえた判断や、個人情報の取扱いの適否を問う事例問題に備えます。
